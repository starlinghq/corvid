# Claude Code's terminal UI: rendering architecture, documented failures, praised features (state as of 21 October 2026)

Scope note for the report writer. Claude Code (`@anthropic-ai/claude-code`) was first published to npm as 0.2.6 on 2025-02-24, reached 1.0.0 on 2025-05-22, 2.0.0 on 2025-09-29, and the latest version at research time is 2.1.307, published 2026-10-21; the registry holds 551 versions, roughly one release per day — [npm registry metadata](https://registry.npmjs.org/@anthropic-ai/claude-code). The project CHANGELOG has 427 version headings and no dates, so every date below comes from the npm registry's `time` map and every version-attributed feature/fix from [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md). GitHub reaction counts and issue states were read on 2026-10-21. "Classic renderer" below means the scrollback-based renderer that Claude Code has used since 2025; "fullscreen renderer" means the alternate-screen renderer introduced in March/April 2026.

## Key Question 1: Rendering architecture (Ink + React + Yoga, inline vs alternate screen, how streaming and the live region are drawn, what Anthropic has said)

### Takeaway
Claude Code is a React application rendered to the terminal by a heavily customized fork of Ink with Yoga flexbox layout, built with Bun; for its first ten months it rendered inline into the terminal's native scrollback (Ink `<Static>` for committed transcript plus a live region), which forced a clear-and-redraw whenever content scrolled off-screen and produced its "signature flicker". Anthropic rewrote the renderer twice: a cell-diffing "differential renderer" with a 16 ms frame budget (2.0.72, Dec 2025, rolled out to everyone Jan 21 2026) that still lives in scrollback, and an opt-in-then-default alternate-screen "fullscreen" renderer with a virtual viewport and mouse support (`CLAUDE_CODE_NO_FLICKER=1`, 2.1.89, 31 Mar 2026; `/tui fullscreen`, 2.1.110, 15 Apr 2026). As of October 2026 both renderers coexist: fullscreen is a "research preview" that is nonetheless the default for accounts that first used Claude Code on/after 6 May 2026 and for attached background sessions, while the classic renderer remains the default for older installs and is mandatory in screen-reader mode.

### Cited Findings

**Stack and provenance (primary sources)**
- Claude Code is written in TypeScript; "The UI is written in React using the Ink framework"; it uses Yoga ("Meta's open-source constraint-based layout system") because terminal apps must support "all sizes of terminals"; Bun is used for building and packaging; npm for distribution. Boris Cherny on why: "We wanted a tech stack which we didn't need to teach: one where Claude Code could build itself", and "around 90% of Claude Code is written with Claude Code". Team: Boris alone, Sid Bidasaria joined Nov 2024, ~10 engineers by July 2025; dogfooding Nov 2024, GA May 2025; "about 60–100 internal releases per day", about one external release per day. (Published 2025-09-23; the section "Redesigning the terminal UX" is paywalled.) — [Pragmatic Engineer: How Claude Code is built](https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built)
- Anthropic's Ink is a fork maintained by Boris Cherny: on 2025-04-18 a commenter on the original flicker issue wrote "@bcherny, bcherny/ink#8 would probably fix this", i.e., the renderer lived in the `bcherny/ink` fork at that time. — [Issue #769](https://github.com/anthropics/claude-code/issues/769)
- Chris Lloyd (Anthropic, "I work on TUI rendering for Claude Code"), 2026-01-21, on why the classic renderer flickers: "other programs like Neovim and Codex use the "alternate screen buffer" which means they don't use scrollback and reimplement their own scrolling. CC uses scrollback (because that's what most users expect) which it has to clear entirely and redraw everything when it changes (causing tearing/flickering). There's no way to incrementally update scrollback in a terminal." — [HN comment 46706299](https://news.ycombinator.com/item?id=46706299)
- Same engineer on the frame pipeline: "Most people's mental model of CC is that "it's just a TUI" but it should really be closer to "a small game engine". For each frame our pipeline constructs a scene graph with React -> layout elements -> rasterize them to a 2d screen -> diff that against the previous screen -> _finally_ use the diff to generate ANSI sequences to draw. We have a ~16ms frame budget so we have roughly ~5ms to go from the React scene graph to ANSI written." Also: GC pauses "On slower machines we were seeing this be in the order of seconds, not ms and when somebody is typing all they feel is the 1 character that's stuttering." — [HN comment 46706040](https://news.ycombinator.com/item?id=46706040)
- Same engineer on what changed in the rewrite: "1. Since we no longer have <Static> components the app re-renders much more frequently with larger component trees. We were seeing unusual GC pauses because of having too much JSX... Better memoization has largely solved that. 2. The new renderer double buffers and blits similar cells between the front and back buffer to reduce memory pressure. However, we were still seeing large GC pauses from that so I ended up converting the screen buffer to packed TypedArrays." (This confirms the pre-rewrite design used Ink's `<Static>` component, which commits finished output to scrollback once, above a re-rendered live region.) — [HN comment 46701325](https://news.ycombinator.com/item?id=46701325)
- Rollout and metric: "we shipped our differential renderer to everyone today. We rewrote our rendering system from scratch and only ~1/3 of sessions see at least a flicker. Very, very few sessions see flickers in rapid succession... We've also been working upstream to add synchronized output / DEC mode 2026 support to environments where CC runs and have had patches accepted to VSCode's terminal [xtermjs/xterm.js#5453] and tmux [tmux/tmux#4744]. Synchronized output totally eliminates flickering. As always, I recommend using Ghostty which has 2026 support and zero flicker." (posted 2026-01-21T04:11Z) — [HN comment 46701013](https://news.ycombinator.com/item?id=46701013)
- Clarifying the 1/3 metric: "it's dependent on screen height and what you do. Most people will not see _any_ flickers at all. Some people with short screens (typically VSCode users because by default the terminal opens fairly short) will see flickers. Previously, if something rendered offscreen users would see a flicker for _every subsequent frame_ regardless of wether anything was actually changing. Now they will only see a flicker occasionally when it's _absolutely_ needed. Once or twice vs thousands... the metric really tracks when CC emits a "clear scrollback" operation. If the user is in a terminal that supports DEC 2026 they won't see a flicker even if we emit that clear scrollback command." — [HN comment 46706299](https://news.ycombinator.com/item?id=46706299)
- tmux pane height matters: "How tall is your tmux pane? If it's very small it might still flicker as CC tries to redraw scrollback... Another option is to rebuild tmux from latest source so it buffers synchronized output, which should prevent the flicker entirely." — [HN comment 46701498](https://news.ycombinator.com/item?id=46701498)
- Thariq Shihipar (Anthropic), 2025-12-17: "We've rewritten Claude Code's terminal rendering system to reduce flickering by roughly 85%". Thread content (via thread mirror): terminals have a viewport and a scrollback buffer; when content exceeds the viewport, rendering happens offscreen; Claude Code "redraws the viewport dozens of times per second"; rendering offscreen or resizing forces the scrollback to be cleared, causing flicker; the fix diffs each cell and emits only minimal escape sequences, with full redraws only when necessary; alternate screen was considered and rejected "for now" because users lose Cmd+F, text selection and copy/paste; the team used property-based tests that rendered thousands of random UI states (widths, content lengths, Unicode edge cases) through old and new renderers and compared output. — [X thread 2001439019713073626](https://x.com/trq212/status/2001439019713073626), mirrored at [ThreadReader](https://threadreaderapp.com/thread/2001439019713073626.html)
- Thariq quoted by Peter Steinberger in Dec 2025: "We value this native experience a lot. We may explore alternate screen mode in the future, but our bar is quite high." Steinberger's write-up says Ink "didn't support the kind of fine-grained incremental updates needed for a long-running interactive UI", so Anthropic "rewrote the renderer from scratch" keeping React as the component model, and credits Mario Zechner's `pi` as "the gold-standard for differential rendering"; he argues selection, scrollback and search should "stay native". — [steipete.me: The Signature Flicker](https://steipete.me/posts/2025/signature-flicker)
- Changelog entries for the renderer rewrites: 2.0.10 (2025-10-07) "Rewrote terminal renderer for buttery smooth UI"; 2.0.12 "Avoid flickering in `/model` selector"; 2.0.14 "Several improvements to rendering"; 2.0.43 (2025-11-17) "Fixed duplicate rendering of some messages in the UI" and "Fixed some visual flickers"; 2.0.72 (2025-12-17) "Reduced terminal flickering" (the differential renderer); 2.1.69 (2026-03-04) "Fixed terminal flicker caused by animated elements at the scrollback boundary"; 2.1.83 (2026-03-24) "Reduced scrollback resets in long sessions from once per turn to once per ~50 messages"; 2.1.84 (2026-03-25) "Reduced terminal flickering when animated tool progress scrolls above the viewport". — [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); dates from [npm registry](https://registry.npmjs.org/@anthropic-ai/claude-code)
- The Dec 2025 rewrite was rolled back and re-rolled out: a trade-press summary of Shihipar's 2026-01-22 post says "Anthropic has re-rolled out the updated rendering system to users after an earlier rollback", restates the 16 ms budget/5 ms React-to-ANSI figure and the "small game engine" framing, and says Shihipar estimated the migration would have taken a single engineer "one to two years without Claude Code". — [Analytics India Magazine, 2026-01-24](https://analyticsindiamag.com/ai-news-updates/claude-code-uses-react-to-render-its-tui)

- Boris Cherny, 2026-04-01: "Today we're excited to announce NO_FLICKER mode for Claude Code in the terminal. It uses an experimental new renderer that we're excited about. The renderer is early and has tradeoffs, but already we've found that most internal users prefer it over the old renderer. It also supports mouse events (yes, in a terminal). Try it: CLAUDE_CODE_NO_FLICKER=1 claude" — [X post 2039421575422980329](https://x.com/bcherny/status/2039421575422980329); same text on [Threads](https://www.threads.com/@boris_cherny/post/DWmbMxDk_WA). - Thariq Shihipar, 2026-04-01: "not an April Fools joke, we rewrote the Claude Code renderer to use a virtual viewport you can use your mouse, the prompt input stays at the bottom, and a lot more small UX wins people have been asking for it's experimental so give us your feedback" — [X post 2039453692592873587](https://x.com/trq212/status/2039453692592873587)
- Official description: "Fullscreen rendering is an alternative rendering path for the Claude Code CLI that eliminates flicker, keeps memory usage flat in long conversations, and adds mouse support. It draws the interface on the terminal's alternate screen buffer, like `vim` or `htop`, and only renders messages that are currently visible. This reduces the amount of data sent to your terminal on each update. The difference is most noticeable in terminal emulators where rendering throughput is the bottleneck, such as the VS Code integrated terminal, tmux, and iTerm2." Status: "Fullscreen rendering is a research preview". "The input box stays fixed at the bottom of the screen instead of moving as output streams in... Only visible messages are kept in the render tree, so memory stays constant regardless of conversation length." — [Fullscreen rendering docs](https://code.claude.com/docs/en/fullscreen)
- Fullscreen as default (docs table, Oct 2026): classic if `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` or `CLAUDE_CODE_NO_FLICKER=0`; fullscreen if `CLAUDE_CODE_NO_FLICKER=1`; classic after a failed fullscreen start; classic in iTerm2 `tmux -CC` or over SSH to Claude Code on Windows; otherwise the saved `tui` setting; otherwise, for sessions that fetch feature flags, "you first used Claude Code on or after May 6, 2026 → Fullscreen", and for non-flag sessions (Bedrock/Vertex/Foundry/telemetry off) "this machine's first Claude Code launch ran v2.1.239 or later → Fullscreen"; "Anything else → Classic". Older installs get a startup dialog offering the switch; "Claude Code stops offering after it has shown the dialog on three launches". Attached background sessions always render fullscreen; screen-reader mode always uses classic. — [Fullscreen rendering docs](https://code.claude.com/docs/en/fullscreen)
- `/tui` command and `tui` setting added in 2.1.110 (2026-04-15): "run `/tui fullscreen` to switch to flicker-free rendering in the same conversation"; `autoScrollEnabled` added the same release. `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` added in 2.1.132 (2026-05-06) "to opt out of the fullscreen alternate-screen renderer and keep the conversation in the terminal's native scrollback". 2.1.239 (2026-08-21): "Added the one-time fullscreen renderer offer on Bedrock, Vertex, Foundry and other previously excluded setups; new installs there now start in fullscreen". — [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Fullscreen's own failure handling: after one failed start "Claude Code tries fullscreen rendering again in the next session"; after two, it "keeps using the classic renderer until you update Claude Code or run `/tui fullscreen`" (behaviour since 2.1.236; "Before v2.1.236, Claude Code kept starting sessions in fullscreen rendering after a failed start"). A session counts as started once it has drawn its first frame and stayed up 10 s or exited cleanly. — [Fullscreen rendering docs](https://code.claude.com/docs/en/fullscreen)
- Fullscreen's known rendering weakness: "Fullscreen rendering sends only the cells that changed between frames. Some terminals, most commonly Windows Terminal and other ConPTY-backed hosts, coalesce these positioned writes incorrectly and leave fragments of earlier output on screen until you resize the window." Workaround `CLAUDE_CODE_ALT_SCREEN_FULL_REPAINT=1` (repaint every cell every frame), enabled automatically on Windows for background sessions and agent view. — [Fullscreen rendering docs](https://code.claude.com/docs/en/fullscreen)
- Changelog for the fullscreen renderer's maturation (selection): 2.1.92 "Fixed an issue where the same message could appear at two positions when scrolling up in fullscreen mode (iTerm2, Ghostty, and other terminals with DEC 2026 support)"; 2.1.94 "Fixed an alt-screen rendering bug where content height changes mid-scroll could leave compounding ghost lines"; 2.1.97 "Added focus view toggle (Ctrl+O) in NO_FLICKER mode", fixes for zellij artifacts, Windows Terminal wheel speed, Warp Shift+Enter, Korean/Japanese copy on Windows; 2.1.152 (2026-05-26) "Fixed terminal styling degrading in very long sessions by recycling the renderer's style pool"; 2.1.183 (2026-06-19) "Fixed fullscreen TUI corruption (statusline mid-screen, duplicated spinner rows, merged text) in Windows Terminal under heavy nested-subagent load"; 2.1.224 (2026-08-07) "keep the full pre-compaction history in scrollback across repeated compactions"; 2.1.232 (2026-08-13) "long sessions stay responsive because the whole conversation is no longer re-normalized on every update"; 2.1.246 (2026-08-25) "Fixed memory growing with session length in the fullscreen and Ctrl+O transcript views"; 2.1.268 (2026-09-10) adding/removing a prompt line "now repaints as fast as typing a character instead of re-rendering the visible transcript"; 2.1.282 (2026-09-24) "Fixed a blank screen flashing before the first frame when starting in fullscreen mode"; 2.1.292 (2026-10-06) "Fixed fullscreen mode sending a full-screen clear on every window resize and Ctrl+L when iTerm2 is detected, which may be what filled iTerm2's scrollback with stale pages"; 2.1.301 (2026-10-15) "Fullscreen mode: Fixed `/compact` and auto-compact briefly freezing the UI while the visible transcript is rebuilt". — [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

**Synchronized output (DEC private mode 2026)**
- "Claude Code probes the terminal for synchronized-output support at startup and uses it when the terminal reports it." "tmux releases through the 3.6 series don't implement synchronized output, so under those versions you may see more flicker during redraws". — [Fullscreen rendering docs](https://code.claude.com/docs/en/fullscreen)

**What the March 2026 source leak revealed about the renderer (third-party analyses; treat specifics as unverified)**
- The leak: "Version 2.1.88 of the @anthropic-ai/claude-code npm package shipped with a source map file"; Anthropic confirmed on 2026-03-31; "Nearly 2,000 TypeScript files and more than 512,000 lines of code"; Anthropic: "No sensitive customer data or credentials were involved or exposed" and "This was a release packaging issue caused by human error, not a security breach"; discovered by Chaofan Shou. — [The Hacker News, 2026-04-01](https://thehackernews.com/2026/04/claude-code-tleaked-via-npm-packaging.html)
- Renderer pipeline per a source-reading write-up: `src/ink/` is "a forked, heavily customized engine, not the stock npm package"; custom `react-reconciler` host config in `src/ink/reconciler.ts` (React 19, ConcurrentRoot); Yoga layout runs in `resetAfterCommit`; six stages: reconciliation → Yoga layout → output ops (`render-node-to-output.ts`) → `Screen` buffer (`screen.ts`) → double-buffered diff (`renderer.ts`, `log-update.ts`) → terminal write; cells store integer indices into a `CharPool`; "Alternating between frontFrame / backFrame Screen buffers"; unchanged regions "copied directly from the previous frame's Screen buffer" (blit); frame rate throttled by `FRAME_INTERVAL_MS`; `AlternateScreen.tsx` exists and "In Alt Screen mode, content height must exactly equal the terminal row count"; input via `termio/`, `events/`, `usePasteHandler` distinguishing typing from pasting by time threshold; Kitty keyboard protocol and modifier protocol listed as supported terminal modes; virtual scrolling constants `DEFAULT_ESTIMATE = 3`, `OVERSCAN_ROWS = 80`, `MAX_MOUNTED_ITEMS = 300`, `SLIDE_STEP = 25`; cited components include `ToolUseLoader.tsx` (blinking indicator via `useBlink`), `Spinner/` (uses `useAnimationFrame` "at fixed intervals, rather than relying on `setInterval`"), `FileEditToolDiff.tsx`, `permissions/PermissionRequest.tsx`, `src/hooks/useVirtualScroll.ts`, `useGlobalKeybindings.tsx`; 140+ components, 85 hooks. (Undated; provenance not stated.) — [claude-harness.dev: Terminal UI](https://claude-harness.dev/en/articles/14-terminal-ui)
- A second source-reading chapter adds: stock Ink "allocates one JavaScript object per cell per frame and diffs at the string level" whereas the fork packs cells into an `Int32Array` with two words per cell (`charId`; `styleId[31:17] | hyperlinkId[16:2] | width[1:0]`), with `CharPool`/`StylePool`/`HyperlinkPool` shared across frames and pools reset every 5 minutes; the diff walks only the damage rectangle; blit is disabled when `prevFrameContaminated`, when an absolute-positioned node was removed, or when layout shifted; patch optimizer "cut bytes by 30-50%"; single `write()` per frame; "typed-array diff takes under 0.5ms on 200x120 (versus 3-5ms for an object-based diff)"; worst-case frame ~12 ms; `throttle(deferredRender, FRAME_INTERVAL_MS, { leading: true, trailing: true })` with `FRAME_INTERVAL_MS` = 16 ms and `deferredRender` via `queueMicrotask`; scroll frames on a separate 4 ms timer (`FRAME_INTERVAL_MS >> 2`); resize handled synchronously; BSU/ESU wrap each frame; on resize in alt-screen mode the erase is deferred inside the BSU/ESU block; `AlternateScreen` enters DEC 1049 on mount via `useInsertionEffect` so `ENTER_ALT_SCREEN` is written before the first frame; each alt-screen frame begins with `CSI H` and carries a DECSTBM scroll-region hint; streaming markdown uses a 500-entry LRU of `marked.lexer()` results and a `StreamingMarkdown` component tolerant of unclosed syntax; code highlighting lazy via `Suspense` + cli-highlight; "Spinners are handled by blitting: only a spinner's 3-4 cells re-render on a steady-state frame"; `OffscreenFreeze` keeps off-screen spinners/timers from forcing full-screen resets; `useDeclaredCursor` lets a component declare where the terminal cursor belongs (for IME preedit and screen readers); mouse via SGR 1003 with 500 ms multi-click timeout; keyboard events dispatched through a custom DOM with capture/target/bubble phases; `REPL.tsx` ~5,000 lines; `CLAUDE_CODE_DEBUG_REPAINTS` flag. (Undated; based on the leaked tree.) — [claude-code-architecture book, ch. 13](https://github.com/mikeoptimax/claude-code-architecture/blob/main/book/ch13-terminal-ui.md)
- A 2026-04-01 leak walkthrough (author notes it is "mainly LLM generated") lists `ink/reconciler.ts`, `ink/dom.ts`, `ink/layout/` ("Yoga-based layout engine"), `ink/events/` ("Keyboard, mouse, focus events"), `VirtualMessageList` ("Virtualized scrolling"), and `REPL.tsx` hosting `Messages.tsx`, `PromptInput`, `StatusLine`, `Spinner.tsx`; it calls `ink.tsx` "~9,000 lines" whereas the claude-harness article says 1,722 lines — the two figures conflict. — [zainhas.github.io](https://zainhas.github.io/blog/2026/inside-claude-code-architecture/); [claude-harness.dev](https://claude-harness.dev/en/articles/14-terminal-ui)

- A different community diagnosis of the scroll-to-top "stroboscope" (May 2026, unverified) says the TUI "emits `ED2` (`\x1b[2J`) inside a DEC 2026 synchronized update block. ### Inferences
- The architecture went through three distinct eras: (1) stock-ish Ink with `<Static>` committing transcript lines to scrollback and a re-rendered live region at the bottom (Feb–Dec 2025), (2) a from-scratch cell-diffing renderer that still draws into the main screen/scrollback (Dec 2025–), and (3) a parallel alternate-screen renderer with a virtual viewport (Mar 2026–). Anthropic never abandoned (2); it is still the "classic" renderer and the only one screen-reader users get.
- The maintainers' own framing is that inline/scrollback rendering is fundamentally limited ("There's no way to incrementally update scrollback in a terminal"), and that the practical fix for flicker is either the terminal implementing DEC 2026 or moving to the alternate screen. The ~1/3-of-sessions flicker figure (Jan 2026) measured "clear scrollback" emissions, so terminals with synchronized output hide the remaining flicker.
- The leak-derived descriptions (Int32Array cell buffers, pooled chars/styles, blit of unchanged regions, 16 ms throttle, DEC 2026 frame wrapping, SGR 1003 mouse) are consistent with Chris Lloyd's public statements (packed TypedArrays, double buffer + blit, 16 ms budget), which raises confidence in them, but they remain third-party readings of a leaked tree and should be cited as such.
- The "memory stays constant" claim for fullscreen is a design intent, not a guarantee: Anthropic itself shipped a fix for "memory growing with session length in the fullscreen and Ctrl+O transcript views" five months after the renderer launched (2.1.246).

## Key Question 2: Documented failures (with issue numbers, dates, status as of 21 Oct 2026)

### Takeaway
The two oldest and most-upvoted UI bugs in the repository — spinner-driven flicker (#769, Apr 2025, ~300 👍) and the "console scrolls to the top while Claude streams" stroboscope (#826, Apr 2025, ~690 👍) — are still open in October 2026; Anthropic's answer to both became "switch renderers" (fullscreen), which in turn created a second family of still-open complaints (lost native scrollback, lost tmux copy mode, mouse capture breaking selection, wheel-sends-arrow-keys), while a third family — copy/paste of rendered output carrying indentation, trailing spaces and hard wraps (#18170, 300 👍) — is unsolved in either renderer. Performance bugs (100% CPU at idle, keystroke lag, memory growth) were worked down through dozens of point fixes in 2026 but several tracking issues remain open; Windows/ConPTY, tmux, CJK/IME and screen-reader regressions recur with each renderer change.

### Inferences
- The oldest flicker/scroll issues were never "fixed" in the classic renderer in the sense of being closed with a cause; Anthropic reduced their frequency (85% / "once or twice vs thousands") and then offered the alternate screen as the complete fix, which the maintainers themselves had rejected in Dec 2025 for exactly the reasons users now cite (#28077, #42670, #60185, #70857).
- The copy/paste-of-output family (#18170 and friends) is structural: a cell-buffer renderer pads lines to terminal width and inserts hard wraps, so terminal selection sees padding rather than the source text. The project's answer has been in-app copy paths (`/copy`, copy-on-select) rather than changing what the terminal receives.
- Most Windows problems in 2026 are ConPTY/Windows-Terminal rendering of positioned writes and mouse-tracking support, not shell issues; the project's mitigations are degraded modes (no line-by-line streaming, no mouse tracking, full repaint).
- Stale-bot closures ("not planned" after inactivity) hide the true open count: several accessibility and rendering regressions (#63500, #75360, #53857) were closed without a fix while users still reported them.

## Key Question 3: Features and keybindings (as documented in October 2026, with introduction versions where known)

### Takeaway
Claude Code's interaction model is a single prompt box with a small set of global chords (Esc to interrupt, Esc Esc to rewind, Shift+Tab to cycle permission modes, Ctrl+O transcript, Ctrl+T todo list, Ctrl+B background, Ctrl+R history, Ctrl+G external editor, Ctrl+V image), prefix-triggered modes (`/` commands with fuzzy menu, `@` fuzzy file picker, `!` shell mode, `#` memory, `:` emoji), a full vim editing mode, a JSON keybindings file with contexts and chords (2.1.18), a scriptable status line fed by JSON (1.0.71), a theme system with custom JSON themes, permission prompts whose options encode scope (once / don't-ask-again rule / session / switch to auto) with Tab-to-comment, and since 2026 a growing fullscreen-only feature set (mouse, in-app selection, diff panel, less-style transcript search, scrollbars) plus an agent view for multi-session work.

### Inferences
- Nearly every shortcut has a terminal-portability escape hatch (Ctrl+J for Shift+Enter, `Ctrl+X Ctrl+S` for Ctrl+Enter, Alt+M for Shift+Tab on old Windows runtimes, `\`+Enter), and the docs enumerate per-terminal behaviour; a new TUI should budget for the same matrix (kitty keyboard protocol, modifyOtherKeys, ConPTY VT mode, tmux extended-keys).
- The Esc key is overloaded (interrupt, close dialog, decline permission, vim NORMAL, double-press rewind/clear) and the changelog shows repeated regressions around it; the double-press pattern (Esc Esc, Ctrl+C twice, Ctrl+D twice within 800 ms, Ctrl+X Ctrl+K twice within 3 s) is Claude Code's standard guard for destructive actions.
- Dangerous single keys were later guarded or removed: `y`/`n` as confirm keys (removed 2.1.280), Tab as thinking toggle (moved to Alt+T), `←` to background a session (10-second delay plus unsent-text cancel after #64657), Ctrl+L double-press `/clear` (removed 2.1.238).

### Gaps
- Exact introduction versions for `@` fuzzy picker ranking, `/resume` picker features and the PR footer badge were not pinned beyond what the changelog greps returned.
- The settings-reference entries (types/defaults) for `tui`, `theme`, `prefersReducedMotion`, `spinnerVerbs`, `maxProseWidth` etc. were only read as index rows; defaults are not recorded here.

## Key Question 4: What users praise and what they complain about (evidence, attributed)

### Takeaway
Praise clusters on interaction design rather than rendering: Esc Esc rewind/checkpoints, plan mode, message queueing while Claude works, the todo list, menu-driven questions and the overall "it's just chat" simplicity; complaints cluster on rendering and terminal citizenship — flicker and scroll-jumping (the two most-upvoted issues in the repo), lost native scrollback/search/selection under the fullscreen renderer, copy/paste artifacts, idle CPU and lag in long sessions, Windows/tmux breakage — and on Anthropic's long silences on those threads.

### Inferences
- The praise is for *agent-interaction* affordances (undo, plan mode, queueing, visible todo/thinking) that are cheap to copy and independent of renderer choice; the complaints are almost all consequences of the renderer strategy (scrollback clear-and-redraw, then alternate screen). A design that keeps native scrollback/selection/search while avoiding full redraws (the approach Steinberger attributes to `pi`, and that Anthropic's differential renderer approximated) is what the loudest critics ask for.
- User tolerance for alternate-screen mode is conditional on exit paths: the features users demanded after the switch (`[` to dump the transcript to scrollback, `v` to open in `$EDITOR`, `/export`, `DISABLE_ALTERNATE_SCREEN`, `DISABLE_MOUSE`, `DISABLE_MOUSE_CLICKS`, modifier-held native selection) are the minimum a new alt-screen TUI should ship on day one.
- Communication matters as much as fixes: the sharpest sentiment in the threads is about months of silence on top-voted issues and stale-bot closures, not about any single bug.
