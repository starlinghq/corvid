Conventions: "SRC" citations point at files on `main` of github.com/openai/codex as fetched on 2026-10-21 (raw.githubusercontent.com URLs); they describe the October 2026 code, not history. Issue/PR/discussion numbers are in openai/codex unless stated. Third-party sources (Daniel Vaughan's blog, InfoQ, HN comments) are marked as such. ## Key question 1: The rewrite from TypeScript/Ink to Rust (codex-rs): when, why, and what changed for users

### Takeaway
OpenAI announced the move on 2025-05-30 in discussion #1174 ("Codex CLI is Going Native"), citing four reasons: zero-dependency install (Node 22+ was "frustrating or a blocker"), native security bindings (Rust sandboxing already shipped for Linux), performance/memory (no GC), and an extensible wire protocol. The first Rust-powered release was rust-v0.2.0 on 2025-07-01, the TypeScript code was deleted from the repo on 2025-08-08 (PR #2048), and the cutover meta-issue #1262 was closed 2025-10-28. Notably, none of the stated reasons was about the terminal UI itself; the UI stack (Ink → ratatui) changed as a consequence, and the Rust TUI then went through its own multi-stage evolution (inline scrollback mode 2025 → alternate-screen toggle Jan 2026 → "fullscreen transcript" default Sept 2026).

### Inferences
- The rewrite was motivated by distribution (no Node), sandboxing and process footprint, not by Ink's rendering problems; the TUI stack change was collateral. Design lesson for Corvid: a single-binary install and native sandbox integration were the user-visible wins; the UI framework choice then dictated a separate multi-year scrollback/alt-screen saga (Q2/Q3).
- The P1 burndown list is a good checklist of what users considered table stakes in a rewrite TUI in mid-2025: Ctrl+C semantics, Markdown rendering, copy/paste, `/model`, `/approvals`, `/diff`, context-window display, session resume, `@` file search.

### Gaps
- I could not find any OpenAI statement that rendering quality, flicker or Ink itself was a reason for the rewrite; absence noted (InfoQ explicitly does not mention Ink or startup time).
- The exact Rust release that first included Windows binaries is not named in #1300 (only "latest version", Aug 12, 2025).

## Key question 2: Rendering model of the Rust TUI (codex-rs/tui): viewports, scrollback, streaming, composer, approvals, resize, capability detection

### Takeaway
Codex ships two transcript ownership modes (SRC `transcript_mode.rs`: `TranscriptMode::{Owned, Terminal}`). "Scrollback"/Terminal mode (the 2025–Sep 2026 default) is an inline, bottom-anchored viewport built on a copy of ratatui's `Terminal` (`custom_terminal.rs`) where finished history is pushed into the terminal's native scrollback by hand-written scroll-region escapes (`insert_history.rs`), with overlays (Ctrl+T transcript, pickers) jumping to the alternate screen; "Fullscreen"/Owned mode (default since rust-v0.157.0, 2025-09-25) keeps the whole conversation in Codex-owned, paginated buffers on the alternate screen with mouse capture, in-app selection/copy, search and expandable diffs. Startup probes (cursor position, OSC 10/11 colors, kitty keyboard protocol) run under a short deadline; bracketed paste, focus events, DEC 2026 synchronized output, OSC 8 links, OSC 9 notifications, Kitty/Sixel images, and a width-resize transcript reflow are all present in the Oct 2026 code.

Design intent lives in module doc-comments quoted below.

Inline ("scrollback") mode — the ratatui inline-viewport pattern, hand-rolled:
- `tui.rs`: "/// Initialize the terminal (inline viewport; history stays in normal scrollback)"; the `Tui` struct keeps `alt_screen_enabled` ("When false, overlays stay on the inline screen") and `alt_screen_active`; `set_alt_screen_enabled` "Set whether overlays switch to the alternate screen or stay inline"; `enter_alt_screen` flushes queued history first because "History queued before opening an overlay belongs to the inline transcript"; `TranscriptMode::resolve(self.owned_screen, self.alt_screen_enabled)` picks the mode — [SRC tui.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs).
- `custom_terminal.rs` is "derived from `ratatui::Terminal`" (MIT header, Ratatui Developers 2023-2025) and is constructed via `CustomTerminal::with_options_and_cursor_position(backend, cursor_pos)` using the probed cursor row — [SRC custom_terminal.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/custom_terminal.rs), [SRC tui.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs).
- `insert_history.rs`: "Codex uses the terminal scrollback itself for finalized chat history, so inserting a history cell is an escape-sequence operation rather than a normal ratatui render. Untrusted content follows ratatui's control-character filtering before semantic hyperlinks add trusted escapes." It defines `InsertHistoryMode::{Standard, FullScreen}` — "Full-screen insertion preserves terminal-native scrollback when partial scroll regions are unreliable and keeps terminal-managed soft wrapping intact for Zellij" — and its own crossterm `Command`s `SetScrollRegion(Range<u16>)` / `ResetScrollRegion` (which `panic!` if executed via WinAPI: "use ANSI instead"). Standard mode sets the scroll region to rows 1..top-of-viewport, puts the cursor at the bottom of that region and writes lines there; if the viewport is not yet at the bottom it is scrolled down first — [SRC insert_history.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/insert_history.rs).
- This is the same technique ratatui documents for `Terminal::insert_before` with its `scrolling-regions` feature: inserted lines "scroll the area above the viewport upward... the topmost lines move into the terminal's scrollback buffer"; "With the `scrolling-regions` feature, it does this without clearing and redrawing the viewport"; `Viewport::Inline(u16)` "spans the full terminal width and its top-left corner is anchored to column 0" at the cursor row — [ratatui 0.30.2 Terminal docs](https://docs.rs/ratatui/latest/ratatui/struct.Terminal.html), [ratatui Viewport docs](https://docs.rs/ratatui/latest/ratatui/enum.Viewport.html). Codex does not call ratatui's `insert_before`; it uses its own `insert_history` on its own `Terminal` copy (SRC above).
- A user-written protocol trace (issue #27644, 2026-06-11, v0.139.0) describes the emitted sequence: set region rows 1..B, `ESC[{k}S` scroll up k lines, reset region, repaint rows below inside a DEC 2026 synchronized-output block; this works in iTerm2/kitty but xterm.js (VS Code, Cursor, Orca) deletes lines on partial-region `CSI n S` instead of moving them to scrollback → "permanent transcript gaps"; a commenter traced surviving `CSI n S` calls to `tui.rs` `draw()` and `update_inline_viewport_for_resize_reflow()`. Open; #14277 and #42020 were marked duplicates of it by etraut-openai on 2026-10-12 — [Issue #27644](https://github.com/openai/codex/issues/27644).
- Alternate screen policy: PR #8555 (merged ~2026-01-09, per a third-party mirror) added `tui.alternate_screen = auto|always|never` and `--no-alt-screen`; `auto` detects Zellij via `ZELLIJ` env and skips the alt screen because Zellij strictly follows xterm's no-scrollback-in-alt-screen rule — [mirror of commit for #8555, secondary](https://forge.lthn.ai/core/core-agent-ide/commit/7daaabc795d5edd9dcab964bcce67456071d46fd). Official config reference today: `tui.alternate_screen` "Control alternate screen usage for the TUI (default: auto; auto skips it in Zellij to preserve scrollback)" — [config-reference.md](https://developers.openai.com/codex/config-reference.md); CLI: `--no-alt-screen` "Disable alternate screen mode" — [SRC cli.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/cli.rs); the docs say launch overrides "such as `--no-alt-screen` still apply" over the `/tui` choice — [developer-commands.md](https://developers.openai.com/codex/developer-commands.md).

Fullscreen ("owned") transcript mode (default since 0.157.0):
- `transcript_mode.rs`: "Effective transcript ownership for this running TUI... Terminal restrictions take precedence over the configured ownership preference. The launch-time mode survives session changes so native scrollback never receives retained-only updates." `Owned` requires both `owned_enabled` and `alternate_screen_enabled` — [SRC transcript_mode.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/transcript_mode.rs). `app.rs` has `mod owned_transcript`, `render_owned_transcript`, and branches on `tui.is_owned_screen()`; `lib.rs` reads `config.tui_fullscreen_transcript` and emits a `codex.tui.fullscreen_transcript` metric — [SRC app.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/app.rs), [SRC lib.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/lib.rs).
- `transcript_view.rs`: "A conversation viewport over the app's retained cells and its current live tail. The app owns history and pagination. This view owns only reading/selection state and bounded layout caches. Anchors address content inside an entry, so prepending history never renumbers them and rewrapping does not turn a reading position into an unrelated screen row." — [SRC transcript_view.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/transcript_view.rs).
- Rationale from the maintainer announcement "Codex CLI goes fullscreen" (fcoury-oai, 2026-09-29): the old Scrollback view "lived in the terminal's scrollback buffer, so it was limited by each terminal's settings", loaded as much history as it could at startup and older history "fell off the top"; Fullscreen loads history as you scroll with no ceiling, keeps the composer pinned, lets diffs and tool output expand individually, copies Markdown/formatted text, "streaming redraws only what changed", `F3` searches the transcript, `F2` opens unread warnings, `/side` shows a side conversation; mouse selects/expands/opens links, right-click copies, `tui.copy_on_select = auto|always|never`. Trade-offs stated: terminal/tmux scrollback no longer hold the conversation ("tmux sees only the current screen"), nothing is left in the terminal after quit (`codex resume` brings it back), Terminal.app/iTerm2 reserve the copy shortcut so Codex copies on select there, over SSH you get raw Markdown. Switch: `/tui` → Scrollback → restart; persists — [Discussion #49129](https://github.com/openai/codex/discussions/49129).
- Release notes rust-v0.157.0 (published 25 Sep [2026]): "Fullscreen transcripts are on by default, and Shift-click extends text selections (#47178, #47414)"; "tmux mouse settings are respected, and Terminal.app over SSH regains native scrollback in auto screen mode (#47399, #47417)" — [Release rust-v0.157.0](https://github.com/openai/codex/releases/tag/rust-v0.157.0). PR #46732 (merged 2026-09-20, bot-authored "copyberry") "Add selection and copying to the transcript viewer": mouse/word/line selection with drag autoscroll, keyboard selection via `Ctrl+Space`, source-anchored positions that survive resize/streaming/pagination, copies that exclude gutters and soft wraps, mouse-capture and keyboard-mode management across overlays/editor handoffs/suspend — [PR #46732](https://github.com/openai/codex/pull/46732).
- Mouse capture: a user's PTY test found default fullscreen mode enables mouse modes 1000, 1002, 1003 plus SGR 1006, and that neither `--no-alt-screen` nor `tui.alternate_screen="never"` enables them — [Issue #48664](https://github.com/openai/codex/issues/48664). Transcript surfaces retain pointer reporting across overlays and disable it before yielding [to an editor]... Refresh tmux's input policy on entry for mouse-capture requests"; `tui.rs` also defines `EnableAlternateScroll` = `CSI ? 1007 h` (wheel→arrow keys on the alt screen) — [SRC tui/tmux.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui/tmux.rs), [SRC tui/alternate_screen.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui/alternate_screen.rs), [SRC tui.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs).

Terminal resize:
- `transcript_reflow.rs`: "Terminal scrollback is not a retained widget tree: once Codex writes wrapped lines into the terminal, the terminal owns those rows. Width resize reflow treats the in-memory transcript cells as the source of truth, clears Codex-owned history, and re-emits the cells at the current width. Height-only growth also schedules a rebuild"; `TRANSCRIPT_REFLOW_DEBOUNCE = 75 ms`; `tui.rs` has `draw_with_resize_reflow` and `update_inline_viewport_for_resize_reflow` and notes "Resize is separate from `Draw` so the app can run feature-gated pre-render logic" — [SRC transcript_reflow.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/transcript_reflow.rs), [SRC tui.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs). Terminal modes and capability detection:
- `set_modes()`: `EnableBracketedPaste`, `enable_raw_mode`, Windows `set_input_record_mode`, then `keyboard_modes::enable_keyboard_enhancement` ("Enable keyboard enhancement flags so modifiers for keys like Enter are disambiguated... Some terminals (notably legacy Windows consoles) do not support keyboard enhancement flags. Attempt to enable them, but continue gracefully"), `EnableFocusChange` on non-Windows (`DisableFocusChange` on Windows) — [SRC tui.rs](https://raw.githubusercontent.com/openai/codex/main/codex-rs/tui/src/tui.rs). Kitty flags pushed: `DISAMBIGUATE_ESCAPE_CODES | REPORT_ALTERNATE_KEYS` (+ `REPORT_EVENT_TYPES` in one branch); pushes/pops are paired per screen and "process exit gets a stronger reset so the parent shell does not inherit enhanced key reporting"; "Windows terminal detection has a deadline, including WSL interop process launch. ### Inferences
- Codex's "scrollback mode" is the ratatui `Viewport::Inline` + `insert_before(scrolling-regions)` design re-implemented in-house on a vendored `Terminal`, which gave them control over wrap policy, hyperlinks, Zellij full-screen insertion and resize reflow — things the stock API doesn't offer. The cost was a long tail of terminal-specific escape-sequence bugs (xterm.js, Zellij, tmux, Windows Terminal) that the team eventually sidestepped by making the retained, alternate-screen "fullscreen transcript" the default.
- The two-region streaming model (stable lines committed to scrollback on newline boundaries, mutable tail re-rendered in place, with a table hold-back) is the key to streaming Markdown without re-flowing already-emitted text; Corvid can adopt the same split regardless of framework.
- Startup capability probing with a short shared deadline and input replay is what makes the kitty keyboard protocol and OSC color queries safe; the 2026 typing-lag bug shows what happens when such queries run synchronously on the draw/focus path.

### Gaps
- The numeric `DEFAULT_TIMEOUT` for startup probes was not read from source (a linked issue cites a 100 ms OSC 10/11 budget; unverified).
- Whether the Rust TUI emits true-color vs 256-color (or how `terminal_palette` chooses) was not determined.
- Which ratatui cargo features (e.g., `scrolling-regions`) the tui crate enables was not captured.
- I did not find an official OpenAI write-up of the rendering architecture beyond module doc-comments; the Vaughan "architecture" post is third-party and omits the inline/alt-screen details.

## Key question 5: What users praise and complain about, specifically regarding the UI (with attribution)

### Takeaway
Praise concentrates on footprint and feel — instant startup, tens of MB of RAM, no flicker/redraw glitches, history left in the terminal (pre-Sept-2026) — usually in contrast to Claude Code's Ink UI. Complaints concentrate on scrolling/scrollback, copy/selection, missing features versus competitors, and, after the fullscreen default, "don't mess with my terminal".

### Cited Findings
- jmmv (HN, ~Mar 2026, OpenCode thread): "Claude Code was using multiple GBs of RAM and 100% CPU whereas Codex was happy with 80 MB and 6%"; "the former feels sluggish and does some odd redrawing when the terminal size changes". ### Inferences
- The praise is almost entirely about properties a native, non-GC, non-React implementation gives for free (startup, RSS, no full-screen redraw); the complaints are about policy decisions (alt screen, mouse capture, copy semantics) and terminal-emulator diversity, not about Rust/ratatui. For Corvid, the choice of UI stack buys the first set; only careful terminal-mode design and a user-selectable mode avoid the second.

## Key question 6: Timeline — history versus the October 2026 state

### Takeaway
The TUI went through four eras: (1) TypeScript/Ink, Apr–Aug 2025; (2) Rust/ratatui inline "scrollback" TUI with alt-screen overlays, Jul 2025–Jan 2026; (3) the same plus `tui.alternate_screen`/`--no-alt-screen`, resize reflow, keymaps and themes, Jan–Sep 2026; (4) "fullscreen transcript" (owned, alt-screen) default with `/tui` to opt back into scrollback, from rust-v0.157.0 on 2026-09-25 through today (0.163.0 stable, 0.164.0-alpha.9).
