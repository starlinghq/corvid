# Building a fast, solid terminal UI in .NET 10 (state as of 2026-10-21)

Scope: options for Corvid's chat UI — (a) a custom renderer in .NET on raw ANSI, (b) an existing .NET TUI library, (c) a separate native TUI process over ACP. Facts below were taken from primary sources (runtime/library source on their default branches, package registries, official docs) on 2026-10-21 unless stated. "Measured here" means measured in this research container (4 vCPU Intel Xeon @ 2.10 GHz, Ubuntu 24.04.5, kernel 6.18, .NET SDK 10.0.402, rustc 1.97.0, bun 1.4.2); treat those numbers as order-of-magnitude indicators, not benchmarks of Corvid.

## Key question 1 — .NET TUI libraries as of 2026 (Spectre.Console, Terminal.Gui v2, Consolonia, others)

### Takeaway
No .NET library gives a ratatui-class combination of diff renderer + proper input decoder + inline (scrollback) mode + permissive licence except Terminal.Gui v2 (MIT, 2.5.0 on 2026-09-11), which since 2026 has an "ansi" driver with its own termios raw mode, Kitty-keyboard detection, an `AppModel.Inline` mode with `PrintAboveAsync`, and a dirty-cell flush — but it is a full widget framework (net10.0-only on its develop branch, pulls Markdig/TextMateSharp/Microsoft.Extensions.*), has a long history of flicker/driver issues, and has no synchronized-output (CSI ?2026) support in its driver code. Spectre.Console (MIT, 0.57.2, 2026-07-02) is a renderer for scrollback output with a cursor-up-and-redraw "Live" mode that still ships the brute-force clear-per-line behaviour reverted after the 2024 flicker regression, has no input layer beyond `System.Console.ReadKey`, no raw mode, no alternate-screen UI and no synchronized output; Consolonia (MIT, 12.0.3.14, 2026-10-01) is Avalonia-on-console (beta, net8.0, Avalonia 12.1.4) whose Unix backend is a vendored Terminal.Gui v1 curses driver; Terminaux and Tutu are GPL-3.0; Ratatui.cs is an FFI wrapper last published 2025-09-18.

### Inferences
- Spectre.Console is best treated as a *scrollback renderer* (markup → ANSI, tables, trees, wcwidth) and never as a frame-based UI: Live redraws the whole block each tick without a cell diff, erases line-by-line on exit, has no raw input, and cannot combine prompts with live rendering. Its ANSI writer (`Spectre.Console.Ansi`) could still be reused for styling in a custom renderer.
- Terminal.Gui v2 is the only .NET library whose driver layer matches what a Claude-Code-style UI needs (own termios raw mode, Kitty keyboard, inline mode, print-above-live-region); the cost is a large widget framework, net10.0-only on develop, heavy transitive dependencies (TextMate grammars, Markdig) that will bloat a trimmed single-file, and a driver layer that is still changing (macOS 26 ARM64 breakage fixed Jan 2026; repaint flicker closed Nov 2025). Its `UnixRawModeHelper`/`AnsiKeyboardParser` are also a useful reference implementation if Corvid writes its own.
- Consolonia's dependence on Avalonia 12 (a GUI framework) and a vendored gui.cs v1 curses driver makes it the heaviest and least "terminal-native" option; it is also net8.0-targeted and still beta.
- Licensing removes Terminaux and Tutu for a non-GPL product unless Corvid is GPL.

## Key question 2 — System.Console traps: Unix (terminfo, termios, ReadKey, signals, encoding, child processes) and Windows (console modes, VT input, code pages)

### Takeaway
On Unix, `System.Console` initialises lazily by `tcgetattr`-ing stdin, writing terminfo `keypad_xmit`, registering `atexit`/UnhandledException restoration and SIGINT/SIGQUIT/SIGCONT/SIGCHLD/SIGWINCH handlers; the first `ReadKey`/`ReadLine` switches the tty to no-ECHO/no-ICANON/no-IEXTEN (ISIG kept unless `TreatControlCAsInput`) and never switches back until exit, child-process start or SIGCONT, so a custom TUI must own termios itself and never mix `Console.ReadKey`/`ReadLine`/`GetCursorPosition` with its own raw reads; `Console.Out` is a 256-byte auto-flushing synchronized writer (one `write(2)` per call), `PosixSignalRegistration` supports SIGWINCH/SIGTSTP/SIGCONT/SIGCHLD/raw numbers but dispatches non-termination signals on the thread pool, and registering SIGTSTP makes .NET swallow the stop unless your handler stops the process itself. On Windows, .NET never enables VT processing, reads keys through `ReadConsoleInput` (VT input stays unparsed, issue open since 2021), maps `Console.OutputEncoding` to an `OSEncoding` of the console's OEM code page (emoji → `?` until you set UTF-8, which is never restored), while ConPTY hosts (Windows Terminal) turn VT processing on by default and classic conhost does not.

### Cited Findings

**Initialisation and terminfo (Unix)**
- `EnsureInitializedCore()` calls `Interop.Sys.InitializeTerminalAndSignalHandling()` ("Do this even when redirected to make CancelKeyPress works"), registers `AppDomain.CurrentDomain.UnhandledException += (_, _) => Interop.Sys.UninitializeTerminal()`, picks the terminal handle (stdout if not redirected, else stdin), writes the terminfo `KeypadXmit` string ("application mode") via `SetKeypadXmit`, and when stdin is not redirected registers `SetTerminalInvalidationHandler` "for signals that may invalidate our cached terminal settings. This includes: SIGCONT, SIGCHLD, SIGWINCH" and loads VERASE/VEOL/VEOL2/VEOF — [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs) (lines ~878–940). The write path and the stdin reader both call `EnsureConsoleInitialized()` (same file).
- Native init: `InitializeTerminalCore` does `tcgetattr(STDIN_FILENO, &g_initTermios)`; on success `g_hasTty = true`, `g_signalForBreak = c_lflag & ISIG`, and `atexit(UninitializeTerminal)`; `UninitializeTerminal` restores `g_initTermios` only if the process changed settings (`g_terminalConfigured`) and is "called on SIGQUIT/SIGINT from the signal dispatching thread, on atexit, and for AppDomain.UnhandledException" — [pal_console.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_console.c). Functions registered with `atexit` are not run when a process is killed by a signal (SIGKILL, SIGSEGV, SIGABRT) — [atexit(3) man page](https://man7.org/linux/man-pages/man3/atexit.3.html) (standard behaviour; not re-fetched in this session).
- terminfo lookup: `$TERM` selects the entry; search order is `$TERMINFO`, `$HOME/.terminfo`, then `/etc/terminfo`, `/lib/terminfo`, `/usr/share/terminfo`, `/usr/share/misc/terminfo`, `/usr/local/share/terminfo` — [TermInfo.DatabaseFactory.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/TermInfo.DatabaseFactory.cs). From the entry .NET takes `keypad_xmit`, `setaf/setab`, `orig_pairs/orig_colors`, `bell`, `clear` (+ extended `E3` to clear scrollback), `cols`/`lines`, cursor visible/invisible/address/left, `el`, title capability, and the key sequences; `max_colors` is normalised to 16/8/0 only; `CursorPositionReport` is hard-coded to `\e[6n` — [TerminalFormatStrings.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/TerminalFormatStrings.cs).
- `Console.WindowWidth/Height` on Unix: cached (`s_windowWidth`), obtained by `ioctl(TIOCGWINSZ)` on the terminal handle, falling back to terminfo `cols`/`lines`; the cache is invalidated by the SIGCONT/SIGCHLD/SIGWINCH invalidation callback — [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs) (`GetWindowSize`, `InvalidateTerminalSettings`), [pal_console.c `SystemNative_GetWindowSize`](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_console.c). `SetWindowSize` is not implemented via `TIOCSWINSZ` (comment in source).
- `Console.GetCursorPosition()` writes `ESC[6n` and reads stdin with `minChars` 0/1 and a timeout of 100 deciseconds (10 s) for the first request and 10 ds afterwards — [ConsolePal.Unix.cs `TryGetCursorPosition`](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs) (line ~482).

**Read mode, ReadKey and echo (Unix)**
- Every console read calls `SystemNative_InitializeConsoleBeforeRead(minChars=1, decisecondsTimeout=0)` → `ConfigureTerminal(...)`, which starts from `g_initTermios`, sets/clears `ISIG` according to `TreatControlCAsInput`, and for the process's own reads clears `IXON|IXOFF|ICRNL|INLCR|IGNCR` and `ECHO|ICANON|IEXTEN`, sets `VMIN/VTIME`, and applies with `tcsetattr(STDIN_FILENO, TCSANOW, …)` only if different from the cached `g_currentTermios`; `UninitializeConsoleAfterRead` merely clears `g_reading` (no restore) — [pal_console.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_console.c). `OPOST` is not touched (so `\n` → CRLF translation on output stays on).
- The managed reader reads up to 1024 bytes per `read()` and then parses with `KeyParser`; an empty read returns the VEOL/VEOL2/VEOF character; echo for non-intercepted keys is done by .NET itself (`EchoToTerminal`) — [StdInReader.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/IO/StdInReader.cs). `Console.ReadLine` on a tty uses the same managed reader (`useReadLine: !Console.IsInputRedirected`) — [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs).
- `KeyParser`: VERASE overrides terminfo; `ESC ESC …` is treated as Alt+sequence (PuTTY/rxvt); a two-char `ESC x` is Alt+key; sequences must start with `ESC [` or `ESC O`; unknown sequences are returned as single chars; `MapEscapeSequenceNumber` gives terminfo-independent fallbacks — [KeyParser.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/IO/KeyParser.cs). Documented limits of the .NET 7 rewrite: Ctrl+1/3/8/9/0 undetectable, Ctrl+Space = Ctrl+2 = NUL, Ctrl+H/I/J/M map to Backspace/Tab/Enter, Shift+digit gives only a char, Num5 → `NoName`, some keys (Alt+F4, F11) may never arrive; tested against xterm, GNOME Terminal, Linux console, PuTTY, Windows Terminal over SSH, rxvt-unicode, tmux, Alacritty; `DOTNET_SYSTEM_CONSOLE_USENET6COMPATREADKEY=1` was a .NET 7 opt-out scheduled for removal in .NET 8 — [Console.ReadKey improvements in .NET 7](https://devblogs.microsoft.com/dotnet/console-readkey-improvements-in-net-7/).
- `Console.ReadKey` throws `InvalidOperationException` when stdin is redirected; `KeyAvailable` uses `SystemNative_StdinReady` (which itself applies the read-mode termios) — [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs), [pal_console.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_console.c).
- A third-party package exists only to toggle ECHO around `Console.ReadKey(true)` and restore it in `finally` — [SeeminglyScience/UnixConsoleEcho](https://github.com/SeeminglyScience/UnixConsoleEcho).

**Output writer and encoding**
- `Console.Out` is `TextWriter.Synchronized(new StreamWriter(stream, OutputEncoding.RemovePreamble(), bufferSize: 256) { AutoFlush = true })` (`WriteBufferSize = 256`) — [Console.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/Console.cs) (`CreateOutputWriter`).
- Unix encoding comes from the locale charset (`EncodingHelper.GetEncodingFromCharset()`), defaulting to `Encoding.Default` (UTF-8); `SetConsoleInputEncoding/SetConsoleOutputEncoding` are no-ops with the comment "There is no good way to set the terminal console encoding" — [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs) (lines ~703–745). Setting `Console.OutputEncoding` recreates `s_out` with the new encoding after flushing — [Console.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/Console.cs) (lines ~130–152).

**Signals: CancelKeyPress, PosixSignalRegistration, SIGWINCH/SIGTSTP/SIGCONT/SIGCHLD**
- `Console.CancelKeyPress` is implemented with `PosixSignalRegistration.Create(PosixSignal.SIGINT, …)` and `SIGQUIT`; the handler maps `ctx.Cancel` ↔ `ConsoleCancelEventArgs.Cancel` — [Console.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/Console.cs) (`CancelKeyPress`, `HandlePosixSignal`).
- Native signal flow: the signal handler writes the signal number to a pipe; a thread named ".NET SigHandler" dispatches; for SIGINT/SIGQUIT/SIGTERM the managed side runs handlers on a *new dedicated thread* ".NET Signal Handler" "in case the ThreadPool is saturated", while **all other signals (SIGWINCH, SIGCHLD, SIGCONT, SIGTSTP…) are dispatched with `ThreadPool.UnsafeQueueUserWorkItem`** — [PosixSignalRegistration.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Runtime/InteropServices/PosixSignalRegistration.Unix.cs) (`OnPosixSignal`). If no handler sets `Cancel`, `SystemNative_HandleNonCanceledPosixSignal` runs: SIGCONT → `ReinitializeTerminal()` (re-applies `g_currentTermios` and `keypad_xmit` unless a child uses the terminal); SIGTSTP/SIGTTIN/SIGTTOU → "Default disposition is Stop. no-op."; SIGCHLD → deferred console reconfiguration; SIGWINCH → no-op; termination signals → restore original handler, `UninitializeTerminal()` (termios restore), `kill(g_pid, sig)` — [pal_signal.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_signal.c), [pal_console.c `ReinitializeTerminal`](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_console.c).
- Handlers installed by default: SIGINT, SIGQUIT and SIGCONT in `InitializeSignalHandlingCore`; SIGCHLD (with `SA_NOCLDSTOP`) and SIGWINCH via the terminal-invalidation registration; other signals only when a `PosixSignalRegistration` exists; ignored signals are respected (not replaced) — [pal_signal.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_signal.c) (`InstallSignalHandler`, `SetTerminalInvalidationHandler`).
- `PosixSignal` enum (values −1…−11): SIGHUP, SIGINT, SIGQUIT, SIGTERM, SIGCHLD, SIGCONT, SIGWINCH, SIGTTIN, SIGTTOU, SIGTSTP, SIGKILL; applies to .NET 6–11 — [PosixSignal enum docs](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.posixsignal), [PosixSignal.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Runtime/InteropServices/PosixSignal.cs). Raw platform numbers are accepted: `SystemNative_GetPlatformSignalNumber` returns `signal` itself when `signal > 0 && signal <= GetSignalMax()` (so `(PosixSignal)10` registers SIGUSR1 on Linux) — [pal_signal.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_signal.c). The managed side throws `PlatformNotSupportedException` when the number maps to 0 — [PosixSignalRegistration.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Runtime/InteropServices/PosixSignalRegistration.Unix.cs).
- Windows mapping: SIGINT→`CTRL_C_EVENT`, SIGQUIT→`CTRL_BREAK_EVENT`, SIGTERM→`CTRL_SHUTDOWN_EVENT`, SIGHUP→`CTRL_CLOSE_EVENT`, anything else → `PlatformNotSupportedException`; handlers run inside the `SetConsoleCtrlHandler` routine and return TRUE (handled) when `Cancel` is set — [PosixSignalRegistration.Windows.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Private.CoreLib/src/System/Runtime/InteropServices/PosixSignalRegistration.Windows.cs).

**Child processes and the tty (Unix)**
- `SystemNative_ConfigureTerminalForChildProcess(childUsesTerminal)`: if the app is in a read it assumes the child will not use the terminal; otherwise, when the process had changed settings, it re-applies the *initial* termios flags for the child (`forChild` keeps ECHO/ICANON; only ISIG/VMIN/VTIME are set) and, when the last child exits, re-applies .NET's settings and rewrites `keypad_xmit`; `tcsetattr` while in the background is handled by temporarily installing a SIGTTOU handler so the process is not stopped — [pal_console.c](https://github.com/dotnet/runtime/blob/main/src/native/libs/System.Native/pal_console.c) (`ConfigureTerminalForChildProcess`, `TcSetAttr`). The native comment says "The Process, Console and PosixSignalRegistration classes call this method for initialization" (same file). Starting children through anything other than `System.Diagnostics.Process` bypasses this hand-off.

### Inferences
- A custom .NET renderer should bypass `System.Console` for I/O: write frames in one `write(2)` through `Console.OpenStandardOutput()` (a raw stream, not the 256-byte auto-flush `Console.Out`), read bytes from `Console.OpenStandardInput()` or a P/Invoked `read()` on fd 0, and set termios itself (`tcgetattr/tcsetattr` P/Invoke, as Terminal.Gui's `UnixRawModeHelper` does). Do this *before* anything touches `Console.In/ReadKey/KeyAvailable/GetCursorPosition`, and never call those afterwards: .NET re-applies its own termios on every read and on SIGCONT, and the two owners would fight. .NET's SIGCONT handler re-applies "its" last termios; if the app owns raw mode it must also register SIGCONT (and SIGTSTP) and re-enter raw mode itself.
- Registering `PosixSignal.SIGTSTP` without stopping the process yourself effectively disables Ctrl-Z (the runtime's non-cancelled path is a no-op for stop signals); the correct pattern is: restore the terminal in the handler, `kill(getpid(), SIGSTOP)` (there is `SystemNative_GetPlatformSIGSTOP` but no public API), then restore raw mode on SIGCONT. Without a SIGTSTP handler, Ctrl-Z stops the process in raw mode and the shell gets a broken tty until `fg` (when SIGCONT re-applies the app's mode) — exactly the class of bug users will report.
- Because SIGWINCH is delivered via the thread pool, a saturated pool (e.g., ONNX work queued on it or many blocked tasks) delays resize handling; keep heavy work off the pool or treat resize as a lazy "re-measure on next frame" (poll `TIOCGWINSZ` per frame — it is cheap and cached by .NET) rather than depending on signal timing.
- `Console.Out` with `AutoFlush = true` and `TextWriter.Synchronized` makes many small writes cost a syscall and a lock each; Spectre.Console writes through it, which is one reason Live rendering is syscall-heavy.
- On Windows, the pragmatic choice is: enable `ENABLE_VIRTUAL_TERMINAL_PROCESSING | DISABLE_NEWLINE_AUTO_RETURN` on stdout at startup (works in conhost ≥ Win10 and is already on under ConPTY), and either (a) enable `ENABLE_VIRTUAL_TERMINAL_INPUT` and decode VT/Kitty sequences yourself (what Terminal.Gui's ansi driver and termina do; resize then needs polling because `WINDOW_BUFFER_SIZE_EVENT` is only delivered to `ReadConsoleInput`), or (b) keep `ReadConsoleInputW` records (what Terminal.Gui's windows driver and crossterm do). Set the output code page to 65001 (or switch to UTF-16 + `WriteConsoleW`) and restore the previous code page on exit, since .NET will not.
- Process-level crash safety: because `atexit` does not run on SIGKILL/SIGSEGV/abort, any raw-mode TUI (library or custom) should keep a `stty`-equivalent recovery path (document `reset`, and restore in a `finally` plus `UnhandledException`/`ProcessExit`).

- No dotnet/runtime issue specifically about "terminal left in raw mode after crash/Ctrl-Z" was fetched; the behaviour above is derived from the runtime source.
- `PosixSignalRegistration` docs remarks (default-action text per signal) could not be extracted from learn.microsoft.com (the page returned only the member table); the native source was used instead.

## Key question 3 — Startup and latency engineering for a self-contained single-file .NET 10 app

### Takeaway
On this box a self-contained single-file .NET 10 hello world starts in ~26 ms median whether or not the app is ReadyToRun-compiled (the framework in the runtime pack is already R2R; forcing `DOTNET_ReadyToRun=0` raises it to ~74 ms), but for an app that pulls in a library the size of Spectre.Console, R2R-compiling the app halves startup (141 → 70 ms median) and trimming shaves a further ~10 ms (61 ms) while cutting 75 → 22 MB; the one option that hurts badly is `EnableCompressionInSingleFile` (~250 ms vs ~29 ms), `PublishReadyToRunComposite` had no observable effect, and bundling ONNX Runtime's native library with `IncludeNativeLibrariesForSelfExtract` costs ~20 ms once (50 ms first run, 29 MB written under `$HOME/.net`) versus zero when the `.so` ships beside the executable. For latency, the GC defaults (workstation, background GC, `Interactive` latency mode) are already the UI defaults; `GCSettings.LatencyMode = SustainedLowLatency` and a dedicated render thread outside the thread pool are the available levers, while `Thread.Priority` does nothing under Linux `SCHED_OTHER` (nice can only be lowered, raising needs `CAP_SYS_NICE`/`RLIMIT_RTPRIO`/`chrt`), so responsiveness under ONNX CPU saturation has to come from capping the model's intra-op threads and lowering their nice value, not from boosting the UI thread.

- janvorli (runtime maintainer), closing #60114 "Thread.Priority ignored on Linux?" (2021-10-12): "Default Linux thread scheduling policy doesn't allow setting priority, so setting priority in .NET has no effect"; changing it requires `CAP_SYS_NICE`/root or `RLIMIT_RTPRIO` and running under `chrt` (SCHED_RR) — [dotnet/runtime#60114](https://github.com/dotnet/runtime/issues/60114). #91165 "Should Thread.Priority set nice on Linux?" (opened 2023-08-27, open, milestone Future): reporter notes `SCHED_OTHER` ignores `sched_priority`; janvorli considered nice for GC threads; a 2026-08-07 comment notes unprivileged processes can only lower priority with nice — [dotnet/runtime#91165](https://github.com/dotnet/runtime/issues/91165).
- PAL: `InternalSetThreadPriority` maps the Win32 priority onto `pthread_setschedparam` within `sched_get_priority_min/max` of the thread's current policy; `PAL_IGNORE_NORMAL_THREAD_PRIORITY` is defined as 0 in `config.h.in`; with `SCHED_OTHER` the usable range is [0,0] on Linux — [coreclr pal thread.cpp](https://github.com/dotnet/runtime/blob/main/src/coreclr/pal/src/thread/thread.cpp), [pal config.h.in](https://github.com/dotnet/runtime/blob/main/src/coreclr/pal/src/config.h.in).
- Linux `setpriority(2)`/nice: lowering nice (raising priority) requires `CAP_SYS_NICE` ("EACCES: The caller attempted to set a lower nice value… but did not have the required privilege") and since 2.6.12 an `RLIMIT_NICE` soft limit permits it; on Linux the nice value is per-thread — [getpriority/setpriority(2) man page](https://man.archlinux.org/man/getpriority.2.en.txt) (per-thread note is in the BUGS section of the man page, not re-fetched).

**Comparison points measured here**
- ratatui 0.30.2 + crossterm 0.29.0 "draw one frame to stdout" release binary (strip+lto+codegen-units=1): 464,704 bytes; start 3/3/3 ms (build 29 s). Bun 1.4.2 `bun build --compile` hello: 81,315,296 bytes, 5/6/6 ms; same with `import { TextRenderable } from "@opentui/core"` (0.6.6): 98,313,696 bytes, 76/81/82 ms. (Same methodology/log as above.)

**Measuring input-to-paint latency**
- Typometer measures "the delay between an input event and the matching screen update, mainly keystroke to character appearance", cross-platform, Java 8+ — [frarees/typometer](https://github.com/frarees/typometer). kitty's performance page: latency is measured "either with dedicated hardware, or software such as Typometer"; its low-latency recipe is `input_delay 0`, `repaint_delay 2`, `sync_to_monitor no` (default `input_delay` 3 ms) — [kitty performance](https://sw.kovidgoyal.net/kitty/performance/).
- Third-party startup posts found are inconsistent and not reproducible (e.g., .NET 8 hello world "<5 ms AOT vs ~110 ms JIT" on one blog; a .NET 11 web "first request" 118/84/37 ms JIT/R2R/AOT on another; a .NET 10 study finding R2R-vs-JIT process start within 3 % noise) — [peterfrench.dev](https://peterfrench.dev/2025/04/04/harnessing-native-aot-in-net-8-faster-smaller-sharper/), [startdebugging.net](https://startdebugging.net/2026/05/native-aot-vs-readytorun-vs-jit-in-dotnet-11/), [dev.to/lzocate-li](https://dev.to/lzocate-li/net-native-aot-parte-2-jit-r2r-e-aot-em-benchmarks-367i). An older Microsoft number: a self-contained WPF sample's startup fell from 1.9 s to 1.3 s with R2R on .NET Core 3.0 preview 6 (2019) — [.NET Core 3.0 Preview 6 announcement](https://devblogs.microsoft.com/dotnet/announcing-net-core-3-0-preview-6/).

### Inferences
- The runtime floor for a self-contained single-file .NET 10 process on Linux is ~25 ms here (ratatui ~3 ms, Bun ~6 ms); what Corvid controls is everything after `Main`: assembly count, static initialisers, JIT of app/library code (R2R-compile the app and its TUI/JSON/ONNX-binding assemblies), ONNX model loading (should be async and must not gate the first paint), and never enabling single-file compression.
- For Corvid's ONNX Runtime native library, `IncludeNativeLibrariesForSelfExtract` means a first-run extraction of the `.so` into `$HOME/.net/<hash>` (and failure under systemd/no-HOME); the alternative is shipping the `.so` beside the executable (not strictly single-file) — the second benchmark quantifies the extraction cost.
- Render responsiveness under CPU saturation: run the UI loop on a dedicated `new Thread` (never a pool task, since both SIGWINCH dispatch and any `Task`-based input pump compete with saturated pool threads), cap ONNX intra-op threads below `nproc` so at least one core is usually free, and lower the model threads' nice value from inside those threads (allowed without privilege) rather than trying to raise the UI thread's priority (not allowed). `SustainedLowLatency` removes blocking gen-2 pauses during a turn at the cost of heap growth; `ConserveMemory` works against latency and should stay 0.
- Measure input-to-paint inside the app with a monotonic timestamp taken when `read()` returns a key and again after the frame's `write()` completes, and externally with Typometer against the real terminal; the gap between the two is terminal-emulator latency (kitty/Alacritty/WezTerm/Windows Terminal differ by tens of ms).

### Gaps
- No published, reproducible measurement of single-file startup for a *real* .NET console app (Spectre/Terminal.Gui sized) was found; the only data point is the Spectre.Console measurement above (Terminal.Gui could not be timed without a pty).
- Composite R2R produced byte-identical output to plain R2R even from a clean build, so its effect (if any) in a single-file self-contained publish is unknown; DATAS/region settings were not measured; macOS and Windows startup were not measured (Linux container only); the extraction cost was measured on this container's disk and will be larger on slow or network home directories.
- Whether `TieredPGO` is on by default in .NET 10 is not stated on the fetched docs page (it only says the setting "enables dynamic PGO in .NET 6 and later").

## Key question 4 — The ACP alternative (Agent Client Protocol): what a client gets, what a first-party TUI would lack, existing terminal clients, two-process costs

### Takeaway
ACP v1 (JSON-RPC 2.0 over newline-delimited stdio; the client spawns the agent) now covers nearly everything a chat TUI needs — streamed message/thought chunks, typed tool calls with status/diff/terminal content and file locations, permission requests with allow/reject-once/always options, plans, slash commands, modes and (preferred) session config options with a `model` category, session list/resume/close/delete, usage (context tokens/cost), notices, compaction and elicitation — but it deliberately puts terminals and file I/O on the *client* side, has stdio as its only stable transport, and a v2 draft (2026-07-20) that renames/removes many v1 fields; anything Corvid-specific (model load progress, approval-rule editing, engine status) would have to ride on `_meta`/`_corvid/*` extensions. Terminal ACP clients already exist (Toad in Python/Textual, bitrouter-tui and Martty in Rust/ratatui, acpx, pool, Nori, Microsoft's Intelligent Terminal), SDKs exist for Rust (3.4.0), TypeScript (2.0.0), Python, Kotlin, Java and three community C# libraries, so a two-process design is practical; its costs are a second runtime/binary (~0.5 MB Rust vs ~80–100 MB Bun), an extra spawn+handshake on the critical path, version/capability skew management, and debugging through ACP logs instead of a stack trace.

### Cited Findings

**Protocol shape (v1)**
- JSON-RPC 2.0; agents "typically run as subprocesses of the Client"; flow `initialize` → optional `authenticate` → `session/new` or `session/load` → `session/prompt` with `session/update` notifications and a stop reason; requests include `initialize, authenticate, logout, session/new, session/load, session/prompt, session/set_mode, session/request_permission, fs/read_text_file, fs/write_text_file, terminal/create|output|release|wait_for_exit|kill, elicitation/create`; notifications `session/cancel, session/update, elicitation/complete`; extensibility via `_meta` fields, methods prefixed with `_`, and custom capabilities at initialisation — [Protocol overview](https://agentclientprotocol.com/protocol/overview).
- Initialisation: `protocolVersion` is an integer (`1`), the client sends the latest it supports, the agent answers with the same or its latest; "If the Client does not support the version the Agent returns, the Client SHOULD close the connection"; client capabilities `fs.readTextFile`, `fs.writeTextFile`, `terminal`, `elicitation` (object with `form`/`url`), `auth.terminal`, `session.configOptions.boolean`, `session.compaction`, `session.notices`; agent capabilities `loadSession`, `promptCapabilities {image, audio, embeddedContext}`, `mcpCapabilities {http, sse}`, `auth`, `logout`, session `delete`/`additionalDirectories`; `clientInfo`/`agentInfo {name,title,version}` — [Initialization](https://agentclientprotocol.com/protocol/v1/initialization.md).
- Sessions: `session/new {cwd, mcpServers}` → `sessionId`; `session/load` replays history as `session/update`s; `session/resume` (capability `sessionCapabilities.resume`) does not replay and "MAY" return initial mode/model/config state; `session/close` (`sessionCapabilities.close`); `additionalDirectories` — [Session Setup](https://agentclientprotocol.com/protocol/v1/session-setup.md). `session/list {cwd?, cursor?}` → `sessions[{sessionId, cwd, title?, updatedAt?}]`, `nextCursor` (capability `sessionCapabilities.list`); `session_info_update {title?, updatedAt?}` — [Session List](https://agentclientprotocol.com/protocol/v1/session-list.md). Session Delete is a stabilised page in the index — [llms.txt index](https://agentclientprotocol.com/llms.txt).
- Prompt turn: `session/prompt {sessionId, prompt: ContentBlock[]}`; `session/update` variants: `user_message_chunk`, `agent_message_chunk` (optional `messageId`), `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan` (entries with `content`, `priority`, `status`), `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update {used, size, cost?{amount,currency}}`, `notice {severity: info|warning|error|_ext, title, description?}` (needs `session.notices`), `compaction_update {compactionId, status: in_progress|completed|failed|cancelled, summary?}` and `compaction_summary_chunk` (need `session.compaction`); stop reasons `end_turn, max_tokens, max_turn_requests, refusal, cancelled`; on `session/cancel` the client MUST answer pending permission requests with `cancelled` and the agent MUST return `cancelled` rather than an error — [Prompt Turn](https://agentclientprotocol.com/protocol/v1/prompt-turn.md).
- Tool calls: fields `toolCallId, title, name?, kind, status, content, locations[{path, line?}], rawInput, rawOutput`; kinds `read, edit, delete, move, search, execute, think, fetch, switch_mode, other`; statuses `pending, in_progress, completed, failed`; content types `content` (any content block), `diff {path, oldText|null, newText}`, `terminal {terminalId}`; `tool_call_update` carries only changed fields; `session/request_permission {sessionId, toolCall, options[{optionId, name, kind: allow_once|allow_always|reject_once|reject_always}]}` with outcome `selected {optionId}` or `cancelled` — [Tool Calls](https://agentclientprotocol.com/protocol/v1/tool-calls.md).
- Modes: `modes {currentModeId, availableModes[{id,name,description?}]}` on session setup, `session/set_mode {sessionId, modeId}`, `current_mode_update`; the page says dedicated mode methods "will be removed in a future protocol version" in favour of config options — [Session Modes](https://agentclientprotocol.com/protocol/v1/session-modes.md).
- Session config options (the "preferred way to expose session-level configuration", e.g. models, modes, reasoning): `configOptions[{id, name, description?, category?: mode|model|model_config|thought_level|_custom, type: select|boolean, currentValue, options: values|groups}]`; `session/set_config_option {sessionId, configId, value}` returns the full list; `config_option_update` carries the full list (used for model fallbacks); `boolean` needs `clientCapabilities.session.configOptions.boolean` — [Session Config Options](https://agentclientprotocol.com/protocol/v1/session-config-options.md). "Model Config Category stabilized" is an announcement in the index — [llms.txt](https://agentclientprotocol.com/llms.txt).
- Slash commands: `available_commands_update {availableCommands[{name, description, input?{hint}}]}`; the client runs one by sending `/name args` as a text block in `session/prompt` — [Slash Commands](https://agentclientprotocol.com/protocol/v1/slash-commands.md).
- Terminals are executed by the **client**: `terminal/create {sessionId, command, args?, env?[{name,value}], cwd?, outputByteLimit?}` → `terminalId` immediately; `terminal/output → {output, truncated, exitStatus?{exitCode?, signal?}}`; `terminal/wait_for_exit`; `terminal/kill`; `terminal/release`; a tool call may embed `{type: "terminal", terminalId}` and the client keeps showing output after release — [Terminals](https://agentclientprotocol.com/protocol/v1/terminals.md).
- Transport: stdio — client launches the agent as a subprocess; messages newline-delimited, UTF-8, no embedded newlines; the agent "MAY write UTF-8 strings to its standard error (stderr) for logging"; stdout/stdin must carry only ACP; Streamable HTTP is "In discussion, draft proposal in progress"; custom transports allowed — [Transports](https://agentclientprotocol.com/protocol/v1/transports.md).
- Draft v2 (announced 2026-07-20; "still labeled draft"; "v1-only peers will remain common for some time"; "Do not ship v2 by default in production"): `protocolVersion: 2`; `session/prompt` returns `messageId` and the stop reason moves to an idle `state_update`; `authenticate`→`auth/login`; `session/load` and `session/set_mode` removed (use `session/resume {replayFrom}` and `session/set_config_option`); `fs/*` and `terminal/*` client methods removed, terminal becomes display-only via `terminal_update`/`terminal_output_chunk`; `tool_call` removed (first `tool_call_update` creates it, status gains `cancelled`); diffs become `changes[]` + optional `git_patch`; permission requests gain `title/description/subject`; capability markers become objects; `clientCapabilities`→`capabilities`, `clientInfo`→`info` (required) — [v2 migration](https://agentclientprotocol.com/protocol/v2/migration.md), [v2 draft announcement](https://agentclientprotocol.com/announcements/acp-v2-draft.md).
- Open RFDs relevant to a first-party TUI: session fork, subagent sessions, plan operations, end-turn token usage, configurable LLM providers, client-provided system prompt, Streamable HTTP/WebSocket, MCP-over-ACP, agent extensions via ACP proxies — [llms.txt index](https://agentclientprotocol.com/llms.txt).

**Hosting and tooling**
- Zed hosts external agents as separate processes configured in `agent_servers` (`type: "custom"`, `command`, `args`, `env`), installs agents from the ACP Registry, and exposes `dev: open acp logs` "to inspect messages between Zed and an External Agent"; model/provider config is "Usually owned by the External Agent" — [Zed external agents docs](https://zed.dev/docs/ai/external-agents). Zed's announcement (2025-08-27; Claude Code beta added 2025-09-03): agents run as subprocesses behind "a minimal set of JSON-RPC endpoints"; Zed's built-in agent uses the same code paths — [Bring your own agent to Zed](https://zed.dev/blog/bring-your-own-agent-to-zed).
- ACP Registry: curated agents list published at `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json` with "distribution information for automatic installation"; submission = `agent.json` + optional icon via PR — [Registry](https://agentclientprotocol.com/get-started/registry.md).
- SDKs: Rust crate `agent-client-protocol` 3.4.0 (2026-10-16, Apache-2.0; 3.0.0 on 2026-10-06, 2.0.0 on 2026-07-23), "runtime-neutral", features `stdio`, `process` (spawn an agent), `schemars`, `unstable_protocol_v2`, `unstable_session_fork` — [crates.io](https://crates.io/api/v1/crates/agent-client-protocol), [docs.rs](https://docs.rs/agent-client-protocol/latest/agent_client_protocol/); TypeScript `@agentclientprotocol/sdk` 2.0.0 (2026-10-19, Apache-2.0) — [npm](https://registry.npmjs.org/@agentclientprotocol/sdk); Python `agent-client-protocol` 0.12.1 — [PyPI](https://pypi.org/pypi/agent-client-protocol/json); Kotlin and Java pages exist in the official index — [llms.txt](https://agentclientprotocol.com/llms.txt); community: C# `acp-csharp` (NuGet `AgentClientProtocol` 0.1.5, 2025-11-05, MIT, unofficial), `Acp.Net`, `Agentic.ACPLibrary`; Go (7 libraries), Swift (3), Dart, Ruby, Elixir, C++, Crystal, Vala — [Community libraries](https://agentclientprotocol.com/libraries/community.md), [acp-csharp README](https://github.com/nuskey8/acp-csharp), [NuGet AgentClientProtocol](https://api.nuget.org/v3/registration5-gz-semver2/agentclientprotocol/index.json). Claude Code adapter `@agentclientprotocol/claude-agent-acp` 0.94.0 (2026-10-19, Apache-2.0) succeeded `@zed-industries/claude-code-acp` 0.16.2 (2026-02-17) — [npm](https://registry.npmjs.org/@agentclientprotocol/claude-agent-acp), [npm](https://registry.npmjs.org/@zed-industries/claude-code-acp).
- Terminal/TUI clients listed officially: acpx, Hash, Hydra, Martty ("extensible Rust/ratatui terminal client"), Nori CLI, pool, Raven, Toad, Intelligent Terminal ("Windows Terminal fork with native agent integration"), plus Emacs `agent-shell` and four Neovim plugins; also a protocol debugger "ACP Inspector" and an "AcpAgent Client" with a traffic inspector — [Clients](https://agentclientprotocol.com/overview/clients.md).

- A precedent for a first-party TUI over ACP with vendor extensions: Kiro CLI's TUI frontend talks to its Rust backend over stdin/stdout ACP and adds `_kiro.dev/`-prefixed extension methods for UI-specific events such as slash commands and context usage — [Kiro CLI ACP doc](https://kiro-cli.mengtge.people.aws.dev/03_acp/) (search snippet only; page not fetched, source authority unverified).

### Inferences
- What Corvid's ACP surface would need *beyond* v1 for a first-party TUI: (1) engine status that is not a session event (model load/warm-up progress, CPU saturation, local-model name/quantisation) — no v1 update type fits except `notice` or `_meta` on `session_info_update`; (2) approval *rule* management (list/edit "always allow" rules) — v1 only has per-request `allow_always`; (3) anything about the in-process models beyond "model" selection (config option category `model` works for switching). All are expressible as `_corvid/*` methods/notifications or `_meta`, which is the sanctioned path, but then only Corvid's own TUI understands them.
- The terminal/file-system inversion matters: in v1 the *client* executes `terminal/*` and `fs/*` on the agent's behalf; a Corvid TUI process would have to implement command execution and file reads, or Corvid's agent would keep running tools itself and not call those client methods (allowed — they are capabilities). v2 removes the client-side execution surface again, so designing around "agent runs tools, client only displays" is the forward-compatible choice.
- Version skew is manageable but real: a v1-only TUI keeps working against a v2 agent only if the agent keeps serving v1 (the announcement asks implementers to do so); pin the pair by shipping both binaries together and still negotiate `protocolVersion`/capabilities at startup.
- Critical path for a two-process design: TUI process start (ratatui ~3 ms, Bun+OpenTUI ~80 ms here) + spawn of the .NET agent (~25 ms runtime floor + Corvid init) + `initialize`/`session/new` round trips, all serial unless the TUI paints a shell first; the agent's stderr is the only sanctioned log channel, so a `--acp-log` tee and a log viewer (as Zed's "open acp logs") are needed for debugging.

### Gaps
- No quantitative data on ACP message overhead (chunk sizes, JSON-RPC parse cost) or on end-to-end latency of streaming through stdio was found.
- Kiro's doc was only seen as a search snippet; Toad's Windows support statement comes from a third-party listing.
- Whether Corvid's current ACP implementation already exposes `session/list`, config options or usage updates was not checked here (out of scope for this researcher).

## Key question 5 — Native options if the TUI is a separate process: ratatui (Rust) and OpenTUI (Zig + TypeScript)

### Takeaway
ratatui 0.30.2 (MIT) over crossterm 0.29 gives a ~0.5 MB stripped binary starting in ~3 ms here, an immediate-mode double-buffer diff renderer, an `Inline` viewport with `insert_before` for scrollback-style UIs, Windows support through crossterm's `ReadConsoleInputW` path (or termina's VT/Kitty path on Windows ≥ 10.0.17763), and its own ANSI/Kitty input parser; OpenTUI 0.6.6 (MIT) is a Zig diff renderer (with synchronized output and Ghostty's VT for embedded terminals) driven from TypeScript on Bun ≥ 1.3.14 or Node ≥ 26.4.0, shipping prebuilt binaries for win32/linux(+musl)/darwin on x64 and arm64, used in production by OpenCode, but a Bun-compiled executable is ~80–100 MB and the OpenTUI import alone costs ~75 ms of startup here.

- OpenTUI input/output internals: own TypeScript parsers `parse.keypress.ts` (Kitty keyboard protocol via `parse.keypress-kitty.ts`, `modifyOtherKeys` `ESC[27;m;c~`, bracketed paste markers), `parse.mouse.ts`, `stdin-parser.ts` with a conformance JSON; Zig core emits synchronized output (`syncSet = "\x1b[?2026h"`, `syncReset`, `DECRQM ?2026$p` probe, tmux passthrough), `renderer.zig` tracks dirty/changed regions ("everything outside placements diffs normally", hit-grid double buffering), `ghostty-vt.zig` imports Ghostty's VT library, `grapheme.zig` packs grapheme/wide-cell flags — [packages/core/src/lib](https://github.com/anomalyco/opentui/tree/main/packages/core/src/lib), [packages/native/src/ansi.zig](https://github.com/anomalyco/opentui/blob/main/packages/native/src/ansi.zig), [renderer.zig](https://github.com/anomalyco/opentui/blob/main/packages/native/src/renderer.zig). ### Inferences
- For "Linux first, then Windows and macOS", ratatui+crossterm is the lowest-risk native TUI: one static binary per RID (~1–3 MB with real widgets), ~ms startup, Windows via console records today with an upgrade path to VT/Kitty via termina; its `Inline` viewport + `insert_before` matches Corvid's scrollback-first layout. OpenTUI buys a React/Solid programming model and a battle-tested Zig renderer (OpenCode) at the price of a 80–100 MB executable, ~75 ms import cost and a Bun/Node 26 runtime dependency.
- Either native client would need an ACP client library (Rust SDK 3.x; TypeScript SDK 2.x) and Corvid's `_corvid/*` extensions; packaging means two artefacts per platform plus a launcher, or a single Corvid binary that spawns the TUI (reversing the usual "client spawns agent" direction is allowed by the stdio transport as long as the TUI owns the agent's stdin/stdout).

### Gaps
- No published ratatui binary-size/startup numbers; the ~0.5 MB / 3 ms figures are this container's hello world, not a full app with widgets, and were measured without a pty (fixed viewport, raw mode not enabled).
- OpenTUI's startup on Node 26 (vs Bun) and its Windows input behaviour (VT input vs console records) were not verified from source in this session.
