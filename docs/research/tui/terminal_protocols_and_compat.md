# Terminal protocols and compatibility facts for a cross-platform TUI (state as of October 2026)

Scope note: this file covers the escape-sequence features a terminal UI must get right, their exact byte sequences, how to detect them without hanging or corrupting the terminal, a support matrix across terminals and multiplexers, Windows/ConPTY specifics, resize/reflow behaviour, SSH/mosh latency, and string-width measurement. Every claim carries a source link. Where a claim could not be sourced it is listed under Gaps rather than asserted.

Notation: `ESC` = 0x1b, `CSI` = `ESC [`, `OSC` = `ESC ]`, `DCS` = `ESC P`, `APC` = `ESC _`, `ST` = `ESC \` (BEL 0x07 is accepted as an OSC terminator by most terminals but ST is the standard form). Spaces inside sequences are illustrative only.

---

## Key question 1: Features and their exact sequences, detection methods and hazards

### Takeaway
Every feature below has a mode-set sequence and, for the modern ones, a query (DECRQM `CSI ? Pd $ p`, kitty `CSI ? u`, graphics `APC G ... a=q`, OSC 99 `p=?`, XTGETTCAP, XTVERSION, DA1/DA2). The one universally safe detection pattern, used by kitty's protocols, notcurses and Claude Code alike, is to batch the queries and end the batch with a DA1 (`CSI c`): "all known terminals respond to it with something", so a DA1 reply without a feature reply means "not supported", and a wall-clock timeout covers terminals that answer nothing at all.

### Cited Findings

#### Synchronized output, DEC private mode 2026
- Begin a frame with `CSI ? 2026 h` (BSU) and end it with `CSI ? 2026 l` (ESU); "When the synchronization mode is enabled following render calls will keep rendering the last rendered state", while the emulator keeps processing incoming text — [contour-terminal/vt-extensions synchronized-output.md](https://github.com/contour-terminal/vt-extensions/blob/master/synchronized-output.md); original gist: [Christian Parpart's gist](https://gist.github.com/christianparpart/d8a62cc1ab659194337d73e399004036)
- Detection: send DECRQM `CSI ? 2026 $ p`; the reply is DECRPM `CSI ? 2026 ; Ps $ y` where Ps = 0 not recognised (unsupported), 1 set, 2 reset (supported), 3 "undefined for this feature", 4 permanently reset (unsupported); "If you get back a `CSI ? 2026 ; 0 $ y` then synchronized output is not supported"; no reply at all means DECRQM itself is unimplemented — [vt-extensions](https://github.com/contour-terminal/vt-extensions/blob/master/synchronized-output.md); [gist](https://gist.github.com/christianparpart/d8a62cc1ab659194337d73e399004036)
- Timeouts: "So far there is no real concensus if and if so how long a timeout should be"; "a too short timeout (maybe due to a very slow connection) won't be worse than having no synchronized output at all" — [vt-extensions](https://github.com/contour-terminal/vt-extensions/blob/master/synchronized-output.md)
- The spec is based on iTerm2's older DCS form `ESC P = 1 s ESC \` (begin) / `ESC P = 2 s ESC \` (end); foot still accepts both — [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en); Alacritty's current docs say "CSI ? 2026 h/l are used instead" of the DCS form — [Alacritty escape_support.md v0.15.1](https://github.com/alacritty/alacritty/blob/v0.15.1/docs/escape_support.md)
- A gist commenter reported GNOME Terminal answering DECRPM with 4 (permanently reset), which the author considered acceptable but "semantically a little misleading" — [gist](https://gist.github.com/christianparpart/d8a62cc1ab659194337d73e399004036); the current vt-extensions table lists VTE/gnome-terminal as Supported (GNOME VTE issue #15) — [vt-extensions](https://github.com/contour-terminal/vt-extensions/blob/master/synchronized-output.md)
- Zellij "handle[s] DECRPM 2026 state 3" since 0.44.2, i.e. real terminals do emit the "undefined" value 3 — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)
- tmux 3.7 (released 26 Jun 2026) "adds DECSET 2026 synchronized output support, and responds to DECRQM 2026"; the merged implementation defers flushing pane output until `ESC[?2026l` arrives or a 1-second timeout expires, "Redraw cancels sync mode rather than blocking", sync is cleared on resize, and a `synchronized_output_flag` format variable was added — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES); [tmux PR #4744 (merged 17 Dec 2025)](https://github.com/tmux/tmux/pull/4744); [tmux releases](https://github.com/tmux/tmux/releases)
- Before 3.7, tmux only used synchronized updates *outbound* (towards the outer terminal, via the `sync` terminal feature, added as "the iTerm2 synchronized updates feature" in 3.2); an application's own `CSI ? 2026 h` inside tmux 3.4 was not honoured, which is why Claude Code flickered in tmux panes — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES); [anthropics/claude-code #37283](https://github.com/anthropics/claude-code/issues/37283)

#### The kitty keyboard protocol (progressive enhancement)
- Flags: 1 "Disambiguate escape codes", 2 "Report event types", 4 "Report alternate keys", 8 "Report all keys as escape codes", 16 "Report associated text" — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- Sequences: push `CSI > flags u`, pop `CSI < number u` (default 1), set `CSI = flags ; mode u` (mode 1 set listed/reset rest, 2 set only listed, 3 reset only listed), query `CSI ? u` with reply `CSI ? flags u`; the main and alternate screens keep separate stacks; popping an empty stack resets all flags; "Send `CSI > 1 u` at startup and `CSI < u` at exit" — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- Detection: "Send the progressive enhancement query (`CSI ? u`) followed by a primary device attributes request (DA1). If a DA1 reply arrives without a progressive enhancement reply, the terminal does not support the protocol"; set the desired flags first and then query to detect partial implementations — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- Key event form: `CSI unicode-key-code:alternates ; modifiers:event-type ; text u`; event type 1 press (default), 2 repeat, 3 release; modifiers are encoded as 1 + (shift=1, alt=2, ctrl=4, super=8, ...); with only flag 1 set, Enter/Tab/Backspace keep their legacy bytes (0x0d, 0x09, 0x7f) so a crashed program's terminal can still run `reset`; Enter only becomes `CSI 13 u` with flag 8 (report all keys), and Enter/Tab/Backspace report no release events unless flag 8 is also set — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- Shift+Enter / Ctrl+Enter: the spec gives no literal example; applying its modifier rules (shift = 1+1 = 2, ctrl = 1+4 = 5) yields `CSI 13;2u` and `CSI 13;5u` (derivation from the spec's rules, not a quoted example) — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- Terminals the spec lists as implementing it: AbsoluteTelnet, alacritty, foot, ghostty, iTerm2, "Microsoft terminal", rio, TuiOS (multiplexer), Warp, WezTerm, xterm.js; libraries: notcurses, crossterm, textual, vaxis, bubbletea, tcell; shells fish and nushell — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- Hazard: a program that pushes flags and crashes leaves the terminal in enhanced mode; Claude Code users reported "[BUG] Terminal left in enhanced keyboard mode after exit — Ctrl-C/Ctrl-D broken" — [anthropics/claude-code #38761](https://github.com/anthropics/claude-code/issues/38761)
- Hazard: a terminal that does not implement the protocol may print the sequences; a JediTerm-based JetBrains terminal displayed kitty sequences as stray `<` characters (WebStorm 2025.3.1.1, Jan 2026) — [anthropics/claude-code #18135](https://github.com/anthropics/claude-code/issues/18135); Caps Lock produced stray `[57358u` in a code-server (browser xterm.js) terminal — [anthropics/claude-code #44327](https://github.com/anthropics/claude-code/issues/44327)

#### Legacy key encoding ambiguities (Esc vs Alt, modifyOtherKeys, timeouts)
- Legacy problems per the kitty spec: Esc is byte 0x1b, "the same byte that starts escape codes", so "client programs use fragile timing related hacks"; ctrl+i = Tab, ctrl+m = Enter; "Enter with no modifiers, Ctrl, Shift, and Ctrl+Shift all send 0xd", Alt and Ctrl+Alt send `0x1b 0xd`; Ctrl+Tab = 0x9; Shift+Tab = `CSI Z`; Backspace and ctrl+Backspace are swapped in some terminals; no release or repeat events — [kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/)
- xterm's alternative: XTMODKEYS `CSI > 4 ; Pv m` (modifyOtherKeys) and XTFMTKEYS `CSI > 4 ; Pv f` (formatOtherKeys); with modifyOtherKeys=1, "alt-Tab sends CSI 2 7 ; 3 ; 9 ~"; with formatOtherKeys=1 "alt-Tab sends CSI 9 ; 3 u" — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
- tmux's `extended-keys-format`: "C-S-a will be reported as '^[[27;6;65~' when set to xterm, and as '^[[65;6u' when set to csi-u" — [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html)
- Timeouts: tmux "waits after an escape is input to determine if it is part of a function or meta key sequences" (`escape-time`); tmux 3.5 "reduces the default escape-time to 10 milliseconds"; on a local machine "an escape-time of zero is likely to be fine", slower links need more — [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html); [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES); [tmux FAQ](https://github.com/tmux/tmux/wiki/FAQ)
- mintty offers "application escape key mode" (DECSET 7727) that "switch[es] the escape key to an unambiguous keycode" because Esc timeouts "fail on slow connections or a heavily loaded machine" — [mintty wiki Tips](https://github.com/mintty/mintty/wiki/Tips); tmux 3.2 notes "mintty's application escape mode means escape-time need not be reduced" — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- Windows console VT input encodes Alt by prefixing `ESC`, Ctrl keys as C0 bytes, arrows as `ESC [ A..D` (application mode `ESC O A..D`), Ctrl+arrows as `ESC [ 1 ; 5 A..D`, Backspace as 0x7f, F1–F4 as `ESC O P..S`, F5–F12 as `ESC [ 15~ 17~ 18~ 19~ 20~ 21~ 23~ 24~` — [Console Virtual Terminal Sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- Shift+Enter inside tmux: with the default `extended-keys on`, tmux forwards extended keys only to panes that request them; the user workaround is `extended-keys always` — [anthropics/claude-code #26629](https://github.com/anthropics/claude-code/issues/26629); tmux 3.7 "makes C-[ match Escape for terminals with extended keys" — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)

#### Bracketed paste (mode 2004)
- `CSI ? 2004 h` enables it; pasted text is delimited by `ESC [ 2 0 0 ~` and `ESC [ 2 0 1 ~` — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
- tmux 3.4 "recognises pasted text wrapped in bracket paste sequences"; 3.6 "adds DECRQM ?2004 reporting"; 3.7 adds a `bracket_paste_flag` format, "a five-second paste limit for Terminal.app, and stops guessing at pastes when bracketed paste is supported" — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- Alacritty lists 2004 among supported `CSI ? h` modes; foot documents it as "Wrap pasted text with start/end delimiters" — [Alacritty escape_support.md](https://github.com/alacritty/alacritty/blob/v0.15.1/docs/escape_support.md); [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en)

#### Mouse reporting
- Modes: 1000 X11 press/release, 1002 cell (button-event) motion, 1003 all-motion (any-event), 1005 UTF-8, 1006 SGR; SGR reports begin `CSI <` with semicolon-separated fields and end in `M` for press and `m` for release; motion adds 32 to the event code, wheel events add 64, modifiers add 4 (Shift), 8 (Meta), 16 (Control) — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
- foot additionally supports 1016 "SGR-Pixels mouse mode" — [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en)
- Trade-off with native selection: tmux's FAQ says terminals "offer no fine-grained mouse handling, so the mouse option is all or nothing", and to bypass it the user must hold a terminal-specific key, "such as Shift on many Linux terminals or Option in iTerm2" — [tmux FAQ](https://github.com/tmux/tmux/wiki/FAQ); Ghostty documents XTSHIFTESCAPE `CSI > Pn s`, the xterm control that lets the application decide whether Shift overrides mouse capture — [Ghostty VT reference](https://ghostty.org/docs/vt/reference)
- Zellij only forwards SGR-format mouse events (initial support in 0.26.0), added any-event tracking in 0.42.0, and fixed "mouse handling in windows terminal" in 0.42.1 — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)
- mosh added "support for mouse modes" in 1.2.5 — [mosh.org](https://mosh.org/)

#### Focus events (mode 1004)
- `CSI ? 1004 h`; xterm sends `CSI I` on focus gain and `CSI O` on focus loss — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
- tmux `focus-events on` requests focus events from the outer terminal and passes them to applications; attached clients must detach and reattach after changing it — [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html); zellij sends focus in/out to panes since 0.33.0 and forwards host focus since 0.45.0 — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)

#### OSC 52 clipboard (write and read)
- Form `OSC 52 ; Pc ; Pd ST`; Pc may contain characters from `c p q s 0 1 2 3 4 5 6 7`; if Pd is `?` xterm "replies to the host with the selection data encoded using the same protocol"; these controls "may be disabled using the allowWindowOps resource" — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); xterm has it disabled by default, enable with `XTerm*disallowedWindowOps: 20,21,SetXprop` — [tmux Clipboard wiki](https://github.com/tmux/tmux/wiki/Clipboard)
- Ghostty: `c`, `p`, `s` recognised (other xterm selectors alias `c`), "only allows specifying one clipboard per sequence", `?` query is supported and answered with another OSC 52, a non-Base64 payload clears the clipboard; 1.2.0 "Indicate[s] support for OSC 52 in the primary DA report" and lets an empty string empty the clipboard — [Ghostty OSC 52](https://ghostty.org/docs/vt/osc/52); [Ghostty 1.2.0 notes](https://ghostty.org/docs/install/release-notes/1-2-0)
- foot: write `OSC 52 ; Pc ; base64 ST`; `?` read is supported, response `OSC 52 ; Pc ; <base64> ST` — [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en)
- WezTerm: "Allows setting or clearing the clipboard"; "Requests to query the clipboard are ignored" — [WezTerm escape sequences](https://wezterm.org/escape-sequences.html)
- Alacritty: OSC 52 implemented, "Only Clipboard and primary selection supported" — [Alacritty escape_support.md](https://github.com/alacritty/alacritty/blob/v0.15.1/docs/escape_support.md)
- kitty: supported; known bug that each copy appended, workaround `clipboard_control write-primary write-clipboard no-append` — [tmux Clipboard wiki](https://github.com/tmux/tmux/wiki/Clipboard)
- iTerm2: supported but must be enabled in Preferences — [tmux Clipboard wiki](https://github.com/tmux/tmux/wiki/Clipboard)
- VTE (GNOME Terminal, XFCE Terminal, Terminator): "do not support the OSC 52 escape sequence"; some versions printed the sequence as text — [tmux Clipboard wiki](https://github.com/tmux/tmux/wiki/Clipboard) (undated page; see Gaps)
- Windows Terminal 1.22: "You can now disallow applications from writing to the Windows Clipboard" via `compatibility.allowOSC52` (boolean, default true) — [WT v1.22.10352.0 release](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0)
- mosh 1.4.0 added "OSC 52 clipboard copy integration" — [mosh 1.4.0 release](https://mosh.org/mosh-1.4.0-released.html)
- tmux: `set-clipboard` is `on` (accept OSC 52 from inner apps and set the outer clipboard), `external` (set outer clipboard only; default since 2.6) or `off`; needs the `Ms` terminfo capability, which tmux adds for `xterm*` by default (`set -as terminal-features ',TERM:clipboard'` otherwise); tmux 3.4 passes through the first OSC 52 argument; 3.6 detects OSC 52 support from the device attributes report; 3.7 adds `get-clipboard` (`both | request | buffer | off`) for inner-app read requests and "makes OSC 52 work in popups" — [tmux Clipboard wiki](https://github.com/tmux/tmux/wiki/Clipboard); [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html); [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- Zellij forwards OSC 52 copy events since 0.31.2 and "properly report[s] OSC52 clipboard support" since 0.44.1 — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)

#### OSC 8 hyperlinks
- Form `OSC 8 ; params ; URI ST`, close with `OSC 8 ; ; ST`; only `id=` is defined (cells sharing URI and id highlight together); VTE and iTerm2 cap URIs at 2083 bytes, VTE caps `id` at 250 bytes; bytes outside 32–126 must be URI-encoded; ECMA-48-conformant terminals ignore the OSC and show plain text, while buggy ones (VTE ≤ 0.46.2 / 0.48.1, Windows Terminal ≤ 0.9, Emacs's terminal, GNU screen with 700+ byte URLs) corrupt the display — [OSC 8 gist (egmontkob)](https://gist.github.com/egmontkob/eb114294efbcd5adb1944c9f3cb5feda)
- Adoption: VTE since 0.50 (GNOME Terminal 3.26), iTerm2 3.1, kitty since 0.19, WezTerm since early 2018, Alacritty since 0.11 (2022-10-13), foot 1.7.0, Windows Terminal 1.4.3141.0 (2020-11-12), Konsole since Jul 2020 "disabled by default", mintty 2.9.7, Ghostty since 2024-07-07, Hyper since Oct 2019, xterm.js 5.0.0 / VS Code 1.72, tmux since 3.4 with `set -ga terminal-features "*:hyperlinks"`, zellij 0.21.0, Tilix 1.5.8; GNU screen and ConEmu are "pending feature requests"; Terminal.app, xterm, urxvt, st, Contour, Warp, Rio, JetBrains, mosh, PuTTY are not listed — [OSC8-Adoption](https://github.com/Alhadis/OSC8-Adoption)

#### Notifications: OSC 9, OSC 777, OSC 99 and BEL
- iTerm2's OSC 9: `OSC 9 ; [Message content goes here] ST` — [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html)
- OSC 777 (rxvt-unicode style): `OSC 777 ; notify ; title ; msg ST`; WezTerm: "Only the notify extension is supported; it shows a 'toast' notification"; foot supports OSC 9, OSC 777 and OSC 99 — [WezTerm escape sequences](https://wezterm.org/escape-sequences.html); [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en)
- kitty's OSC 99: `OSC 99 ; metadata ; payload ST`, metadata is colon-separated `key=value`; `i=` id, `d=` done flag (0 = more chunks), `p=` payload type (title default, body, close, icon, `?` query, alive, buttons), `e=1` Base64, `a=` actions (report/focus), `o=` occasion (always/unfocused/invisible), `u=` urgency 0–2; payload max 2048 bytes raw / 4096 encoded; plain payloads may contain no C0/C1 controls; query with `OSC 99 ; i=<id> : p=? ; ST` and "also send a primary device attributes (DA1) request; if the DA1 reply arrives without a reply to the query, the terminal doesn't support the protocol"; kitty also accepts legacy OSC 9 — [kitty desktop notifications](https://sw.kovidgoyal.net/kitty/desktop-notifications/)
- Ghostty 1.2.0: "OSC 9 notifications can contain single character messages"; and "The progress report OSC 9;4 sequence collides with the iTerm2 notification sequence" — [Ghostty 1.2.0 notes](https://ghostty.org/docs/install/release-notes/1-2-0)
- Zellij 0.45.0: "support additional notification protocols (OSC9 + OSC777)" — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)
- BEL (0x07) is documented as a control in Ghostty's reference (`/docs/vt/control/bel`); tmux has `monitor-activity`/`visual-bell` options (ruled out as the cause in the Claude Code tmux flicker report) — [Ghostty VT reference](https://ghostty.org/docs/vt/reference); [claude-code #37283](https://github.com/anthropics/claude-code/issues/37283)

#### OSC 9;4 progress (ConEmu)
- `OSC 9 ; 4 ; st ; pr ST`: st 0 removes progress, 1 sets value pr (0–100), 2 error state (pr optional), 3 indeterminate, 4 paused (pr optional) — [ConEmu ANSI escape codes](https://conemu.github.io/en/AnsiEscapeCodes.html)
- Windows Terminal supports it from v1.6 (tab ring + taskbar; taskbar animation only if "Show animations in Windows" is on) — [WT progress bar tutorial](https://learn.microsoft.com/en-us/windows/terminal/tutorials/progress-bar-sequences)
- Ghostty 1.2.0 (15 Sep 2025) "recognizes the ConEmu OSC 9;4 sequences and renders a GUI native progress bar" — [Ghostty 1.2.0 notes](https://ghostty.org/docs/install/release-notes/1-2-0); Ghostty documents it at `/docs/vt/osc/conemu` — [Ghostty VT reference](https://ghostty.org/docs/vt/reference)
- iTerm2 documents `OSC 9 ; 4 ; [st] ; [pr] ST` with the same states and an abbreviated stop form `OSC 9 ; 4 ST` — [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html)
- tmux has a `progressbar` terminal feature ("Supports the OSC 9;4 progress bar extension") — [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html)

#### OSC 7 current working directory and OSC 133 semantic prompts
- OSC 7: `OSC 7 ; file://hostname/path ST`; foot requires "a local hostname"; iTerm2 shows `file://example.com/usr/bin` and also accepts `OSC 1337 ; CurrentDir=path ST` — [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en); [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html)
- tmux: simple OSC 7 support exposed as `pane_path` (3.1) and an `osc7` terminal feature handled like the title and controlled by `set-titles` (3.3) — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- Windows Terminal's shell-integration guidance uses ConEmu's `OSC 9 ; 9 ; "cwd" ST` for the working directory — [WT shell integration](https://learn.microsoft.com/en-us/windows/terminal/tutorials/shell-integration); ConEmu defines `OSC 9;9;"cwd" ST` as "Inform ConEmu about shell current working directory" — [ConEmu](https://conemu.github.io/en/AnsiEscapeCodes.html)
- OSC 133: `OSC 133 ; A ST` prompt start, `OSC 133 ; B ST` command start, `OSC 133 ; C ST` output start, `OSC 133 ; D ; <ExitCode> ST` command finished; Windows Terminal supports these since 1.15 Preview, marks "stable" in 1.21 — [WT shell integration](https://learn.microsoft.com/en-us/windows/terminal/tutorials/shell-integration); iTerm2 documents A/B/C/D with exit status 0–255 — [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html); foot (A, C, D), WezTerm ("Informs the terminal about Input, Output and Prompt regions") and zellij 0.45.0 also support it — [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en); [WezTerm](https://wezterm.org/escape-sequences.html); [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)

#### Window title (OSC 0/2)
- `OSC 0 ; string ST` sets icon name and title, `OSC 2 ; string ST` title only — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); Windows console accepts strings "less than 255 characters" — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- tmux gates it behind `allow-set-title`; its FAQ warns "Some consoles don't like attempts to set the window title" — [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html); [tmux FAQ](https://github.com/tmux/tmux/wiki/FAQ)

#### Mode 2027 (grapheme cluster width)
- Query `CSI ? 2027 $ p`; foot documents the mode as "Grapheme cluster processing" — [Mitchell Hashimoto](https://mitchellh.com/writing/grapheme-clusters-in-terminals); [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en)
- Windows Terminal 1.22: "You can query for grapheme cluster support using DECRPM 2027" — [WT v1.22.10352.0](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0)
- Hazard: "terminals with similar capabilities often do not respond to Mode 2027 queries, so it has limited utility as a binary indicator" — [Quast 2025](http://www.jeffquast.com/post/state-of-terminal-emulation-2025)

#### 24-bit colour and its detection
- SGR `ESC[38;2;r;g;bm` / `ESC[48;2;r;g;bm`; the colon form `ESC[48:2:1:2:3m` is also accepted by many terminals; detection via `COLORTERM=truecolor` or `24bit`, but "COLORTERM is not forwarded through sudo or ssh" by default; terminfo `RGB` capability exists since ncurses 6.0-20180121; most reliable method is to set a colour then query with DECRQSS and compare — [termstandard/colors](https://github.com/termstandard/colors)
- tmux: declare the outer terminal with `terminal-features ',gnome*:RGB'` (3.2+) or `terminal-overrides ',gnome*:Tc'`; "RGB is the official flag, Tc is a tmux extension"; tmux 3.6 "checks COLORTERM as a hint for RGB colour" — [tmux FAQ](https://github.com/tmux/tmux/wiki/FAQ); [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- notcurses: `COLORTERM=24bit` forces RGB "regardless" of terminfo; Terminal.app "No RGB"; GNU screen "24-bit only in 5.X" — [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md); termstandard now lists Terminal.app truecolor "Since macOS 26" — [termstandard/colors](https://github.com/termstandard/colors)
- Windows console: SGR 38;2 / 48;2 documented; on a 16-colour conhost it picks "the nearest appropriate color from the existing 16 color table" — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences); Windows Terminal and ConHost are listed as fully supporting truecolor — [termstandard/colors](https://github.com/termstandard/colors)

#### Cursor shape (DECSCUSR)
- `CSI Ps SP q`: 0/1 blinking block, 2 steady block, 3 blinking underline, 4 steady underline, 5 blinking bar, 6 steady bar (xterm adds 7 "initial resources") — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); Windows console supports 0–6 — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- iTerm2: `CSI 0 SP q` resets to the user default, "intentionally deviates from DEC" — [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html); foot: Ps=0 means "use style from foot.ini" — [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en); tmux has `cursor-style`/`cursor-colour` options (3.3) and DECRQSS cursor-style reporting (3.6) — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)

#### Alternate screen (1049) and its trade-offs
- `CSI ? 1049 h` saves the cursor (DECSC), switches to the alternate buffer and clears it; `l` restores; xterm recommends 1049 over 47 — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
- Windows console: "The alternate buffer is exactly the dimensions of the window, without any scrollback region"; scrolling margins are per-buffer — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- Trade-off in practice: Claude Code's "flicker-free alt-screen rendering with virtualized scrollback" (`CLAUDE_CODE_NO_FLICKER=1`) was reported as destroying scrollback when output exceeded the window height (v2.1.89; a bot later marked it fixed "as of version 2.1.101") — [claude-code #41965](https://github.com/anthropics/claude-code/issues/41965); Anthropic's Thariq: "We may explore alternate screen mode in the future, but our bar is quite high" — [steipete, Signature flicker](https://steipete.me/posts/2025/signature-flicker)

#### Scroll regions (DECSTBM) and insert/delete line as a way into scrollback
- `CSI t ; b r` sets the region (default full window) — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); Windows console: IL/DL only affect lines inside the margins, "If lines would be shifted below the margins, they are discarded", and margins are per-buffer — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- ratatui's inline viewport: `Terminal::insert_before` "uses terminal scrolling regions to insert content above an inline viewport" without clearing it (behind the `scrolling-regions` feature; otherwise it clears the viewport and redraws); when the viewport is at the bottom, "inserted lines will scroll the area of the screen above the viewport upwards" and "the top lines will go directly into the terminal's scrollback buffer" — [ratatui Terminal docs](https://docs.rs/ratatui/latest/ratatui/struct.Terminal.html)
- Claude Code gates its DECSTBM-based status line on terminal identity: debug log lines `DECSTBM: gated (TMUX=unset ZELLIJ=unset TERM_PROGRAM=unset TERM=unset)` and `DECRQM(2026): skipped (no XTVERSION reply) → sync unsupported` — [claude-code #75218](https://github.com/anthropics/claude-code/issues/75218)
- tmux has a `margins` feature for DECSLRM (left/right margins) — [tmux(1)](https://man7.org/linux/man-pages/man1/tmux.1.html)

#### Images (kitty graphics, iTerm2 inline, sixel)
- kitty graphics detection: send `ESC _ G i=31,s=1,v=1,a=q,t=d,f=24;AAAA ESC \` followed by `CSI c`; reply `ESC _ G i=31;OK ESC \` (or an error) means supported; "If you get back an answer for the device attributes without getting back an answer for the query action" it is unsupported; terminals "must reply to query actions immediately without processing other input" — [kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/)
- Transmission: base64 chunks "no larger than 4096 bytes" (all but the last a multiple of 4); media `t=d` direct, `f` file, `t` temp file, `s` POSIX shared memory; a remote client "has no a-priori knowledge of whether it shares a filesystem/shared memory with the terminal emulator" and must send pixels directly — [kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/)
- Multiplexers: images can be placed with the Unicode placeholder `U+10EEEE` plus row/column diacritics (`U=1` virtual placements), which "allows using images inside any host application that supports Unicode", tmux included; kitty's FAQ calls this "the unicode placeholders workaround that kitty created for tmux refusing to support images" — [kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/); [kitty FAQ](https://sw.kovidgoyal.net/kitty/faq/)
- Implementers listed by the kitty spec: AbsoluteTelnet/SSH, Ghostty, Konsole, Mobile SSH, st (patch), Warp, wayst, WezTerm, iTerm2, xterm.js — [kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/)
- iTerm2 inline images: `OSC 1337 ; File=[args] ST`; WezTerm implements the File upload part "Allows displaying images inline" — [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html); [WezTerm](https://wezterm.org/escape-sequences.html)
- Sixel: `DCS q <data> ST`; xterm advertises it as DA1 parameter 4; support: Contour native, foot 1.2.0, iTerm2 3.3.0, Konsole 22.04, mintty 2.6.0, mlterm 3.1.9, Rio 0.1.12 (broken in 0.4.x, restored 0.4.12), tmux "from commit dfbc6b1" with `--enable-sixel`, WezTerm from 20200620 (WezTerm's own docs call support "preliminary and incomplete"), Windows Terminal 1.22.10352.0, xterm by default since patch #359, xterm.js via the image addon, VS Code 1.80 with `terminal.integrated.enableImages`, Zellij 0.31.0; unsupported: Alacritty ("rejected by the maintainers"), Ghostty (kitty protocol instead), GNOME Terminal/VTE ("VTE removed SIXEL from every stable release"), kitty, Terminal.app, mosh ("closed as not planned"), Warp, PuTTY, urxvt — [arewesixelyet](https://www.arewesixelyet.com/); [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); [WezTerm](https://wezterm.org/escape-sequences.html)
- tmux 3.4 "Add[s] basic support for SIXEL if built with --enable-sixel"; 3.6 ignores non-SIXEL DCS sequences and adds a `sixel_support` format; 3.7 raises the image limit to 20 — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES); zellij added kitty graphics in 0.45.0 and "only advertise[s] Sixel support if the attached terminal also supports it" — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)

#### DA1 / DA2 / DA3 / XTVERSION / XTGETTCAP / DECRQM / DSR
- DA1 `CSI c` → `CSI ? Psc ; ... c` (VT220-class terminals answer `CSI ? 62 ; ... c`); parameters include 1 132-columns, 4 "Sixel graphics", 6 selective erase, 8 user-defined keys, 22 ANSI color, 28 rectangular editing, 29 text locator — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); tmux 3.5 "looks for feature codes 21 and 28" and 3.6 detects "OSC 52 support ... from the device attributes report"; Ghostty 1.2 "Indicate[s] support for OSC 52 in the primary DA report" — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES); [Ghostty 1.2.0 notes](https://ghostty.org/docs/install/release-notes/1-2-0)
- DA2 `CSI > c` → `CSI > Pp ; Pv ; Pc c` with Pp 0 VT100, 1 VT220, 2 VT240, 18 VT330, 19 VT340, 24 VT320, 32 VT382, 41 VT420, 61 VT510, 64 VT520, 65 VT525; Pv firmware version — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); DA2 "Identifies Alacritty's version number" — [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md)
- DA3 `CSI = c` → identifies VTE and foot (foot replies "FOOT" in hex) — [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md); [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en)
- XTVERSION `CSI > 0 q` → `DCS > | text ST`; foot answers `ESC P > | foot(version) ESC \`; iTerm2 answers `ESC P > | iTerm2 3.4.0 ST`; Contour, WezTerm and xterm identify via XTVERSION; tmux itself uses `CSI > q` to identify the outer terminal (3.2) — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en); [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html); [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md); [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- XTGETTCAP `DCS + q <hex names ; ...> ST` → valid `DCS 1 + r Pt ST`, invalid `DCS 0 + r ST`; `TN` (`DCS + q 544e ST`) identifies kitty and mlterm; foot answers from its built-in terminfo; Ghostty 1.2 fixed lowercase hex — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md); [foot-ctlseqs(7)](https://man.archlinux.org/man/foot-ctlseqs.7.en); [Ghostty 1.2.0 notes](https://ghostty.org/docs/install/release-notes/1-2-0)
- DECRQM `CSI ? Pd $ p` → DECRPM `CSI ? Pd ; Ps $ y` (0 not recognised, 1 set, 2 reset, 3 permanently set, 4 permanently reset) — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html); tmux 3.6 "adds DECRQM reporting for several modes" (?2004, ?1006), 3.7 answers DECRQM 2026 — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- DECRQM hazards found by ucs-detect: iTerm2 "Reports 'supported, but disabled, and cannot be changed' for all DEC Private Modes queried, including fictional mode 9876543"; Konsole "Does not reply to DEC Private Mode queries"; Contour "replied with a different mode number than the one queried" — [Quast 2025](http://www.jeffquast.com/post/state-of-terminal-emulation-2025)
- DSR `CSI 6 n` → CPR `CSI r ; c R`; hazard: shifted F3 can send `CSI 1 ; 2 R`, "which can be mistaken for a CPR" — [xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
- Windows console answers `ESC [ 0 c` with `\x1b[?1;0c` ("VT101 with No Options") per the 2018 doc and emits query replies into the input stream even when VT input mode is off — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)

#### The query-plus-sentinel technique
- kitty keyboard, kitty graphics and OSC 99 all specify "send the query, then DA1; a DA1 reply without the feature reply means unsupported" — [kitty keyboard](https://sw.kovidgoyal.net/kitty/keyboard-protocol/); [kitty graphics](https://sw.kovidgoyal.net/kitty/graphics-protocol/); [kitty notifications](https://sw.kovidgoyal.net/kitty/desktop-notifications/)
- notcurses sends DA3, DA2, XTVERSION, XTGETTCAP(TN), then DA1 last, because "all known terminals respond to it with something"; caveat: "if a terminal does not reply in a recognizable way to Primary Device Attributes, notcurses_init() will hang"; it only queries when `isatty(3)` is true — [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md)
- tmux 3.3 "raises the time terminals have to answer device attributes queries to three seconds" and 3.2 "waits for the initial commands before sending DA" — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- .NET's own cursor-position query (`System.Console` on Unix) waits 100 deciseconds (10 s) on the first request and 10 deciseconds afterwards, and pushes any non-matching bytes back as user input — [dotnet/runtime ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs)
- Claude Code (2.1.202) chains XTVERSION first and skips DECRQM 2026 when XTVERSION gets no reply (`XTVERSION: no reply (terminal ignored query)` in Windows Terminal 1.24 via PowerShell) — [claude-code #75218](https://github.com/anthropics/claude-code/issues/75218)

### Inferences
- A single startup probe batch written in one `write()` — `CSI ? 2026 $ p`, `CSI ? 2027 $ p`, `CSI ? u`, `CSI > 0 q`, optional `APC G a=q`, optional `OSC 99 ... p=?`, then `CSI c` — resolves on the DA1 reply or a timeout; the kitty, notcurses and Claude Code sources all converge on this. A terminal that answers DECRPM with 4 for every mode (iTerm2) or never answers DECRQM (Konsole) means DECRPM must be read as "1 or 2 ⇒ yes" and never as "0/4 ⇒ definitely no" when other evidence (XTVERSION, TERM_PROGRAM) says the terminal is known to support the feature.
- Because flag 1 alone leaves Enter as 0x0d, a UI that wants Shift+Enter must push flag 8 (and typically 1|2|8) and must pop on exit and on crash paths; the "terminal left in enhanced keyboard mode" reports show the cost of forgetting.
- OSC 9;4 and OSC 9 notifications share a prefix; a terminal that treats `OSC 9 ; 4 ; ...` as a notification (older OSC 9 implementations) will show a toast per progress update. Use XTVERSION/TERM_PROGRAM allow-lists (Windows Terminal ≥ 1.6, Ghostty ≥ 1.2, iTerm2, ConEmu, tmux `progressbar` feature) rather than probing.

### Gaps
- No primary source quantifies the Esc-timeout values used by crossterm, neovim or fish (tmux's 10 ms default and the "50 ms hardcoded delay" complaint in [claude-code #29129](https://github.com/anthropics/claude-code/issues/29129) are the only numbers found).
- The exact DA1 string emitted by current Windows Terminal/OpenConsole (after sixel support) was not found; the Microsoft doc still shows the 2018 `?1;0c`.
- VTE's current OSC 52 status could not be confirmed (the GNOME issue page gave no status; the tmux wiki says unsupported; a PyPI page claims "recent GNOME Terminal" supports it).
- The official mode 2027 spec text (contour-terminal/terminal-unicode-core) could not be retrieved; only the DECRQM form and terminal implementations are sourced.
- The freedesktop OSC 133 spec page was blocked (Anubis); sequences are sourced from Microsoft and iTerm2 docs instead.

## Key question 2: Support matrix across terminals and multiplexers

### Takeaway
The "modern baseline" (2026 sync, kitty keyboard, OSC 8, OSC 52 write, 24-bit colour, OSC 133) is now met by Ghostty, kitty, WezTerm, foot, Alacritty, iTerm2, Windows Terminal (1.24/1.25), Warp, VS Code (1.109) and zellij; the holdouts are Terminal.app (no 2026/OSC 8/OSC 52 evidence; truecolor only since macOS 26), legacy conhost, JetBrains' JediTerm, GNU screen, mosh and VTE for OSC 52. Through tmux the picture changes: tmux ≥ 3.7 handles 2026, ≥ 3.4 OSC 8 and sixel (build flag), OSC 52 needs `set-clipboard on`, images need the Unicode placeholder scheme, and the kitty keyboard protocol is not supported at all (only xterm-style/CSI u extended keys).

## Key question 3: Windows specifics (ConPTY, SetConsoleMode, Windows Terminal vs conhost, WSL, Git Bash/mintty, agent-CLI failures)

### Takeaway
On Windows the terminal the app talks to is almost always ConPTY, not the visible terminal: the app must enable VT with `SetConsoleMode` (output `ENABLE_VIRTUAL_TERMINAL_PROCESSING | DISABLE_NEWLINE_AUTO_RETURN`, input `ENABLE_VIRTUAL_TERMINAL_INPUT`), queries are answered by the console host rather than the terminal (DA1 `?1;0c` historically; XTVERSION observed unanswered), and the 1.22 rewrite replaced the old "render a snapshot" model with "direct API→VT translation", which is what makes 2026 (1.24), sixel (1.22) and kitty keys (1.25) possible. The classic traps are mintty/Git Bash giving native programs pipes instead of a console, Win10's conhost, and hosts (Rider) that never enable VT processing.

### Cited Findings

#### Enabling VT input/output
- Output sequences are intercepted "if the ENABLE_VIRTUAL_TERMINAL_PROCESSING flag is set on the screen buffer handle using SetConsoleMode"; "DISABLE_NEWLINE_AUTO_RETURN ... may also be useful in emulating the cursor positioning and scrolling behavior of other terminal emulators"; input sequences are emitted "if the ENABLE_VIRTUAL_TERMINAL_INPUT flag is set on the input buffer handle"; recommended pattern: GetConsoleMode, OR the flags, SetConsoleMode, and on failure with ERROR_INVALID_PARAMETER "gracefully degrade behavior and try again" without DISABLE_NEWLINE_AUTO_RETURN — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- Query replies (DSR/DA) "will emit their responses into the console input stream immediately ... The ENABLE_VIRTUAL_TERMINAL_INPUT flag does not apply to query commands" — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- The doc's "Anniversary Update" sample uses 1049, tab stops, DECSTBM and DEC line drawing; DECSTBM, IL/DL and SU/SD obey margins; alternate buffer has no scrollback — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- Some hosts never enable VT processing for the child: Rider's run console and external console lacked `ENABLE_VIRTUAL_TERMINAL_PROCESSING`, fixed only by the app setting it itself ("known issue") — [JetBrains Rider support thread](https://rider-support.jetbrains.com/hc/en-us/community/posts/4415072120210)
- .NET's `Console.ReadKey` returns `ConsoleKeyInfo.Modifiers` as a bitwise combination of Shift/Alt/Control, with the documented example distinguishing `SHIFT+R`, `ALT+K`, `CTL+P` (Windows console API path) — [ConsoleKeyInfo.Modifiers](https://learn.microsoft.com/en-us/dotnet/api/system.consolekeyinfo.modifiers)

#### ConPTY behaviour
- `CreatePseudoConsole(size, hInput, hOutput, dwFlags, phPC)`; flags documented: 0 or `PSEUDOCONSOLE_INHERIT_CURSOR`; "The input and output streams encoded as UTF-8 contain plain text interleaved with Virtual Terminal Sequences"; minimum Windows 10 1809 / Server 2019; with INHERIT_CURSOR the host must answer the cursor-state request asynchronously or "the calling application [may] hang" — [CreatePseudoConsole](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole)
- 2018 design: ConHost's "VT Renderer" "Generates the VT sequences necessary to move the cursor" and "renders changed areas of the Output Buffer as text/VT" back to the terminal; input text is converted into INPUT_RECORDs; `ResizePseudoConsole(hPC, size)` "Resizes the given ConPTY's internal buffer" — [Introducing ConPTY](https://devblogs.microsoft.com/commandline/windows-command-line-introducing-the-windows-pseudo-console-conpty/)
- Windows Terminal 1.22 (preview 27 Aug 2024, stable 1.22.10352.0 on 5 Feb 2025): "A completely rewritten console hosting implementation, which now supports Sixels"; "It may cause some compatibility issues, but it is also the future we're staking ConPTY on"; the preview post describes it as direct API→VT translation instead of rendering a point-in-time snapshot — [WT v1.22.10352.0](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0); [WT 1.22 preview post](https://devblogs.microsoft.com/commandline/windows-terminal-preview-1-22-release)
- ConPTY consequences for queries: a Claude Code debug log inside Windows Terminal 1.24 + PowerShell shows `XTVERSION: no reply (terminal ignored query)`; the reporter's hypothesis that ConPTY "does not reliably forward the terminal's response" was not verified at the ConPTY level, and the status-line symptom turned out to be a Git Bash/PowerShell stdin problem — [claude-code #75218](https://github.com/anthropics/claude-code/issues/75218)
- Windows Terminal exposes only `WT_SESSION`/`WT_PROFILE_ID`, not `TERM_PROGRAM`, so `/terminal-setup`-style detection that keys on `TERM_PROGRAM` fails — [claude-code #24384](https://github.com/anthropics/claude-code/issues/24384)
- VS Code 1.109 added an experimental `terminal.integrated.enableWin32InputMode`, "tuned specifically for Windows and its pseudoterminal backend ConPTY", off by default — [VS Code 1.109](https://code.visualstudio.com/updates/v1_109)

#### Windows Terminal vs conhost
- Windows Terminal: 2026 in stable 1.24; kitty keyboard protocol in 1.25 ("allows applications to receive Shift+Enter among other things ... some agentic command-line tools"); ambiguous-width setting — [WT 1.25 preview post](https://devblogs.microsoft.com/commandline/windows-terminal-preview-1-25-release/)
- Windows Terminal 1.22: grapheme clusters, DECRPM 2027, `compatibility.textMeasurement` (grapheme / wcswidth / "original Windows Console" mode "where zero-width characters were actually 1-width"), `compatibility.allowOSC52`, new cooked-read popups "render[ed] under the cursor and use[ing] VT instead of console APIs" — [WT v1.22.10352.0](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0)
- Windows Terminal OSC 133 (1.15 preview, stable 1.21) and OSC 9;4 (1.6) — [WT shell integration](https://learn.microsoft.com/en-us/windows/terminal/tutorials/shell-integration); [WT progress bar](https://learn.microsoft.com/en-us/windows/terminal/tutorials/progress-bar-sequences)
- conhost: "the conhost console layer of Windows interferes with escape sequence controls"; "This broken behaviour was fixed for Windows 11 but not back-ported to Windows 10"; workaround is replacing conhost.exe with OpenConsole.exe from the Windows Terminal project — [mintty wiki Tips](https://github.com/mintty/mintty/wiki/Tips)

### Inferences
- A .NET TUI on Windows has two keyboard paths: with `ENABLE_VIRTUAL_TERMINAL_INPUT` it receives xterm-style bytes (and, under WT 1.25, kitty-style bytes if it pushes flags); without it, `ReadConsoleInput`/`Console.ReadKey` already deliver Shift+Enter and Ctrl+Enter as distinct key records. Because .NET's `ConsoleKeyInfo.Modifiers` documents Shift/Alt/Control on Windows, the console API path is the simplest robust way to get Shift+Enter on Windows regardless of terminal, whereas on Unix it depends on kitty flags or terminal-specific configuration.
- Treat Windows as "unknown terminal behind ConPTY": run the same probe batch, but expect XTVERSION to go unanswered, prefer `WT_SESSION` for identity, and gate 2026 on DECRPM rather than identity (WT 1.24+ answers it).
- Since ConPTY itself re-encodes output, inline-UI techniques that rely on the terminal's reflow (DECSTBM-into-scrollback) have a second interpreter in the path; verify on WT and conhost separately.

### Gaps
- No official documentation of a ConPTY "passthrough" flag was found (CreatePseudoConsole lists only 0 and INHERIT_CURSOR); the experimental Windows Terminal passthrough mode is only referenced in secondary search summaries.
- Which specific sequences ConPTY (post-1.22) swallows or rewrites (DA2, XTVERSION, XTGETTCAP, DECRQM for unknown modes) is not documented by Microsoft; only the XTVERSION "no reply" log line is primary evidence.
- Whether .NET's `System.Console` on Windows enables `ENABLE_VIRTUAL_TERMINAL_PROCESSING` automatically was not confirmed from dotnet/runtime sources (only third-party reports that apps had to set it themselves).

## Key question 4: Resize and reflow

### Takeaway
Modern terminals (and tmux since 2.x, zellij, WT 1.22) reflow wrapped lines on resize, but scrollback is immutable cell data: an inline (non-alternate-screen) UI that redraws by "cursor-up N lines and erase" loses track of N as soon as the terminal re-wraps, and anything that scrolled above the viewport cannot be erased, producing duplicated or "squished" copies. The documented coping strategies are: redraw only the live region after a resize (debounced), track the previous width and re-wrap your own line model, keep the live region shorter than the viewport, or use the alternate screen at the cost of native scrollback.

### Cited Findings
- Windows console: "The alternate buffer is exactly the dimensions of the window, without any scrollback region"; scrolling margins are per-buffer — [Console VT sequences](https://learn.microsoft.com/en-us/windows/console/console-virtual-terminal-sequences)
- tmux reflow history: "performance improvements for reflow, and wide characters are handled when reflowing" (2.7); "preserves horizontal cursor position as well as vertical during reflow" (2.9); "removes SIXEL images before reflow" (3.5); "fixes misplaced wrapped lines during partial redraws" (3.8) — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- tmux 3.7 clears an in-progress synchronized update on resize ("Also clears sync mode on resize") — [tmux PR #4744](https://github.com/tmux/tmux/pull/4744)
- zellij: "reset scroll region boundaries when resizing in alternate screen" and "improve line-wrapping/resize performance" (0.44.0); "out of bounds removal when app does not update its scroll region on resize" (0.42.0); "do not render if resizing screen to same size" (0.41.0); "adjust saved cursor position on resize" (0.29.0) — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)
- Claude Code (Ink-based at the time) on Windows Terminal: "When the terminal window is resized horizontally, Claude Code re-renders the entire conversation output for each resize event. Previous renders are not cleared from the scroll buffer, resulting in 10-20+ duplicated copies"; reporter's proposed fixes: alternate screen (loses history), "debounce resize events and clear the previous render before re-drawing", or "only re-render the active input area, leave historical output as-is" — [claude-code #40555](https://github.com/anthropics/claude-code/issues/40555)
- Repeated lines after resize on macOS/WezTerm with the alt-screen mode enabled — [claude-code #47208](https://github.com/anthropics/claude-code/issues/47208); the alt-screen "virtualized scrollback" mode re-rendered the whole conversation once output exceeded ~24 rows, destroying scrollback (v2.1.89; fixed per bot "as of version 2.1.101") — [claude-code #41965](https://github.com/anthropics/claude-code/issues/41965)
- Ink has no API to force a full redraw after resize: "scrollback content rendered during the narrow period stays at 60 chars"; "The only option is to restart the Ink application" (issue open, May 2026) — [vadimdemedes/ink #942](https://github.com/vadimdemedes/ink/issues/942)
- Ink's stale-frame mechanism: when a frame is taller than the terminal, cursor-up saturates at the top of the viewport so content that scrolled off cannot be erased, and the previous frame's height is not accounted for (Ink issues 717/781 as mirrored by the Harbor benchmark tasks) — [Harbor task ink-717](https://hub.harborframework.com/tasks/abundant/vadimdemedes__ink-717); [Harbor task ink-781](https://hub.harborframework.com/tasks/abundant/vadimdemedes__ink-781) (secondary mirrors; the upstream issues were not fetched)
- Anthropic "rewrote the renderer from scratch" for Claude Code 2.0.72 to stop the flicker while keeping React as the component model; Ink "didn't support the kind of fine-grained incremental updates needed for a long-running interactive UI"; "Amp switched to alt mode in September" and "the Gemini TUI was rolled back" — [steipete, Signature flicker](https://steipete.me/posts/2025/signature-flicker)
- ratatui inline viewports: "On resize, Ratatui recomputes the inline origin while trying to keep the cursor at the same relative row inside the viewport"; it tracks a "last known cursor position" for that; `clear` for inline viewports "clears after the viewport's origin, leaving any content above the viewport untouched"; near the bottom, "terminals scroll; Ratatui accounts for that scrolling by shifting the computed viewport origin upward" — [ratatui Terminal docs](https://docs.rs/ratatui/latest/ratatui/struct.Terminal.html)
- Warp: stale Claude Code header/status rows repeating after resize or fullscreen transitions were triaged to Warp's own resize/grid handling — [warpdotdev/warp #9838](https://github.com/warpdotdev/warp/issues/9838)
- Resize signalling in .NET: `PosixSignal.SIGWINCH` ("Window resized") exists since .NET 6 and System.Console on Unix invalidates its cached window size on SIGCONT/SIGCHLD/SIGWINCH, falling back to terminfo `Columns`/`Lines` when `TIOCGWINSZ` fails; `SetWindowSize` throws on Unix — [PosixSignal](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.posixsignal); [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs)
- Windows Terminal 1.22 grapheme-cluster measurement changed how wide/zero-width characters occupy cells (with wcswidth and legacy console modes selectable) — [WT v1.22.10352.0](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0)

### Inferences
- The only resize strategy that cannot duplicate output is to never redraw anything that has already left the live region: emit committed transcript text once (so the terminal owns its reflow) and keep a small live region (status/input/current streaming block) whose height is always ≤ viewport rows. On SIGWINCH/`WINDOW_BUFFER_SIZE_EVENT`, debounce, re-measure width, clear from the live region's origin to end of screen (`CSI J`), and repaint only the live region; this matches ratatui's inline model and the fixes proposed in the Claude Code reports.
- Width-tracking matters because wrapping changes the number of physical rows the live region occupies; the live region's row count must be recomputed from the new width (and from the terminal's actual width-measurement mode, see question 6) before issuing cursor-up counts.

### Gaps
- No primary documentation was found describing exactly how each terminal (Ghostty, kitty, WezTerm, Alacritty, Terminal.app, Windows Terminal, conhost) reflows scrollback on resize; the reflow facts above come from multiplexer changelogs and bug reports.
- Ink's upstream issues #717/#781 were only seen through mirrors.

## Key question 5: SSH and high latency (batching, mosh, query cost)

### Takeaway
Over slow links the costs are round trips: every probe costs at least one RTT and a timeout if unanswered, so probes must be batched into one write and ended with a DA1 sentinel; frames must be coalesced into single writes wrapped in 2026 so partial frames never show; and mosh adds its own layer (predictive underlined echo, visible-state-only sync, no scrollback) that a TUI should treat as a plain xterm-256color without sync, kitty keys or images.

### Cited Findings
- mosh "runs a predictive model in the background of the server's behavior"; predictions are shown when confirmed, "On a bad connection, outstanding predictions are underlined"; predictions resume after ESC, Enter or arrow keys; the State Synchronization Protocol runs over UDP and "synchronizes only the visible state of the terminal" — [mosh.org](https://mosh.org/)
- mosh 1.4.0 added true colour, OSC 52 copy, and "skip prediction on large pastes into mosh-client" — [mosh 1.4.0 release](https://mosh.org/mosh-1.4.0-released.html)
- Queries over the wire: kitty requires terminals to "reply to query actions immediately without processing other input" — [kitty graphics](https://sw.kovidgoyal.net/kitty/graphics-protocol/); iTerm2 and Extraterm were slow enough that ucs-detect reduced test parameters, and the author advises to "Expect slow automatic replies from some terminals and handle them gracefully" — [Quast 2025](http://www.jeffquast.com/post/state-of-terminal-emulation-2025)
- tmux gives outer terminals three seconds to answer DA queries (3.3), raised the escape-sequence timeout to five seconds (3.1), and "aligns request and extended escape timeouts" (3.7) — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)
- tmux's `escape-time` must be larger on slow links; "an escape-time of zero is likely to be fine" locally — [tmux FAQ](https://github.com/tmux/tmux/wiki/FAQ)
- zellij fixed "occasional input spam when pressing ESC and holding the mouse over slow SSH connections" (0.45.0) — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)
- 2026 timeout guidance: a too-short timeout "due to a very slow connection" is "no worse than having no synchronized output" — [vt-extensions](https://github.com/contour-terminal/vt-extensions/blob/master/synchronized-output.md); tmux 3.7 flushes after 1 second if ESU never arrives — [tmux PR #4744](https://github.com/tmux/tmux/pull/4744)
- Environment does not survive SSH: "COLORTERM is not forwarded through sudo or ssh" by default — [termstandard/colors](https://github.com/termstandard/colors); kitty's terminfo is missing on remote hosts ("SSHing into a computer that does not have the kitty terminfo files"), fixed by `kitten ssh` — [kitty FAQ](https://sw.kovidgoyal.net/kitty/faq/); Ghostty 1.2's `ssh-env` sets `TERM=xterm-256color` for SSH sessions and `ssh-terminfo` copies its terminfo — [Ghostty 1.2.0 notes](https://ghostty.org/docs/install/release-notes/1-2-0)
- The kitty graphics protocol's file/shared-memory media cannot be assumed over SSH; remote clients must send pixels inline in ≤4096-byte chunks — [kitty graphics](https://sw.kovidgoyal.net/kitty/graphics-protocol/)
- .NET's cursor-position query budget is 10 s for the first request and 1 s afterwards, which is the kind of latency allowance a remote session needs — [ConsolePal.Unix.cs](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Console/src/System/ConsolePal.Unix.cs)

### Inferences
- Over SSH the probe batch is ~one RTT when the terminal answers DA1, and exactly the chosen timeout when it does not; the budget should be generous (1–3 s like tmux) but non-blocking (render a conservative UI immediately, upgrade when replies arrive).
- With mosh, the prediction engine underlines locally echoed keystrokes; a TUI that redraws its input line on every keystroke will fight the predictions, so it should rely on the terminal echoing nothing (raw mode) and accept visible underlined predictions as a mosh artefact.

### Gaps
- No source quantifies how mosh treats 2026, kitty keyboard flags or bracketed paste; its "visible state only" model suggests unknown sequences are dropped, but that was not documented.

## Key question 6: Accurate string width measurement

### Takeaway
There is no single correct width: wcwidth-per-codepoint (sum of 2+0+2 = 4 for the ZWJ farmer emoji) is what tmux, kitty, Alacritty, VTE, xterm and Warp do; grapheme clustering (= 2) is what Ghostty, Contour, foot, WezTerm, iTerm2 and Windows Terminal ≥ 1.22 do; Terminal.app gives 6 and old Windows Terminal gave 5. A program must either avoid depending on width for multi-codepoint graphemes, query/negotiate mode 2027, or measure with CPR (`CSI 6 n`); libraries differ by Unicode version (wcwidth 0.8+ targets Unicode 18 segmentation; unicode-width 0.2.2 is based on Unicode 16).

### Cited Findings
- The farmer emoji (U+1F9D1 U+200D U+1F33E) measures 2 + 0 + 2 = 4 with per-codepoint wcwidth but 2 as a grapheme cluster; observed cursor moves are "2, 4, 5, or 6 cells"; table: Ghostty 2 (2027 ✅, falls back to wcwidth if 2027 off), Contour 2 (always clusters), Foot 2 (2027 ✅), WezTerm 2 (always clusters, 2027 ✅), iTerm 2 (always clusters, no 2027), Alacritty 4, Gnome 4, Kitty 4, Tmux 4, Warp 4, Xfce 4, xterm 4, Windows Terminal 5 ("Considers ZWJ one cell"), Terminal.app 6; the author disabled always-on clustering in Ghostty because fish redrew its prompt in the wrong place; guidance: ignore it if you never track the cursor, query 2027, or measure with `CSI 6 n`; "do not assume either wcwidth or clustering behavior" — [Mitchell Hashimoto](https://mitchellh.com/writing/grapheme-clusters-in-terminals)
- Windows Terminal 1.22 added grapheme clusters ("Emoji with zero-width joiners, combining characters, Unicode flag sequences, and more"), DECRPM 2027, and `compatibility.textMeasurement` with a wcswidth-compatible mode and the legacy console mode — [WT v1.22.10352.0](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0); ucs-detect on WT 1.24.11321.0: wide 93.87% raw, 100% ZWJ and VS16 — [ucs-detect WT results](https://ucs-detect.readthedocs.io/sw_results/windowsterminal.html); Windows Terminal 1.25 lets users configure how "Ambiguous" width characters render — [WT 1.25 post](https://devblogs.microsoft.com/commandline/windows-terminal-preview-1-25-release/)
- ucs-detect methodology: it prints text followed by cursor-position requests and compares the reported column with Python wcwidth; 2025 findings: Ghostty highest score, kitty "just as well", only those two correctly support VS15; iTerm2 answers DECRQM with "supported, but disabled, and cannot be changed" for every mode; Konsole doesn't answer DECRQM; Contour answers with the wrong mode number; VTE scores low and "unchanged from 2023"; mode 2027 "has limited utility as a binary indicator"; recommendation: "Test interactively for specific features, codepoints, and Unicode version levels" — [Quast 2025](http://www.jeffquast.com/post/state-of-terminal-emulation-2025); Apple Terminal VS15: 0/158 — [ucs-detect Apple Terminal](https://ucs-detect.readthedocs.io/sw_results/appleterminal.html)
- Python wcwidth spec: width 0 for Mn/Me/Cf/Default_Ignorable, Hangul Jungseong (U+1160–U+11FF, U+D7B0–U+D7FF), and the codepoint after ZWJ; width -1 for C0/C1 controls (only in low-level functions); width 2 for East Asian F/W, both Regional Indicators of a flag pair ("measured as width 2 total"), standalone Fitzpatrick modifiers; "VS16 adds 1 cell to the narrow character it directly follows, making the pair width 2"; "VS15 subtracts 1 cell from the wide character it directly follows"; "Any grapheme cluster width is limited to 2 cells since 0.8.0"; VS15 "is contested"; `wcwidth.iter_graphemes()` implements UAX #29 for Unicode 18.0 while Python 3.15's `unicodedata.iter_graphemes()` implements Unicode 17.0; Tamil/Kannada/Sinhala are a known limitation — [wcwidth specs](https://wcwidth.readthedocs.io/en/latest/specs.html)
- Rust unicode-width 0.2.2: "the width of a string differs from the sum of the widths of its constituent characters" for `\r\n` (1), well-formed emoji ZWJ sequences (2), emoji presentation sequences (2), emoji modifier sequences (2); `cjk` feature makes East_Asian_Width Ambiguous characters 2 in CJK context; example `"“𘀀”"` is 4 with `width()` and 6 with `width_cjk()`; references point to Unicode 16.0.0 — [unicode-width docs](https://docs.rs/unicode-width/latest/unicode_width/)
- Multiplexers: tmux uses wcwidth (farmer = 4) and its "cursors become out of sync" with a clustering host terminal — [Mitchell](https://mitchellh.com/writing/grapheme-clusters-in-terminals); tmux added ZWJ support (3.3), rewrote combined-character handling "to support newer Unicode combining characters" (3.4), added `codepoint-widths` and a VS16 width option plus Hangul Jamo/filler and regional-indicator handling (3.6), skin tone combination (3.6a), and `codepoint-widths` ranges (3.7) — [tmux CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES); zellij accounts "for emoji/widechars when double/triple-clicking" (0.43.0) — [zellij CHANGELOG](https://github.com/zellij-org/zellij/blob/main/CHANGELOG.md)
- iTerm2 has a "Use Unicode version 9+ widths" option and experimental REP/VS16 features; kitty lacks `bce`; Konsole marks ccc/blocks unsupported — [notcurses TERMINALS.md](https://github.com/dankamongmen/notcurses/blob/master/TERMINALS.md)
- Legacy Windows console measured zero-width characters as 1 cell — [WT v1.22.10352.0](https://github.com/microsoft/terminal/releases/tag/v1.22.10352.0)

### Inferences
- For Corvid, the safest layout rule is: measure with a grapheme-aware algorithm capped at 2 cells (the wcwidth 0.8+/unicode-width model), then *also* avoid placing multi-codepoint emoji in width-critical positions (right-aligned columns, box borders, the last cell of a line). On terminals that answer DECRPM 2027 with 1 or 2 the clustering assumption holds; on terminals that answer 0/4 or nothing, the UI should assume per-codepoint wcwidth for tmux/kitty/Alacritty/VTE but still cannot predict Terminal.app (6) or old Windows Terminal (5), so a one-time CPR calibration (print a known ZWJ sequence, `CSI 6 n`, compare) is the only way to learn the terminal's real behaviour.
- Because tmux measures with wcwidth regardless of the outer terminal, inside tmux the correct model is tmux's, not the terminal's; the `TMUX` env var should switch the width model to wcwidth-with-cap-2 (tmux 3.6+ options can change this per user, which the program cannot see).

### Gaps
- .NET's built-in grapheme segmentation (`System.Globalization.StringInfo`) and the `Wcwidth` NuGet port used by Spectre.Console were not researched; their Unicode versions are unknown from this research.
- The per-terminal Unicode-version table from ucs-detect's summary page (results.html) could not be fetched; only the Windows Terminal and Apple Terminal per-terminal pages were reachable.
- A Unicode-standard terminal-width specification (the L2/23-107 proposal cited by wcwidth) was not retrieved.
