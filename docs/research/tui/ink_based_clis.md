# Ink-based agent CLIs (Gemini CLI, Qwen Code, Copilot CLI, Cline CLI, Hermes Agent TUI) and the lessons they learned about Ink at scale — state as of 2026-10-21

Scope note: Claude Code is excluded by assignment. All GitHub issue/PR numbers below were read directly on 2026-10-21 unless marked "(search snippet only)". Dates are the dates shown on the pages. Where a source is secondary (blog recaps, news) it is marked as such.

## Q1. How Ink renders, and the failure modes that show up across these projects

### Takeaway
Ink is a React reconciler that re-renders the *whole dynamic frame* (throttled to 30 fps by default) and erases/rewrites it with cursor-up + erase-line sequences; only `<Static>` output is written once and left in scrollback. The single most important mechanic for agent CLIs is the fallback: when the dynamic frame is as tall as (or taller than) the terminal, Ink cannot erase lines that scrolled off, so it clears the viewport and redraws everything — which is the root of the flicker, "jump to top", lost-scrollback and duplicated-output reports in Gemini CLI, Qwen Code, Copilot CLI and Hermes alike. Every project ended up doing some combination of: alternate screen buffer, a forked Ink, height-capping of the live region, virtualizing history, synchronized output (DEC 2026), and throttling streaming updates.

### Cited Findings
- Ink's README describes `<Static>` as a component that "permanently renders its output above everything else", meant for output that will not change (completed tasks, logs), and notes the caveat "`<Static>` only renders new items in the `items` prop and ignores items that were previously rendered" — [Ink README](https://github.com/vadimdemedes/ink)
- Ink `render()` options and defaults (from the README, which says "This readme documents the upcoming version of Ink"): `maxFps` default 30; `incrementalRendering` default `false` ("Updates only changed lines instead of redrawing all output. Lines with unsupported terminal controls fall back to whole-line updates"); `alternateScreen` default `false` ("Renders in the terminal's alternate screen buffer and restores the original content on exit. Only works in interactive mode"); `patchConsole` default `true` (Ink clears the main output, prints the console output, then re-renders); `concurrent` default `false`; `kittyKeyboard` (mode `'auto'`, flags `['disambiguateEscapeCodes']`); `exitOnCtrlC` default `true` — [Ink README](https://github.com/vadimdemedes/ink)
- `useInput`: "Pasted text longer than one character arrives as a single string"; `isActive` exists for when several `useInput` hooks are mounted; `measureElement()` "returns zeros for all properties when called during render"; `useStdout().write()` is "similar to `<Static>` but accepts only strings"; `suspendTerminal()` hands the terminal to a child process (editor) and then forces a full redraw — [Ink README](https://github.com/vadimdemedes/ink)
- Ink's own "Who's using Ink" list includes Claude Code, Gemini CLI, GitHub Copilot CLI, Qodo Command, Nanocoder, Neovate Code, Deep Code CLI, SSH AI Chat, tweakcc, Shopify CLI, Cloudflare Wrangler, Prisma (self-reported) — [Ink README](https://github.com/vadimdemedes/ink)
- Ink source (master, `src/ink.tsx`): the fullscreen decision is `const isFullscreen = isStdoutTty && outputHeight >= viewportRows;` and a full-clear path is chosen by `shouldClearTerminalForFrame(previousOutputHeight, nextOutputHeight, isUnmounting)`. The clear sequence is `homeAndEraseDown = cursorTo(0,0) + eraseDown`, with a comment that `ansiEscapes.clearTerminal` "emits CSI 3J, which erases the" scrollback and so must be avoided. On the alternate screen the full clear writes `homeAndEraseDown + this.fullStaticOutput + outputToRender`; on the primary screen with a partial previous frame it does `this.log.clear()` then writes `staticOutput + outputToRender`. Throttle: `maxFps ?? 30` → `throttle(this.onRender, ceil(1000/maxFps), {leading: true, trailing: true})`, unthrottled in `debug` or screen-reader mode. New `<Static>` output "is still written once, ahead of the frame"; full static output is "Only kept in debug mode, where every frame rewrites it, and on the alternate screen, where it has to be replayed on full clears" — [ink.tsx](https://github.com/vadimdemedes/ink/blob/master/src/ink.tsx)
- Ink synchronized output: `bsu = '\u{1B}[?2026h'`, `esu = '\u{1B}[?2026l'`; `shouldSynchronize()` is true for any TTY stream outside CI (`isTTY && (isInteractive ?? !isInCi)`) — there is **no** terminal allowlist in Ink itself — [write-synchronized.ts](https://github.com/vadimdemedes/ink/blob/master/src/write-synchronized.ts)
- Ink issue #382 (opened 2020-09-22, closed 2023-04-01 with no fix): "if the terminal height is 10 lines for instance, and my ink app renders out 11 lines then the whole terminal history is wiped"; maintainer: "this behavior is built on purpose", "The part that's invisible (which you have to scroll up to see) is not going to re-render", and Ink "is not well-suited for fullscreen UIs" (pointing to blessed) — [ink#382](https://github.com/vadimdemedes/ink/issues/382)
- Ink discussion #621 (2023-09-01): the clear is triggered by the check `outputHeight >= this.options.stdout.rows`; commenting it out produced "only brief glitches"; a 2026-03-10 proposal (Feuermurmel) suggests a default mode that clips UI taller than the terminal instead of clearing scrollback plus an alternate-screen mode with mouse-wheel scrolling and a `useMainScreen(enable)` hook — [ink discussion #621](https://github.com/vadimdemedes/ink/discussions/621)
- Ink issue #450 title: "Flickering when rendering element with height precisely equal to `process.stdout.rows`" (search snippet only) — [ink#450](https://github.com/vadimdemedes/ink/issues/450)
- Ink release notes (page shows day/month without year): v7.0.0 (08 Apr) "Require Node.js 22", "Require React 19.2+", "Renders into the terminal's alternate screen buffer (like vim or less), restoring the previous terminal content on exit", "Kitty keyboard protocol: query all terminals in auto mode instead of a hardcoded allowlist", "Fix splitting wide characters (emoji, CJK) when overlapping writes occur"; v7.0.4 (24 May) "Share resize listener via `emitLayoutListeners` instead of per-hook listeners"; v7.0.6 (12 Jun) "Fix stale frames on Windows when output exactly fills the terminal"; v7.1.0 (17 Jun) "Add suspendTerminal() to hand the terminal to a child process"; v7.1.1 (16 Jul) "Preserve last `<Static>` line erased after a full-clear frame"; v8.0.0 (03 Oct) "Require React 19.3+", "Only the changed part of a line is written, which reduces output and flicker", "Replay `<Static>` output when resuming re-enters the alternate screen", "Redraw the frame when the terminal loses rows", "Preserve scrollback when clearing the viewport", "Stop replaying `<Static>` output on full-clear frames" — [Ink releases](https://github.com/vadimdemedes/ink/releases)
- Qwen Code's maintainer write-up "Ink Rendering And Flicker in Qwen Code: An Introduction" (#1778, opened 2026-02-10, closed 2026-06-26): `<Static>` is written once and kept; everything else is redrawn; if dynamic height ≥ terminal rows Ink "clears the entire terminal and redraws everything", which it calls "the biggest flicker trigger"; incremental mode "compares output line by line and rewrites only changed lines"; synchronized output "cannot be forced from Ink — the terminal decides whether it works"; flicker causes listed: dynamic output reaching terminal height, large/frequent writes and token-sized streaming chunks, unnecessary React re-renders, and environments (Windows terminals, remote VMs on poor networks, tmux, very short terminals). Its 7 design rules: keep dynamic output below terminal height; move append-only history into `<Static>`; commit completed lines to `<Static>` and keep only the live tail dynamic; batch streaming updates over a short interval; limit React re-renders to the changed region; evaluate incremental rendering case by case; treat synchronized output as a bonus, not a requirement — [qwen-code#1778](https://github.com/QwenLM/qwen-code/issues/1778)
- The same thread records a duplicate-output bug: `serializeTerminalToObject` called without `scrollOffset` so "every render reads from row 0 of the entire scrollback buffer", re-emitting history (commenter dorokuma, 2026-04-05, not confirmed by maintainers) — [qwen-code#1778](https://github.com/QwenLM/qwen-code/issues/1778)
- GitHub's engineering post on Copilot CLI (2026-01-28, Aaron Winston): Ink "re-renders on every state change", "doesn't manage frame deltas", "doesn't synchronize with terminal paint cycles", "doesn't solve flicker or cursor ghosting"; "Most terminals repaint the entire viewport when new content arrives"; the team relied on "Separating static and non-static components to minimize unnecessary redraws"; the early animation prototype used a 75 ms tick with a code comment "Higher can cause flicker in some terminals", production frames are 80 ms; Windows Command Prompt and older PowerShell "have limited or no ANSI support" — [GitHub Blog](https://github.blog/engineering/from-pixels-to-characters-the-engineering-behind-github-copilot-clis-animated-ascii-banner/)
- Gemini CLI PR #29629 describes the same path from the app side: "When Ink's last frame height is >= the terminal rows, it takes `renderFullTerminal` (`clearTerminal` + full static history + frame) instead of the incremental path. During streaming that repeats on every token update." Measured on a 20-row terminal: 164 full-clear frames out of 669 renders before, 0 of 766 after capping the pending-text height; on 60 rows 63/645 → 0/749; "total bytes written were not meaningfully reduced" — [gemini-cli#29629](https://github.com/google-gemini/gemini-cli/pull/29629)
- Other projects hitting the identical mechanism: Marco-Cricchio/moh #874 "TUI: viewport flicker with long sessions — Ink fullscreen path triggered when volatile region exceeds terminal height" (search snippet only) — [moh#874](https://github.com/Marco-Cricchio/moh/issues/874); PostHog wizard PR #1406 "bump ink to 7.1.1 to stop full-screen flicker" reports that Ink 7 "only clears the screen when output overflows the viewport, so full-height frames update in place" (community report, search snippet only) — [PostHog/wizard#1406](https://github.com/PostHog/wizard/pull/1406)
- Hermes (Ink-based) reproduces the lost-history symptom on Windows: responses over ~2,000 chars stream fine, then near the end "only the final 1-2 paragraphs remain", "All earlier content disappears and cannot be scrolled back to"; a 16,000-character / 240-line live-render cap (`boundedLiveRenderText`) is involved — [hermes-agent#55425](https://github.com/NousResearch/hermes-agent/issues/55425)

### Inferences
- The projects converge on the same architecture: (1) never let the *live* region reach terminal height (cap it, show "N lines hidden"), (2) push finished turns into write-once history, (3) throttle/batch token streams, (4) wrap frames in DEC 2026 where it is safe, (5) virtualize history for long sessions, and (6) when the main buffer cannot be made robust, take the alternate screen and own scrolling/selection yourself. Gemini and Hermes both forked Ink to get there; Qwen moved to Ink 7's incremental renderer plus its own viewport; Copilot wrote a cell-based renderer; Cline left Ink for OpenTUI.
- The year is not printed on Ink's releases page; the sequence (Hermes used Ink 6.8.0 in April 2026, Gemini's fork is 6.6.9, Qwen's "virtual viewport on ink 7" PR is May 2026, v8.0.0 is "03 Oct") places v7.0.0 on 2026-04-08 and v8.0.0 on 2026-10-03. Ink 8's "Only the changed part of a line is written" and "Preserve scrollback when clearing the viewport" directly target the failure modes catalogued above, but none of the surveyed projects had adopted Ink 8 as of their latest manifests (Gemini: `@jrichman/ink@6.6.9`; Hermes: local `@hermes/ink`; Qwen: Ink 7).
- For a .NET TUI that will not use Ink, the transferable lessons are the mechanics, not the library: compute the live-region height against `rows` on every frame; keep a flicker detector (Gemini's `useFlickerDetector` fires whenever the root frame measures taller than the terminal); diff lines instead of erase-and-rewrite; never emit CSI 3J; respect that DEC 2026 only works where the terminal implements it (and tmux handling is special).

### Gaps
- Ink's README text for the `<Static>` "output taller than the terminal" caveat was not reachable in the fetched version (the maintained behavior is documented only in source and issues).
- No primary source was found that benchmarks Ink 7/8 incremental rendering against Ink 6 beyond PR #29629's full-clear frame counts.

## Q2. Gemini CLI: rendering/performance history and fixes, settings, input handling, theming, confirmations and diffs, checkpointing//restore, session resume, what's new in 2026

### Takeaway
Gemini CLI went through three rendering generations in twelve months: (a) stock-Ink main-buffer rendering (flicker, bouncing prompt); (b) v0.15.0 (Nov 2025) alternate-screen mode with a forked Ink, a line-by-line incremental renderer, virtualized history, mouse scrolling and sticky headers — enabled by default for nine days and then turned off (v0.17.1) because selection/scrolling broke on many terminals; (c) April 2026 "TerminalBuffer" mode (static history + dynamic prompt/spinner, Ink render process, StaticRenderer/VirtualizedList) — also briefly default, reverted for performance regressions, and still opt-in (`ui.terminalBuffer: false`) when the epic was closed on 2026-10-14. Beyond rendering, its feature set (keybindings.json, vim mode, `!` shell mode, `@` mentions, `/rewind`, `/restore` with shadow-git checkpoints, Session Browser, persistent policy approvals) is the most complete reference among the Ink CLIs.

### Inferences
- Gemini's history is the clearest warning that *taking the alternate screen is a product decision, not a rendering trick*: the flicker fix was real, but losing native scrollback/selection on Windows consoles, tmux and older terminals produced enough complaints to reverse the default within nine days, and a year later neither alternate-buffer nor TerminalBuffer mode is default. A new TUI should either make main-buffer rendering robust (cap live height, line-diff, no scrollback erase) or detect terminal capability before entering the alternate screen, and must provide copy/selection and wheel scrolling parity if it does.
- Features worth copying for Corvid: confirmation option set that separates "once / this session / all future sessions (persisted to a policy file) / modify in editor / reject with feedback"; sticky headers on tool blocks; capped, top-overflowing live region with "lines hidden" hint and Ctrl+O to expand; queued tool confirmations; `keybindings.json` with unbind syntax; `!` toggle shell mode and `@` path completion; Esc-Esc rewind; shadow-git checkpoints with `/restore` re-proposing the tool call; auto theme switching from OSC 11 background probes; a flicker detector that logs when the frame exceeds the viewport; TUI regression tests (frame-count tests, "no continuous render" test).
- The `ui.renderProcess` setting plus the "terminal worker launching bug" in PR #24512 imply the fork runs Ink's layout/serialization off the main thread; this is not documented anywhere I could read.

### Gaps
- The `@jrichman/ink` fork's npm page returned HTTP 403, so its changes relative to upstream Ink 6.x (render worker, StaticRenderer, `maxWidth/maxHeight`, text-measurement API) could not be verified from source.
- PR #15783 (resize corruption fix), #29725 (tmux spinner fix) and #24873 contents were not read; only their linkage from issues is cited.
- No official per-terminal compatibility matrix for alternate-buffer/mouse support was found, although #13623 promised detection logic.

## Q3. Qwen Code: what it changed from Gemini CLI's UI

### Takeaway
Qwen Code forked Gemini CLI at v0.8.2, stopped syncing at Qwen Code v0.1, and from February 2026 ran its own rendering programme: a maintainer-written Ink flicker analysis (#1778), a "foundation" PR that throttles streaming, pre-slices tall tool output by visual height and gates synchronized output behind an allowlist (#3591), and an opt-in Ink 7 "virtual viewport" (`ui.useTerminalBuffer`) that mounts only the visible range of history and owns wheel/keyboard scrolling (#4146). Its visible UI remains close to Gemini's.

### Cited Findings
- README: the project "was originally based on" Google Gemini CLI v0.8.2; "Starting from Qwen Code v0.1, we stopped syncing with upstream"; npm install requires Node.js 22+; ships a desktop app (macOS/Windows/Linux) and an experimental `qwen serve` Web UI; built-in skills `/review, /batch, /loop, /bugfix` — [QwenLM/qwen-code README](https://github.com/QwenLM/qwen-code)
- Reviews describe the interface as "a mirror image of Gemini CLI", distinguished by branding, colour scheme and the `.qwen/` config directory (secondary, search snippets) — [morphllm](https://www.morphllm.com/qwen-cli), [elite-ai-assisted-coding](https://elite-ai-assisted-coding.dev/p/qwen-code-tool-review)
- Umbrella issue #2748 "TUI performance and UX improvements" (2026-03-30, open): "Slow Startup: TUI takes 3-5 seconds to start, especially when MCP servers are configured"; "Screen Flicker: Visual jumping/flashing during startup and view switching"; "Verbose Output: All content is fully expanded, no collapsible mechanism for long outputs"; users also asked to scroll up while an answer is still generating — [qwen-code#2748](https://github.com/QwenLM/qwen-code/issues/2748)
- PR #3591 "fix(cli): add TUI flicker foundation fixes" (merged 2026-04-25): throttles safe-content and thought promotion during streaming and adds redraw counters; avoids duplicate `clearTerminal` writes on `/clear`; "Pre-slices large plain-text and ANSI tool output by visual height, including long single-line JSON, base64, and minified output"; suppresses soft-wrap-only shell re-renders; "Gates synchronized terminal output behind a conservative terminal allowlist, with an opt-out and counters"; E2E assertion "No full-screen clear was emitted during assistant stream delta"; explicitly "does **not** claim to fully close every TUI flicker / long-output / detail-panel issue"; follow-ups: managed viewport & Static replacement, bounded detail & virtualized long output, shell E2E & terminal frame renderer — [qwen-code#3591](https://github.com/QwenLM/qwen-code/pull/3591)
- PR #4146 "feat(cli): virtual viewport for long conversations on ink 7" (opened 2026-05-14, merged 2026-06-02): legacy path uses `<Static>`, which is "append-only" and re-feeds the entire history on any remount (Ctrl+O, model change, Alt+M, resize) — "1000 `HistoryItemDisplay` renders" on a long session; new path: "only the visible viewport range is mounted in React", completed items frozen via `memo(HistoryItemDisplay)`, off-screen content kept in in-app scroll state rather than terminal scrollback; gated by `ui.useTerminalBuffer` (default `false`), legacy path "untouched"; keys Shift+↑/↓ (line), PgUp/PgDn, Ctrl+Home/End; mouse wheel via SGR tracking (`?1002h`, `?1006h`) while the list is mounted, Shift (Option on macOS) bypasses capture for native selection; scrollbar drag deferred; claims to close #3702, #2950 ("long-session scroll storm"), #3118 (flicker after alt-tab), #3007 (Ctrl+E/Ctrl+F flicker), #1491/#1861/#2924/#2928 (expand/collapse flicker), #2972, #2378 ("Win11 composer scroll storm"); the self-review notes error text could "leak paths into scrollback" and replaced it with a generic `[render error]` marker — [qwen-code#4146](https://github.com/QwenLM/qwen-code/pull/4146)
- #1778 closing (2026-06-26): flicker "greatly reduced" in current releases; implemented fixes listed as #3591, #3721 ("Bounds expanded sub-agent details by visual height"), #4146, and a `LiveAgentPanel` replacing the inline agent-execution frame — [qwen-code#1778](https://github.com/QwenLM/qwen-code/issues/1778)

### Inferences
- Qwen's path is the "stay on upstream Ink but engineer around it" option: upgrade to Ink 7, measure (redraw counters, full-clear counters in E2E), bound every tall thing (tool output, sub-agent details, live text) by *visual* height, and virtualize history yourself. That is the closest analogue for a from-scratch renderer: treat "height of what I am about to paint vs rows" as a hard invariant.
- The decision to gate DEC 2026 behind an allowlist with an opt-out (while Ink itself emits it for every TTY) reflects real breakage on terminals that mis-handle the sequence; Copilot later did the same for tmux.

### Gaps
- No Qwen release version was found for when #3591/#4146 shipped, and no benchmark numbers were published (the PR's "performance comparison harness" was listed as follow-up).
- Qwen's documentation page for `ui.useTerminalBuffer` and its non-rendering UI deltas (e.g. `/approval-mode`, session "welcome back") were not verified from primary docs.

## Q5. Hermes Agent (NousResearch): TUI stack, documented UI issues, notable features

### Takeaway
Hermes' `hermes --tui` (shipped in v0.11.0, 2026-04-23) is a React + Ink app in `ui-tui/` with its own forked Ink renderer (`@hermes/ink`), driven by a Python `tui_gateway` over newline-delimited JSON-RPC on stdio; the classic Python CLI remains the default. ### Inferences
- Hermes' TUI is the strongest evidence that Ink's `useInput` model (a global emitter, handlers run in registration order, one char per tick) is dangerous for an agent that overlays modal approvals: the approval freeze (#13618), blind-keystroke acceptance (#13634), the composer freeze on keystroke bursts (#90061) and the per-keystroke full re-render (#84349) all stem from input and rendering sharing one React tree. A new TUI should route input through a focus stack with explicit capture, and render the composer independently of the transcript.
- The "fast-echo path" (writing typed ASCII straight to stdout, bypassing the framework) is a tell that framework re-render latency was unacceptable; Corvid should budget input echo at well under one frame regardless of transcript size (and treat IME/CJK as first-class).
- Hermes' split (TypeScript screen ↔ Python gateway over JSON-RPC) adds failure modes a single-process .NET app avoids (gateway restarts, bundle rebuild races, orphaned subprocesses, journal/queue desync).
- Features worth copying: queue-while-busy with visible queue preview; live session switcher; `/rollback diff N` preview before restore; approvals as modal panels with session/always/deny; status line with elapsed time, compression and background-task counters, YOLO badge; `display.mouse_tracking` levels; theme detection order (env → `COLORFGBG` → OSC 11).

## Q6. Cross-cutting lessons from Ink maintainers and users; alternatives people moved to

### Takeaway
Across five projects the lessons are consistent: Ink's whole-frame repaint and viewport-overflow clear do not scale to streaming agents with long transcripts, so teams either forked Ink (Gemini, Hermes), upgraded and built viewports around it (Qwen), built their own cell renderer behind it (Copilot), or left for a native-backed renderer (Cline → OpenTUI; OpenCode → OpenTUI; Codex → Rust). The maintainer's own 2020 position — Ink "is not well-suited for fullscreen UIs" — still frames the trade-off, and Ink 8 (Oct 2026) is the first upstream release to address partial-line writes and scrollback preservation.

### Cited Findings
- Ink maintainer (2020): erasing history when output exceeds the terminal is "built on purpose"; "Ink is not well-suited for fullscreen UIs" (recommends blessed); open to an alternate-screen experiment — [ink#382](https://github.com/vadimdemedes/ink/issues/382)
- Ink 8.0.0: "Only the changed part of a line is written, which reduces output and flicker"; "Preserve scrollback when clearing the viewport"; "Redraw the frame when the terminal loses rows" — [Ink releases](https://github.com/vadimdemedes/ink/releases)
- Gemini CLI forked Ink (`npm:@jrichman/ink@6.6.9`) and states that robust incremental rendering outside the alternate buffer "need[s] to be implemented in the fork of the Ink library" — [package.json](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/package.json), [gemini-cli#14415](https://github.com/google-gemini/gemini-cli/issues/14415); it also added a render process (`ui.renderProcess`), `StaticRenderer`, `VirtualizedList`, a serializer, a flicker detector and performance-regression tests — [gemini-cli#24512](https://github.com/google-gemini/gemini-cli/pull/24512), [gemini-cli#21924](https://github.com/google-gemini/gemini-cli/issues/21924), [useFlickerDetector.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/ui/hooks/useFlickerDetector.ts)
- Hermes forked Ink into a local `@hermes/ink` package and added memory monitoring, FPS store, perf pane and a precision wheel — [ui-tui README](https://github.com/NousResearch/hermes-agent/tree/main/ui-tui)
- Qwen Code stayed on upstream (Ink 7) and added a virtual viewport, redraw counters, visual-height pre-slicing and a synchronized-output allowlist — [qwen-code#4146](https://github.com/QwenLM/qwen-code/pull/4146), [qwen-code#3591](https://github.com/QwenLM/qwen-code/pull/3591)
- Copilot CLI replaced its renderer twice: alt-screen (default 2026-03-18; old renderer removed in v1.0.12) and "Cell-based terminal renderer ... enabled for all users by default" (1.0.55, 2026-05-28) — [copilot-cli changelog](https://github.com/github/copilot-cli/blob/main/changelog.md), [copilot-cli#239](https://github.com/github/copilot-cli/issues/239)
- OpenAI's "Codex CLI is Going Native" (2025-05-30): TypeScript CLI's UI was Ink-based and "easy to build and iterate on", but the rewrite to Rust was justified by "Zero-dependency Install — currently Node v22+ is required", native security bindings for sandboxing, "no runtime garbage collection, resulting in lower memory consumption", and an extensible wire protocol; by 2025-12-02 `npm i -g @openai/codex` installed the native build — [openai/codex discussion #1174](https://github.com/openai/codex/discussions/1174)
- OpenTUI: Zig core with React/Solid renderers; "OpenCode uses OpenTUI in production for millions of users"; Cline CLI depends on `@opentui/react 0.4.3` — [anomalyco/opentui](https://github.com/anomalyco/opentui), [cline apps/cli/package.json](https://github.com/cline/cline/blob/main/apps/cli/package.json); third-party coverage says OpenCode moved from Go/Bubble Tea to OpenTUI for a better UI and performance (secondary, no primary statement found) — [openreplay blog](https://blog.openreplay.com/opentui-alternative-ink/)
- Synchronized output is not a silver bullet: Ink emits DEC 2026 on every TTY, but Qwen gated it behind an allowlist with opt-out and Copilot skips it under tmux "to avoid mouse pointer flicker" — [write-synchronized.ts](https://github.com/vadimdemedes/ink/blob/master/src/write-synchronized.ts), [qwen-code#3591](https://github.com/QwenLM/qwen-code/pull/3591), [copilot-cli changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)
- Alternate-screen costs that every project then had to pay: native selection/copy (Gemini Ctrl-S/F9 copy mode, Copilot `copy_on_select`, double/triple-click, X11/Wayland/WSL/Windows clipboard fixes), wheel scrolling speed and terminals without SGR mouse encoding, scrollbars, resize anchoring, restoring terminal modes after crashes/suspend, and replaying history on exit — [gemini-cli#13623](https://github.com/google-gemini/gemini-cli/pull/13623), [copilot-cli changelog](https://github.com/github/copilot-cli/blob/main/changelog.md), [gemini-cli#10677](https://github.com/google-gemini/gemini-cli/issues/10677)
- Keyboard protocol lessons: Gemini v0.35.0 added "the extended Kitty protocol" to keybindings; Ink 7 queries all terminals for kitty support instead of an allowlist; Hermes dropped keystrokes on kitty CSI-u sub-parameters and could not distinguish Shift+Enter on macOS Terminal.app / Windows Terminal — [changelog](https://github.com/google-gemini/gemini-cli/blob/main/docs/changelogs/index.md), [Ink releases](https://github.com/vadimdemedes/ink/releases), [hermes-agent#103885](https://github.com/NousResearch/hermes-agent/issues/103885), [Hermes CLI docs](https://hermes-agent.nousresearch.com/docs/user-guide/cli)
- Sanitization lesson: untrusted text (tool output, notifications) rendered raw can change terminal modes (`ESC[?9001h`) and persist into session files — [hermes-agent#124205](https://github.com/NousResearch/hermes-agent/issues/124205); Gemini added "strict checks preventing control characters from being rendered in Text objects" and passes diffs through `stripUnsafeCharacters` — [gemini-cli#7026](https://github.com/google-gemini/gemini-cli/issues/7026), [ToolConfirmationMessage.tsx](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/ui/components/messages/ToolConfirmationMessage.tsx)
- Cancellation lesson: a detached (unawaited) Ctrl-C cancel plus a double-tap force-quit can corrupt the persisted session — [gemini-cli#29588](https://github.com/google-gemini/gemini-cli/issues/29588); Copilot's `Esc` twice "within half a second" stops thinking, and Cline's Ctrl+C aborts first and exits on the second press — [GitHub Docs](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-copilot-cli), [Cline TUI docs](https://docs.cline.bot/usage/tui)

### Inferences
- Design rules distilled for a from-scratch renderer (each traceable to a cited failure): (1) maintain an explicit live-region height budget < rows, with top-overflow clipping and an "expand" key; (2) write finished turns once to scrollback and never repaint them (except on resize, in small batches); (3) line/cell diff with cursor addressing — never erase-and-rewrite the frame, never CSI 3J; (4) coalesce streaming deltas to a frame tick (Gemini/Ink 30 fps; Copilot's banner found >13 fps flickery on some terminals; Copilot later added "frame coalescing"); (5) wrap frames in DEC 2026 only when the terminal is known-good and skip it in tmux; (6) treat resize as "taint everything, redraw the full visible height"; (7) keep input parsing (CSI-u/kitty, bracketed paste, modified Enter, Win32 input mode) in a dedicated layer with a focus stack, and echo keystrokes without waiting for a transcript re-render; (8) sanitize every string from the model or tools before it reaches the terminal; (9) if the alternate screen is used, budget for selection, copy, wheel scrolling, scrollbars and exit-replay from day one, and offer a main-buffer fallback; (10) instrument: full-clear counters, frame-overflow detector, FPS/heap panes, and automated "no continuous rendering" tests.
- For Corvid's comparison against Hermes specifically: the Hermes TUI's defects are mostly architectural consequences of Ink + a separate Python gateway (input routing, per-keystroke re-render, orphaned processes, journal desync), not of its feature choices; its feature set (queue-while-busy, session switcher, rollback diff preview, modal approvals, mouse-tracking levels) is sound and worth matching.
