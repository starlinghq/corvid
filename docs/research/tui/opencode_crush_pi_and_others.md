# Terminal UIs of OpenCode/OpenTUI, Crush, pi, Amp, Goose, Aider, Cursor CLI, Droid and Warp (state as of 2026-10-21)

Scope note: notes gathered 2026-10-21 from primary sources (repos, changelogs, docs, maintainers' posts) with secondary sources flagged. Raw copies of the pi-tui README, pi CHANGELOGs and pi docs used for the version/date lookups are saved under `(session scratchpad, not included)`.

## Cross-cutting: where the "scrollback-first vs alternate screen" debate stands in October 2026

### Takeaway
Between July and October 2026 the three agents Corvid's plan cites as scrollback-first models all added or defaulted to an alternate-screen ("fullscreen") renderer: pi 1.0 (2026-10-01) made fullscreen the default, Claude Code's fullscreen mode is the default for new users since 2026-05-06, and OpenCode's lead summarised it as "pretty much every terminal coding agent has now switched over to a fullscreen TUI" (2026-09-29), while keeping a scrollback-first `opencode mini`. The scrollback-first approach is still shipped by all three as an explicit opt-in/alternative, and its known failure modes (reflow above the viewport, `ESC[3J` clears, terminals without synchronized output) are now well documented.

### Cited Findings
- pi 1.0.0 (2026-10-01): "**Fullscreen by default** — The TUI now runs fullscreen. Set `tuiMode` to `"regular"` to keep the terminal's normal scrollback." — [pi coding-agent CHANGELOG](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md)
- pi's motivating bug (#7304, opened 2026-07-30, pi 0.83.0 on Windows Terminal): when the user scrolls up while a long markdown answer streams, "the view jumps and the scrollback they were reading is wiped"; root cause is that `TUI.doRender()` calls `fullRender(true)` when the first changed line is above the previous viewport top, which emits `ESC[3J` and clears terminal scrollback; badlogic's answer was an experimental alternate-screen renderer that "owns the viewport", shipped the same day via commit c13ffe1 with the stated goal of becoming the default — [earendil-works/pi#7304](https://github.com/earendil-works/pi/issues/7304)
- Dax (OpenCode): "pretty much every terminal coding agent has now switched over to a fullscreen TUI (after telling us we were wrong for doing this) probably a good time to mention `opencode mini` which is a minimal scrollback version of opencode" (post ID 2105079184225603658, timestamp decodes to 2026-09-29 23:36 UTC) — [x.com/thdxr](https://x.com/thdxr/status/2105079184225603658)
- Claude Code docs: fullscreen "draws the interface on the terminal's alternate screen buffer, like `vim` or `htop`, and only renders messages that are currently visible"; new users who "first used Claude Code on or after May 6, 2026" start in fullscreen; `/tui default` and `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` keep "the conversation in your terminal's native scrollback so `Cmd+f` and tmux copy mode work as usual" — [Claude Code: Fullscreen rendering](https://code.claude.com/docs/en/fullscreen)
- Claude Code's TUI engineer (chrislloyd, HN, ~Jan 2026): Neovim and Codex use the alternate screen buffer while Claude Code uses scrollback and must "clear entirely and redraw everything when it changes"; "There's no way to incrementally update scrollback in a terminal."; "Synchronized output totally eliminates flickering"; the differential renderer has "a ~16ms frame budget"; disputed in-thread by withinboredom: "There is absolutely a way to incrementally update scrollback in a terminal, 100% flicker-free." — [HN comment 46701013](https://news.ycombinator.com/item?id=46701013), [HN thread 46699072](https://news.ycombinator.com/item?id=46699072)
- Mario Zechner's taxonomy (2025-11-30): full-screen TUIs "own the viewport and treat it like a cell buffer" ("Amp and opencode use this approach") and "you lose the scrollback buffer, which means you have to implement custom search"; "Mouse scrolling specifically always feels kind of off in such TUIs"; append-style CLIs ("Claude Code, Codex, and Droid") write like normal programs and only move the cursor within the viewport; he chose append-style for pi because coding agents are "essentially linear chats" and it keeps native scrolling and search — [mariozechner.at 2025-11-30](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)
- OpenCode has a third mode: OpenTUI's `split-footer` keeps a fixed footer on the main screen and commits history rows into real terminal scrollback ("Captured writes become ordered scrollback commits above the footer") — [OpenTUI renderer docs](https://opentui.com/docs/core-concepts/renderer); the same approach is attributed to Codex's `grow_viewport` in `codex-rs/tui/src/tui/scrollback.rs` — [anomalyco/opentui#1630](https://github.com/anomalyco/opentui/issues/1630)
- Charm (2026-02-23) framed Bubble Tea v2 around the same shift: AI agents moved into the terminal and "the terminal became a primary platform for development tools", so rendering had to become "faster and more efficient by orders of magnitude" — [charm.land/blog/v2](https://charm.land/blog/v2/)
- Warp (2026-04-29) describes the structural limit all TUIs hit: from the application's point of view "there's no such thing as a 'command,' just a stream of bytes in and a stream of bytes out", and alt-screen programs have no scrollback and the alt screen "gets replaced wholesale when the program exits" — [warp.dev block model post](https://www.warp.dev/blog/block-model-behind-warps-agentic-development-environment)

### Inferences
- The projects did not abandon scrollback-first because it is wrong for linear chat; they abandoned it as the *default* because two unfixable cases (reflow of lines already in scrollback, and terminals without DEC 2026) produce the two most-complained-about symptoms (scroll jump and flicker). Every one of them kept a scrollback-first path and a documented "hand the transcript back to the terminal" escape hatch.
- For Corvid, the pragmatic reading is: build the line-diff/scrollback renderer first (pi "regular", Claude Code "classic", OpenCode `mini`), design the component tree so the same `render(width) -> lines` output can later be painted into an app-owned viewport, and treat the alternate-screen mode as a second renderer behind one interface, exactly as pi-tui's `TUI` interface with `TuiMainScreen`/`TuiAltScreen` does.

### Gaps
- I did not find a write-up by Mario Zechner explaining the 1.0 default flip beyond the CHANGELOG line and issue #7304; any X/Discord posts are not fetchable here.
- Codex's TUI (ratatui) was out of scope and only appears as a cited reference implementation of inline viewport + scrollback insertion.

## pi (badlogic/pi-mono → earendil-works/pi) and pi-tui

### Takeaway
pi-tui is a ~950-line-README, framework-free TypeScript library whose main-screen renderer diffs full-document line output against a backbuffer and rewrites from the first changed line, wrapped in DEC 2026; since 0.84.0 (2026-08-06) the same `TUI` interface also has an alternate-screen renderer with app-owned scrolling, mouse hit-testing, drag selection with OSC 52 copy, transcript search and OSC 133 navigation, and pi 1.0.0 (2026-10-01) made that fullscreen mode the default. Ownership moved to Earendil in April 2026 and the package is now `@earendil-works/pi-tui` 1.4.0 (2026-10-21).

- The TUI package today is `"name": "@earendil-works/pi-tui", "version": "1.4.0"` with native clipboard builds for darwin, linux and win32 (`native/clipboard.h`, `native/win32/prebuilds/**/*.node`) — [packages/tui/package.json](https://github.com/earendil-works/pi/blob/main/packages/tui/package.json)

Design rationale (author's own words, 2025-11-30)
- Rejected Ink-style: "I definitely don't want to write my TUI like a React app"; "Blessed seems to be mostly unmaintained, and OpenTUI is explicitly not production ready."; "TUIs are mostly portable and easily streamable, they also suck at information density." — [mariozechner.at 2025-11-30](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)
- Retained-mode model: a `Component` has `render(width)` returning ANSI lines plus optional `handleInput(data)`; `Container` stacks children; "an assistant message that's fully streamed doesn't need to re-parse markdown and re-render ANSI sequences every time"; the TUI keeps a backbuffer of what it wrote and diffs — same source
- Differential rendering, three cases: first render outputs everything; width change clears and re-renders everything ("since soft wrapping changes"); normal update finds the first differing line, moves the cursor there and redraws to the end; "The terminal doesn't let you write to the scrollback buffer above the viewport" so a change above the viewport forces a full clear — same source
- Flicker: output wrapped in `CSI ?2026h`/`CSI ?2026l`; "In any capable terminal like Ghostty or iTerm2, this works brilliantly and you never see any flicker."; in VS Code's terminal "you will get some flicker depending on the time of day, your display size, your window size, and so on. And it still flickers less than Claude Code." — same source
- Cost: "Realistically, on computers younger than 25 years, this is not a big deal"; memory "a few hundred kilobytes for very large sessions"; "What I get in return is a dead simple programming model that lets me iterate quickly." No frame timings published — same source
- Claude Code critique in the same post: "Also, it flickers."; background bash "has poor observability (a common theme with Claude Code)" — same source
- 2025-12-22: pi lets "custom tools ... contribute custom UI to pi, a feature I haven't seen in any of the other coding agent harnesses"; deliberately "No MCP support, no built-in sub-agents, no plan mode, no to-do tool." — [mariozechner.at 2025-12-22](https://mariozechner.at/posts/2025-12-22-year-in-review-2025/)

Current pi-tui rendering model (README on main, 2026-10)
- "Interchangeable Renderers: Shared `TUI` interface with main-screen and alternate-screen implementations"; "Differential Rendering: Updates only changed lines or viewport rows"; "Synchronized Output: Uses CSI 2026 for atomic screen updates (no flicker)" — [packages/tui/README.md](https://github.com/earendil-works/pi/blob/main/packages/tui/README.md)
- "`TuiMainScreen` renders into the main terminal buffer and preserves terminal scrollback."; "`TuiAltScreen` renders a fixed-height viewport in the alternate terminal buffer with application-owned scrolling. When stopped, it restores the main buffer and prints the complete final document." — same
- `TuiMainScreen` strategies: "First Render: Output all lines without clearing scrollback"; "Width Changed or Change Above Viewport: clear the screen and fully re-render"; "Normal Update: move the cursor to the first changed line, clear to the end, and render the changed lines" — same
- Mouse: "`TuiMainScreen` does not capture mouse input because the terminal owns its scrollback."; `TuiAltScreen` "normalizes SGR mouse input and hit-tests components and overlays"; return flags `handled`/`capture`/`focus`; "Render requests are coalesced and terminal output remains differential."; hit-testing uses "geometry recorded by the last rendered frame, so pointer motion does not rerender children" — same
- Alt-screen layout: `VStack`, `HStack`, `ScrollView` with `basis/grow/shrink/minSize/maxSize`; "These semantics are intentionally unavailable on `TuiMainScreen`, where the terminal owns scrollback."; wheel "chains unused delta to outer scroll views"; jumps "between OSC 133 semantic prompt markers"; `Ctrl+Shift+F` search panel with `Enter`/`Ctrl+G` next and `Shift+Enter`/`Ctrl+Shift+G` previous; `scrollToEndIndicator` clickable "jump to end" label — same
- Selection/copy: "Dragging with the primary mouse button selects text and, unless `TuiAltScreenOptions.copyOnSelect` is `false`, copies it to the clipboard with OSC 52; holding the drag at a scroll view's top or bottom edge auto-scrolls and extends the selection"; OSC 8 links open on click; scrollbars support "hover expansion, thumb dragging, and track-click jumping" — same
- Images: Kitty graphics protocol images crop vertically in alt-screen; iTerm2 inline images "fall back to text because the iTerm2 protocol cannot delete or crop placements during viewport repainting" (they render normally on main screen) — same
- Invariants: "Each line **must not exceed `width`** or the TUI will error."; "The TUI appends a full SGR reset and OSC 8 reset at the end of each rendered line."; components "should cache output keyed by width and clear it in `invalidate()`" — same
- Hardware cursor/IME: focused components emit a zero-width `CURSOR_MARKER` and the TUI positions the hardware cursor there; `renderFakeCursor()` draws reverse-video; hardware cursor hidden by default, `showHardwareCursor` for terminals that need it for IME — same
- Keys: `matchesKey()`/`Key` helpers "supports Kitty keyboard protocol"; raw mode so Ctrl+C must be intercepted by the app; `Terminal` interface is `start(onInput, onResize)`, `stop`, `write`, `columns`, `rows`, `moveBy`, `hideCursor`, `showCursor`, `clearLine`, `clearFromCursor`, `clearScreen`; `VirtualTerminal` on `@xterm/headless` for tests; `PI_TUI_WRITE_LOG` dumps the raw ANSI stream — same

### Inferences
- pi's July→October 2026 arc is the clearest evidence that the main-screen differential renderer cannot keep a scrolled-up viewport stable while streaming markdown reflows: the author did not patch the main-screen path, he added an app-owned viewport. The main-screen path remains supported ("regular") but the fixes since August overwhelmingly target fullscreen.
- The explicit "lines must not exceed width" + "SGR/OSC 8 reset per line" rules are what make line-level diffing safe; Corvid's component contract should adopt both.
- The tui 1.4.0 exit-handler fix (#11170) and the 0.84.0 "capability-query replies leaking into the shell" fix are the two shutdown bugs a .NET port will also hit: restore modes synchronously on any exit path and drain query responses before exiting raw mode.

## Claude Code's renderer and Ink (the other half of Corvid's "Claude Code and pi style" model)

### Takeaway
Claude Code started on Ink, replaced Ink's writer with its own React→layout→rasterize→diff→ANSI pipeline (December 2025/January 2026, "~85%" less flicker), then added an alternate-screen "fullscreen" renderer with virtualized transcript, in-app selection with multiple clipboard paths, a `[`-key "write the transcript back to native scrollback" escape, and a diff panel; a v2.1.89 regression (April 2026) that enabled it by default and destroyed scrollback shows the migration risk.

### Cited Findings
- Ink's model (README): `<Static>` "permanently renders its output above everything else" for "things that don't change after they're rendered"; `incrementalRendering` "only updates changed lines instead of redrawing the entire output ... Lines containing unsupported terminal controls fall back to whole-line updates."; `alternateScreen` option: "The terminal's scrollback buffer is not available while in the alternate screen."; default `maxFps` 30; "When the terminal is resized narrower, ghost lines may briefly appear" — [vadimdemedes/ink README](https://github.com/vadimdemedes/ink)
- Anthropic statement quoted on HN: "We originally built Claude Code on Ink, a React renderer for the terminal"; they moved to their own renderer while still using React — [HN 46699072](https://news.ycombinator.com/item?id=46699072); HN moderator links a December 2025 post "We've rewritten Claude Code's terminal rendering to reduce flickering by 85%" — same; a third-party post says the flicker fix landed in 2.0.72 — [steipete.me](https://steipete.me/posts/2025/signature-flicker) (secondary)
- chrislloyd (Claude Code TUI rendering): "we shipped our differential renderer to everyone today"; "only ~1/3 of sessions see at least a flicker"; causes included "no `<Static>` components, more frequent re-renders, and GC pauses", fixed with memoization and "converting the screen buffer to packed TypedArrays"; pipeline "React → layout → rasterize → diff → ANSI" with "a ~16ms frame budget"; they upstreamed DEC 2026 support to VS Code's terminal and tmux — [HN 46701013](https://news.ycombinator.com/item?id=46701013)
- Fullscreen mode: "eliminates flicker, keeps memory usage flat in long conversations, and adds mouse support"; "Only visible messages are kept in the render tree, so memory stays constant regardless of conversation length."; "The input box stays fixed at the bottom of the screen"; selection "copies automatically on mouse release"; `Ctrl+o` transcript mode with `less`-style keys and `/` search; `[` "writes the full conversation into your terminal's native scrollback buffer, with all tool output expanded"; `v` opens it in `$EDITOR`; `/diff` opens a panel beside the conversation — [Fullscreen rendering docs](https://code.claude.com/docs/en/fullscreen)
- Clipboard paths: local `pbcopy` / `wl-copy`,`xclip`,`xsel` (writes clipboard and PRIMARY) / PowerShell `Set-Clipboard`; tmux paste buffer; OSC 52 over SSH; "Claude Code prints a toast after each copy telling you which path it used."; native selection via Shift/Option/Fn depending on terminal; `CLAUDE_CODE_DISABLE_MOUSE=1` and `CLAUDE_CODE_DISABLE_MOUSE_CLICKS=1` — same
- Scroll: `CLAUDE_CODE_SCROLL_SPEED` (VS Code sends "exactly one event per notch"; "Claude Code can't detect which"), `/scroll-speed` dialog, wheel acceleration (`wheelScrollAccelerationEnabled`), JetBrains terminal gets special handling — same
- Windows: "Some terminals, most commonly Windows Terminal and other ConPTY-backed hosts, coalesce these positioned writes incorrectly and leave fragments of earlier output on screen until you resize"; `CLAUDE_CODE_ALT_SCREEN_FULL_REPAINT=1` repaints every cell; SSH to Windows and iTerm2 `tmux -CC` force classic — same
- Failure handling: a session counts as started once it "has drawn its first frame and then either stayed up for 10 seconds or you ended it"; after two failed fullscreen starts Claude Code falls back to classic until updated — same
- Regression: issue #41965 (opened 2026-04-01) "v2.1.89 regression: flicker-free rendering destroys terminal scrollback by default" — with output over ~24 rows the whole conversation was re-rendered and "only about 1–2 pages of history" survived; closed 2026-04-17 as duplicate of #41814, fixed in v2.1.101; no Anthropic staff comment — [anthropics/claude-code#41965](https://github.com/anthropics/claude-code/issues/41965)
- tmux flicker issue #37283 asking for DECSET 2026 was closed "not planned" — [anthropics/claude-code#37283](https://github.com/anthropics/claude-code/issues/37283) (search snippet)
- Terminal config page: `/terminal-setup` writes Shift+Enter bindings and sets VS Code `terminal.integrated.gpuAcceleration` to `"off"` "to prevent garbled text"; tmux needs `allow-passthrough on` and `extended-keys on`; theme JSON files in `~/.claude/themes/` hot-reload; OSC 7501 "Program Status Protocol" status reporting since v2.1.295 — [terminal-config docs](https://code.claude.com/docs/en/terminal-config)

### Inferences
- Claude Code's fullscreen docs are effectively a checklist of everything an alt-screen agent must re-implement: selection with word/line granularity, several clipboard backends with user feedback, "export to scrollback", search, jump-to-bottom with new-message count, scroll speed detection, full-repaint fallback for ConPTY, and a crash-counter fallback to the classic renderer.
- The v2.1.89 incident is the concrete risk of "switch renderers by default": the regression was not the renderer itself but the transition logic (re-rendering on overflow).

### Gaps
- Anthropic's own December 2025 rendering post could not be fetched (only HN references); exact release numbers for the differential renderer vary across secondary sources (2.0.72 vs "December 17").

## OpenCode and OpenTUI

### Takeaway
OpenCode went Go/Bubble Tea (Kujtim Hoxha's original) → TypeScript on OpenTUI after the mid-2025 split with Charm; OpenTUI is a Zig core with TS/React/Solid bindings, flexbox (Yoga) layout, cell-diff encoding and three screen modes (`alternate-screen` default, `main-screen`, `split-footer`). OpenCode's main TUI runs on the alternate screen; `opencode mini` (OpenCode 2, 2026) is the scrollback-first client on `split-footer`, and both the alt-screen mode (no scrollback, Neovim users) and split-footer mode (five scrollback bugs filed Oct 2026, resize replay) have documented complaints. The TUI is a client of a per-user shared background server in OpenCode 2.

### Cited Findings
History and reasons
- Third-party HN retelling (2025-07-07, vidyesh): "Kujtim started opencode few years back"; "thdxr(dax)(SST) and Adam started contributing"; Charm "approached Kujtim for some deal to move opencode to charm"; "Dax and Adam wanted to keep it open source as is. What OpenTUI is (primary docs, release 0.6.6)
- "OpenTUI is a native terminal UI core written in Zig with TypeScript bindings. It renders a component tree, lays it out with Flexbox, handles terminal input, and updates the cells that changed." — [opentui.com/docs](https://opentui.com/docs)
- Packages: `@opentui/core`, `@opentui/react`, `@opentui/solid`, `@opentui/keymap`, `@opentui/qrcode`, `@opentui/three` (WebGPU), `@opentui/ssh`; "OpenCode uses OpenTUI in production for millions of users"; dev requires Bun 1.4.1+ and Zig 0.16.0; MIT — [anomalyco/opentui README](https://github.com/anomalyco/opentui)
- Core: "It is written in Zig."; "The TypeScript packages call native Zig through an internal foreign function interface (FFI) boundary."; runs on "Bun 1.3.14 or later, or on Node.js 26.4.0 or later with ESM and `--experimental-ffi`"; "Native Windows arm64 requires Bun 1.4.0 or later." — [packages/core/README.md](https://github.com/anomalyco/opentui/blob/main/packages/core/README.md)
- Diffing: the renderer "compares cells with its existing encoding state, so an update need not send the entire screen again"; "The native library does not start an application event loop or a rendering worker."; a frame is "presented" only after the host reports delivery — [opentui.com/docs/native/overview](https://opentui.com/docs/native/overview); "The current buffer is encoding comparison state, not a guaranteed copy of the last presented frame."; "At most one output ticket can remain outstanding per Session." — [opentui.com/docs/native/frames](https://opentui.com/docs/native/frames)
- Screen modes: `alternate-screen` (default) "Uses the terminal's alternate screen and restores the main screen when the renderer exits."; `main-screen` "Uses a reserved region on the main screen"; `split-footer` "Uses a footer on the main screen", `footerHeight` default 12; `externalOutputMode` defaults to `capture-stdout` in split-footer and "Captured writes become ordered scrollback commits above the footer." — [opentui.com/docs/core-concepts/renderer](https://opentui.com/docs/core-concepts/renderer)
- Render loop: demand-driven (`requestRender()`), `start()` for continuous `targetFps`/`maxFps`; `requestResize` debounced 100 ms ("only the latest size applies"; skipped in split-footer); "OpenTUI listens for `SIGWINCH` only when it uses `process.stdout`."; `nativeSceneWorkBudget` lets preparation yield but "Painting runs in one native call and never yields" — same
- Platforms: example executables for macOS x64/arm64, Linux x64, Windows x64 "including x64 WSL and Git Bash" — [opentui.com/docs](https://opentui.com/docs)

## Goose (Block → Agentic AI Foundation)

### Takeaway
Goose's CLI is a Rust, line-oriented REPL (rustyline-style editing, slash commands, themes for markdown highlighting), not a full-screen TUI; the maintainers wrote in March 2026 that "there's no ambition to be a full blown TUI" while planning a TypeScript TUI prototype and consolidating three binaries around ACP.

### Cited Findings
- Roadmap discussion #7697 (2026-03-06, DOsinga): the CLI is "a line-oriented CLI that can adapt to do slightly better depending on the terminal that it runs in"; "can borrow some ideas from the Rust TUI work, but there's no ambition to be a full blown TUI"; "We should add a decent TUI (we have a prototype in typescript)"; proposal to replace `goose`, `goosed`, `goose-acp-server` with "one binary that speaks one protocol" (ACP), `goose serve` over HTTP/WebSocket; alexhancock: ACP is "the future protocol of goose" — [goose discussion #7697](https://github.com/block/goose/discussions/7697)
- CLI docs: slash commands `/mode` (`auto`, `approve`, `chat`, `smart_approve`), `/compact`, `/r` toggles full tool output, `/t` cycles `light`/`dark`/`ansi` themes ("Syntax highlighting styles only affect the font, not the overall terminal interface."); Ctrl+J newline (`GOOSE_CLI_NEWLINE_KEY`), Ctrl+R reverse history search; `GOOSE_PROMPT_EDITOR` "replaces the standard CLI input and keyboard shortcuts for the entire session"; sessions: `--resume`, `--history`, `--fork` (copy with history), `--edit` ("opens the conversation as YAML") — [goose-docs.ai CLI commands](https://goose-docs.ai/docs/guides/goose-cli-commands/)
- Desktop and CLI "share one session store" — [goose-docs.ai session management](https://goose-docs.ai/docs/guides/sessions/session-management/) (search snippet)
- Secondary: a sandbox analysis lists rustyline for input and "no TUI framework (no ratatui, tui-rs, crossterm widget layers)" — [agent-safehouse.dev](https://agent-safehouse.dev/docs/agent-investigations/goose); the repo moved to `aaif-goose/goose` under the Linux Foundation's Agentic AI Foundation in April 2026 — [morphllm comparison](https://www.morphllm.com/comparisons/opencode-vs-goose) (secondary)

### Inferences
- Goose is the counter-example: a plain REPL keeps every terminal feature (scrollback, selection, search) for free and costs nothing in rendering bugs, at the price of no fixed composer, no live tool-call panels and no mouse. Its `--edit` (conversation as YAML in `$EDITOR`) and `--fork` are cheap, copyable session features.

### Gaps
- No primary statement on the exact Rust line-editing crate was fetched from the repo itself.

## Aider

### Takeaway
Aider is a Python prompt_toolkit + Rich program that streams markdown by re-rendering the accumulated text and splitting it into "stable" lines printed to the console and the last 6 lines repainted in a Rich `Live` window ("The live window doesn't play nice with terminal scrollback"); its praised feature is the git flow: every edit is auto-committed with a model-written Conventional Commits message, `/undo` reverts the last change and `/diff` shows changes since the last message.

### Cited Findings
- `aider/mdstream.py`: `live_window = 6` ("Number of lines to keep visible at bottom during streaming"); `min_delay = 1.0 / 20` ("Minimum time between updates (20fps)"); adaptive `self.min_delay = min(max(render_time * 10, 1.0 / 20), 2)`; docstring: "The stable lines emit to the console above the Live window. The unstable lines emit into the Live window so they can be repainted."; comment: "Markdown going to the console works better in terminal scrollback buffers. The live window doesn't play nice with terminal scrollback." — [Aider-AI/aider mdstream.py](https://github.com/Aider-AI/aider/blob/main/aider/mdstream.py)
- Git integration: "Whenever aider edits a file, it commits those changes with a descriptive commit message."; dirty files are committed first so "your edits and aider's stay separate"; "Aider sends the `--weak-model` a copy of the diffs and the chat history and asks it to produce a commit message." (Conventional Commits by default, `--commit-prompt`); author/committer get "(aider)" appended, with `--attribute-co-authored-by` alternative; `/undo` "will undo and discard the last change"; `/diff` "will show all the file changes since the last message you sent"; `/commit`, `/git`; `--no-auto-commits`, `--no-dirty-commits`, `--no-git` ("not recommended") — [aider.chat/docs/git](https://aider.chat/docs/git.html)
- Stack (secondary): prompt_toolkit for input, Rich for output — [agent-safehouse.dev](https://agent-safehouse.dev/docs/agent-investigations/aider)
- prompt_toolkit limits that apply to any prompt_toolkit app: "Mouse support breaks scrolling" (#168) and mouse scroll event problems (#449) — [prompt-toolkit#168](https://github.com/prompt-toolkit/python-prompt-toolkit/issues/168), [#449](https://github.com/prompt-toolkit/python-prompt-toolkit/issues/449)

### Inferences
- Aider's "print stable lines, repaint only a small tail" is the minimal scrollback-friendly streaming technique and maps directly onto a line-diff renderer: only the tail of a streaming markdown block should be mutable; everything above it should be frozen once it can no longer reflow.
- Its auto-commit + `/undo` design is the cleanest model for Corvid's undo/rollback: one git commit per agent edit, weak-model commit messages, attribution flags.

### Gaps
- I found no aider-specific GitHub issue about flicker or scroll jumps; searches returned only Claude Code/Copilot issues.

## Cursor CLI (`cursor-agent` / `agent`)

### Takeaway
Cursor's CLI is an Ink/React (Node) interactive agent with Agent/Plan/Ask modes (Shift+Tab), a Ctrl+R change-review view, y/n command approvals and `agent resume`/`--continue`; user reports in 2026 show Ink-era problems (an inverse-video fake cursor invisible on light themes, a segfault/heap exhaustion while painting a ~13k-char highlighted string).

### Cited Findings
- Docs: "Start a conversational session with the agent to describe your goals, review proposed changes, and approve commands"; modes Agent/Plan/Ask with Shift+Tab, `/plan`, `/ask`; `-p` print mode; `&` prefix hands off to a Cloud Agent; `agent ls`, `agent resume`, `--continue`, `--resume="<chat-id>"`; `/sandbox` toggles; sudo password "flows directly to `sudo` via a secure IPC channel; the AI model never sees it" — [cursor.com/docs/cli/overview](https://cursor.com/docs/cli/overview)
- "Review changes with Ctrl+R."; "Press i to add follow-up instructions."; "Use ArrowUp/ArrowDown to scroll, and ArrowLeft/ArrowRight to switch files."; "Before running terminal commands, CLI will ask you to approve (y) or reject (n) execution."; Ctrl+J/Ctrl+Enter newline ("For tmux users, use Ctrl+J instead."); Ctrl+D double-press to exit — [cursor.com/docs/cli/using](https://cursor.com/docs/cli/using); slash command reference (`/model`, `/plan`, `/ask`, `/goal`, `/summarize`, `/open`) — [slash commands](https://cursor.com/docs/cli/reference/slash-commands)
- Crash report (2026-09-21, cursor-agent 2026.09.18): "intermittently hard-crashes on Linux x86_64 while the Ink/React TUI redraws large ANSI-styled or syntax-highlighted terminal output"; stack frames "onImmediateRender / Yoga layout, React commit", "String[13289] and JSArray[208] of ANSI tokens"; staff reply attributed it to JavaScript heap exhaustion and suggested `NODE_OPTIONS=--max-old-space-size=4096`; workarounds `NO_COLOR=1` or `agent -p` — [forum.cursor.com 172501](https://forum.cursor.com/t/cursor-agent-cli-crash-on-linux-x86-64-herdr/172501)
- Light-theme bug report: reporter's hypothesis that the input box "is rendered by Ink, which hides the host terminal's native cursor and draws its own cursor using inverse video", with no theme/cursor colour setting in `cli-config.json` — [forum.cursor.com 160845](https://forum.cursor.com/t/cursor-agent-cli-input-cursor-invisible-on-light-theme-terminals-please-expose-theme-cursor-color-in-cli-config-json/160845)

### Inferences
- Cursor CLI confirms two Ink-class hazards for any renderer: never paint a large highlighted blob as one string (chunk tool output; virtualise), and a drawn cursor needs theme-aware colours or the real hardware cursor.

### Gaps
- No official Cursor statement names Ink; the evidence is stack traces and reporter hypotheses.

## Warp agent mode (a terminal that owns rendering)

### Takeaway
Warp (Rust, GPU-backed, custom UI framework, since 2021) replaces the character grid with a typed block list; agent conversations are rich blocks that render "reasoning, tool calls, and diffs inline", virtualised at block and row level, and scroll as one stream, which is exactly what an in-terminal TUI cannot do because the PTY only sees bytes.

### Cited Findings
- Engineering post (2026-04-29, David Stern and Oz): foundations are "a typed block list, a GPU-backed renderer, and a custom UI framework built in Rust"; "Where a traditional terminal is a single grid of character cells, Warp's BlockList is an ordered list of typed blocks"; agent conversation blocks "render an agent session's reasoning, tool calls, and diffs inline alongside your own work"; "we only pay rendering costs for what you can actually see"; alt-screen programs get "a separate `AltScreen` with its own `GridStorage`, outside the block list"; "there's no such thing as a 'command,' just a stream of bytes in and a stream of bytes out" — [warp.dev block model post](https://www.warp.dev/blog/block-model-behind-warps-agentic-development-environment)
- Docs: terminal mode is the default; auto-detection labels input "agent" or "shell"; "Agent controls appear only when you're in a conversation, keeping your terminal clean otherwise."; commands run inside a conversation "only appear within that specific conversation and don't appear in the terminal block list"; code review pane `⌘⇧+`, toggle auto-accept `⌘⇧I` — [docs.warp.dev terminal and agent modes](https://docs.warp.dev/agents/local-agents/interacting-with-agents/terminal-and-agent-modes/); terminal blocks "can be attached as context to any conversation" — [docs.warp.dev blocks as context](https://docs.warp.dev/agents/local-agents/agent-context/blocks-as-context/)

### Inferences
- The capabilities Warp gets for free (typed blocks, per-block selection "in one gesture", virtualised rendering, inline diff widgets that are not text) are the ceiling a TUI can only approximate: OSC 133 prompt marks, OSC 8 links, OSC 52 clipboard and DEC 2026 are the protocol-level pieces a TUI can use to recover some of it (pi-tui already uses all four).

### Gaps
- Warp's docs do not describe selection/copy inside agent blocks or any ANSI-level comparison.
